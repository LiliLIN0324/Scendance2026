01

这件事今天为什么难

我们不是在做「又一个 AI 出图工具」。难点在另外三件事上——它们都不是生成模型能解决的。

难点一

场地是真的，比例不是

效果图里的草坪和真实草坪差着几十米。布置方案一旦尺寸不对，落地就全废。 所以我们先解决坐标：锚点、高德 POI 点位、OSM 真实多边形，全部转成同一套局部米制坐标。

难点二

物料库里没有婚礼的东西

976 个模型里没有白木椅、没有香槟塔、没有桌花。婚礼物料要么靠采购清单里的一行字， 要么现做。我们选择现做，并且把做出来的东西公开回物料库，让下一个婚礼直接用。

难点三

生成出来的东西没有尺寸

AI 生成的 3D 没有绝对尺寸，比例跟着参考图走。所以我们不假装它准： 每个物件的实测包围盒尺寸都记在案，并单列一张偏差表——备料前必须以实测为准。

难点四

交付物必须是能照着搭的

「一张好看的平面图」没法施工。要交付的是：分区边界、每件物料的规格与数量、 三条动线不打架、岗位怎么排、哪些还得采购。我们把这些做成了同一份数据契约。

02

我们把它接成了四条产线

每条产线的产出都能单独验证，也都能单独用。

地

① 真实场地搬进屏幕

锚点用平台自己的高德检索（GCJ-02），建筑点位同样；草坪与水体边界用 OSM leisure=grass / natural=water 真实多边形， WGS-84 先转 GCJ-02 再换算到局部 ENU。
花家山庄：主草坪 1449 m²、其北侧草坪带 1951 m²、滴翠湖 2574 m²。

3D

② 物料从参考图或一句话长出来

aholo 图生 3D（20 credits/件）与文生 3D（20 credits/件）两条通道都接进平台自己的 生成任务体系，产物落对象存储、自动渲染预览图、公开进公共物料库。 失败 0 扣分。

约

③ 摆放回到同一份契约

2D 平面与 3D 场景读同一份 SitePlanData：分区语义、动线类型、 人员岗位、模型引用全部有 schema 约束，越界与悬空引用在写入前就会被拒绝。 本次 188 件物料全部过校验。

单

④ 交付是一张能照着搭的清单

149 行物料 BOM（名称 / 规格 / 数量 / 许可 / 来源）、18 条库内缺口分档、 18 条尺寸偏差逐条列明，外加 PNG / CSV / GeoJSON / PDF 导出。

04

关键资产迭代：一张签到台，四次改法

这是本轮最典型的一次迭代。结论先说：换形态，不换种子—— 图生通道不把提示词发给模型，换参考图才是唯一有效变量；换到第三张仍然失败之后， 我们换通道（文生 3D）一次成功。

06

我们不做什么，以及哪里还没做完

这一节和前面一样重要。报告里出现的每一个数字，都能在仓库或生产库里查到出处。

不编场地事实官方平面图、两片草坪的准确边界、禁喷花 / 明火 / 雨天条款、非合作婚庆入场费——查不到就写「未查到」，不猜。
不假装尺寸是准的AI 生成的 3D 没有绝对尺寸。18 条偏差逐条列出，含「婚礼圆桌提示词 1.8 m、实测 1.20 m」这类会直接影响席位数的事实。
不自动重派付费请求生成失败不自动重试。aholo 失败至今是黑盒（status:4、零原因字段），好在失败 0 扣分，试探成本只有时间。
不动契约本轮没有改数据库迁移、Edge Function 契约、根依赖或 CI。新增的只是数据与文档。
真实 DEM 地形本轮不做第二档工作。起稿用的是平台自己的底图，接真实地形需要额外的位移网格接线。
不做室内设计仙子厅 26×18 m、层高 7.5 m、约 30 桌，只作为雨天退路标注在图上。

幕景 Scendance · 项目整体逻辑图

口径：最新 main · 2026-11-19范围：产品全貌 + 系统组成 + 室内线退役演进

把真实户外场地变成能搭建的 3D 空间，再把方案摆进去。生成模型给的是「看起来对」，幕景补的是量得准、摆得下、交得出——真实尺寸、真实地面、执行团队能直接照着搭。

业务主线：七环节一条方案从想法到可交付

前四步把「真实场地」搞到手，第五步在画布上编排，第六步补定制物料，第七步交付出去。每一步都标了谁在做、产出什么、落到哪个系统。

Agent 每一步都是 提案 → 预览 → 人确认 → 才写画布；确认、驳回、作废都进复核台账。方案不是 Agent 直接改出来的，人在每一步都有否决权。

两个拆出去的独立仓

scendance-capture（私有）
  • 现场采集器：手机端导引拍摄，产出采集回执 JSON
  • 采集阈值真源仍留在本仓 frontend/lib/capture-guide/，双端共用
  • 本仓自 2026-11-05 起不再保留 miniprogram/
scendance-scene-library
  • 10 套场景模板库，2026-11-19 独立成仓
  • 预设场地与模板条目从主仓抽出单独维护
硬边界：照片 / 视频不是点一下就出可编辑几何——采集不达标就重建不出来；重建出的 3DGS 只提供观感，不提供精确几何，量尺与碰撞由矢量壳和 GLB 承担。

唯一正源：地图方案契约 SitePlanData

户外方案的所有物料、墙体、出入口、分区、动线、人员、测量、标注、会话、历史、导出都消费这一份 plan。米制 ENU 坐标（x 东 / y 北），1 世界单位 = 1 米，2D 平面与 3D 壳体同源。

人物 / 人群链路

参考形象 → 四视图 → 静态人形 → 绑骨 → 动作重定向。动作预设：Idle_Loop / Walk_Loop / Idle_Talking_Loop / Sitting_Idle_Loop；NPC 动作类型 idle / talk / walk / sit / wave / emote。列队、分区漫游、落座行为已有入口；绑骨角色接人群组配置尚未做。

产物已知硬伤：① 生成件无米制真值，只有包围盒 + 启发式归一化；② 朝向不可控，只能整体绕 Y 转；③ 单网格不可分件；④ 户外生成件当前 sessionOnly，刷新 / 换设备模型绑定悬空；⑤ 宾客画像 persona 数据模型未建。

Agent 分两层：模型只懂意图，工作台才动手

① 意图理解层（对话模型）

读用户这句话，只返回结构化 JSON：action + facts + references + operation + choice。不执行任何写操作，不直接改画布。

② 工作台执行层（前端 bridge）

把 JSON 翻译成对 plan 的读 / 算 / 预览动作；候选只算不写，人点确认后才 applyPlan 落进画布。

红线与约束（写进系统协议）

  • 事实 evidence 逐字来自本句；未说不填，数量不猜；count=0 表示整区清空
  • 地点候选只引用本次 search 实际返回，不凭记忆写酒店 / 场地名
  • 商场轮廓 ≠ 活动授权；道路交点 ≠ 真实门；不编地图像素与测量值
  • 指代必须绑真实 ID / revision；多义先 ask
  • 普通肯定只确认当前待确认提案，不触发收费生成任务
  • 生成类动作受登录、能力配置、只读项目、3 槽位并发门禁
后端对话：conversation-api 提供 /brief/extract、/assistant/chat、/assistant/chat/stream 三个端点；未启用时降级 503。模型槽位 MiniMax / DeepSeek / Tokendance 网关，置顶槽位不跨槽重试。会话按项目 id 绑定，过渡期仍保留旧布局的影子订阅。

还能提升什么（按优先级）

P0 · 闭环补齐
  • 生成结果回写对话：job 终态（ready / failed）回写对话线程，就绪后出「放入方案」候选卡；失败带可读原因与是否重试。现状发起生成后对话不轮询，结果要自己去物料库取。
  • 巡检自检接成动作：把已有可达性 walk-audit、验收 acceptance-selfcheck、重叠 / 越界 / 人数-座位 / 通道检查封装成一个 plan.check 类动作；现状这些纯函数只在 HUD / 验收板消费，Agent 调不到。
  • 提案确认卡链补全：人员、测量、标注、图层、设施增删改的对话内提案 + 预览 + 确认 / 驳回卡，对齐分区 / 动线已有范式；墙体工具随 M2 落地后接入。
P1 · 理解与规划质量
  • 尺寸标定入口：给生成件 / 物料补人工米数（宽深高），排布、间距、座位测算才不靠包围盒猜；否则「摆得下」的建议不可信。
  • 宾客 persona 对象：把身份（家长 / 嘉宾 / 工作人员…）、人数、动线偏好建成 plan 可承载的数据，才能分区排人、安排落座与动线，而不是 role + count 粗排。
  • 场地证据分级喂稳：partial / unavailable 时不先硬排；hard-block / soft-avoid / info 分级更稳地进上下文，提案标注「依据不足」。
  • 多轮改口回灌：把已确认 brief 结构化回灌模型，减少「再加 2 个」被当总量、旧物件名残留这类差错。
P2 · 候选与费控
  • 候选排序带依据：选址、物料、模型候选按人数 / 面积 / 风格 / 预算匹配度排序并说理由；风格包与排布变体统一成「多方案对比」卡。
  • 收费动作前置提示：生成 / 参考图类动作在提案前写明扣几次、失败是否返还；确认卡讲清，避免普通肯定误触发付费。
P3 · 工程与可靠性
  • 会话 / 台账上云：卡片记录与复核台账目前本地 localStorage（30 条），跨设备不同步；随 M3 绑 project id 后上云，延续已确认决策。
  • 模型槽位降级：置顶槽位失败不跨槽重试，可为理解类请求补有限降级路径与可读提示。
  • 台账回溯：Agent 可读确认 / 驳回历史，自我规避已否决方案，并能解释「这版改了什么、依据哪句原话」。
不在 Agent 层单独解的：生成件朝向可控、单网格分件、DEM 贴地联动——这些卡在模型能力与地形链路，要从产物 / 地形侧补。

终局目标：不再区分室内 / 室外，只剩一套地图规划

  • 生产链路不再挂载室内 Viewport / three 室内场景，DOM 里只剩唯一地图画布（2D ↔ 3D 直切）
  • 唯一正源是 SitePlanData；物料、墙体、出入口、分区、动线、人员、测量、标注、会话、历史、导出都消费这份 plan
  • 会话绑定项目 id，不再绑室内 layout.id；undo/redo 基于 plan 快照；导出从 plan 出图
  • 产品概念上无「室内 / 室外」二分；场地类型只作为 Agent 提案的业务输入字段保留
迁移方法：绞杀者模式——新地图旁路逐块接管旧系统；防腐层隔离旧概念漏进新侧；垂直切片按功能域走「建新 → 验一致 → 切流 → 拆旧」；过渡期 plan ↔ layout 双写影子镜像；新侧稳定后旧模型退为只读投影再删除。拆旧必须等对应建新在地图侧接住，不允许先拆旧再补能力。

# 需求文档：Agent 按需求排道具 + 材质语言入口

| 项 | 内容 |
|---|---|
| 文档版本 | v0.2（2026-11-17，已落地 v0，含实测证据） |
| 读者 | 丽丽（产品 / 研发对接） |
| 关联模块 | 户外规划 · 物料库 · Agent 对话 · 3D 人物动作 |
| 前置结论 | 「能坐」这类规则搜索已撤，不作为产品路径；挥手暂无美术级素材，保留程序化兜底，与本需求解耦 |

## 一、背景与问题

物料库已有 976 条能力标签（当前可见 514 条：可坐 22、可坐组合 5、可交谈 40、可挥手 6、纯装饰 436），3D 侧也已能按标签让人物落座、交谈、漫游。但用户仍要自己在面板里搜名字、拖位置、逐个点材质——能力表只服务了「展示」，没有服务「布置」。

规则检索（输入「能坐」筛出椅子）已被验证是伪需求：它解决的是「找」，用户要的是「排」。真正缺的是一条 Agent 链路——把一句需求变成可执行的布置方案，并支持用自然语言改材质。

## 二、目标与非目标

| 类型 | 内容 |
|---|---|
| 目标 1 | 一句话需求 → 可执行方案：道具、数量、位置、朝向、材质、人物动作，一次生成、可预览、可撤销 |
| 目标 2 | 材质语言入口：「把这几把椅子改成金属」→ 命中对象 → 预览 → 应用，支持批量与撤销 |
| 目标 3 | 每条结果都能解释「为什么选它」，不让用户面对黑箱 |
| 非目标 | 不做自由 3D 生成；不做语义搜索框；不改现有 2D/3D 编辑器的手动操作 |
| 非目标 | 不追求美术级挥手素材（暂无 CC0 来源，已有程序化兜底） |

## 三、用户场景

- 婚礼布置：30 人观礼区，需要 30 把可坐的椅子、2 个可交谈的接待台、一条不挡视线的通道。
- 市集摊位：8 个摊位沿通道两侧排开，统一深木材质，摊位间留 2 m 疏散间距。
- 材质调整：把舞台区所有物件改成黑金属，但保留原有木纹纹理（只调 PBR，不换模型）。
- 改完反悔：一步撤销回到生成前，或「换一批」重新给候选。

## 四、功能需求

### 4.1 需求解析（P0）

从一句话或多轮对话中抽取结构化约束：数量、物件类型、能力（可坐 / 可交谈 / 可操作 / 可挥手）、区域、材质、尺寸或预算上限、避让要求。解析结果必须先回显给用户确认，再进入排布。

### 4.2 候选检索（P0）

用能力表 + 物料目录（名称、子类、真实宽深高）召回候选，不靠关键词猜。每类给 3–5 个候选并附理由（能力命中、尺寸适配、同风格）。候选必须来自真实物料，不允许凭空造 slug。

### 4.3 排布（P0）

在场地边界内落位：避让已有设施、流线、出入口；成组规则（桌椅配对、摊位成排）；朝向按功能（座椅面向舞台、摊位面向通道）；容量核算（座位数 ≥ 需求人数）。越界或冲突时给替代位置，不静默失败。

### 4.4 落库与回滚（P0）

所有变更以一次 plan patch 提交，复用现有 facility 契约；提交前过 schema 校验，失败整体回滚；成功后可一步撤销。禁止逐条写库造成半成品方案。

### 4.5 材质语言入口（P0）

支持两类说法：「把这几个改成金属」（按当前选中集）和「把这一片的木色都调深」（按区域 + 当前材质筛选）。命中对象先高亮预览，确认后批量写入 `materialPreset`；一次撤销可整体回退。

材质只改 PBR 参数（基色、粗糙度、金属度、透明度），保留原贴图，因此木纹、拉丝纹理仍在；「纯色金属」这类去贴图需求列为 P1，需单独处理 UV 与细节。

### 4.6 动作绑定（P1）

座位类自动绑定落座、接待台绑定交谈、舞台绑定挥手。缺片段时明确提示「当前素材没有挥手」，不假装已接通；人物动作仍由现有 3D 动作运行时执行。

## 五、交互流程

1. 用户输入：「30 人观礼，要能坐，前面留通道」。
2. Agent 回显解析结果：30 把可坐座椅、通道净宽 2 m、区域为场地南侧——用户确认或修改。
3. Agent 给候选与布局预览（2D 高亮 + 3D 可切），标注每类选择理由与冲突提示。
4. 用户说「椅子换木色」「通道再宽一点」，Agent 只改对应部分，不重排全案。
5. 确认后一次提交；失败整体回滚；用户可一步撤销。

## 六、数据契约（建议）

| 对象 | 字段 | 说明 |
|---|---|---|
| 请求 | `intent` / `constraints` / `selection` | constraints 含 count、capability、zone、material、maxWidth；selection 为当前选中设施 id |
| 响应 | `ops[]` / `rationale[]` / `warnings[]` | ops 只允许 addFacility、updateFacility、setPersonAction 三种 |
| 设施 | templateId、modelOverride、materialPreset、position、rotationDeg、size、notes | 复用现有 `planFacilitySchema`，materialPreset 已落地（7 档预设） |
| 校验 | schema + 边界 + 重叠 + 流线避让 | 任一失败 → 整批拒绝并说明原因 |

## 七、验收标准

| 指标 | 口径 | 目标 |
|---|---|---|
| 能力命中 | 20 条真实需求，Top-3 候选能力正确率 | ≥ 80% |
| 方案合法 | 生成方案过 schema、边界内、无非法重叠 | 100% |
| 可回滚 | 提交后一步撤销回到原方案 | 100% |
| 材质批量 | 50 件批量改材质并出预览 | ≤ 2 s |
| 诚实性 | 缺片段/缺模型时必须有提示，不静默假装 | 100% |

## 九、风险与开放问题

- 能力表覆盖：976 条中 462 条未在可见库（隐藏/无模型），候选可能落到不可见项，需要过滤规则。
- 大模型不稳定：所有输出必须过确定性校验（schema、边界、重叠），不信任自然语言结果。
- 材质语义：用户说「金属」可能指颜色也可能指去贴图，首版按 PBR 调参并在回执里写清楚。
- 挥手素材缺失：CC0 动画库 46 条无 Wave，Mixamo 有但非 CC0；当前程序化兜底，素材到位后走同一条重定向链路替换。
- 多人协同：批量改动会覆盖他人编辑，需要沿用现有写租约与冲突提示。

### 关键修复

人群富化原先在 `await loadPeopleModel(THREE)` 之后还有一道代际守卫，React 一次重渲染就把整段富化（含挥手/交谈注册）跳过了，人物停在轻量占位模型上，于是 `wave/talk` 全为 false。改为**先同步注册**（带挥手、有缓存就带交谈），`people.glb` 晚到再升级交谈，守卫只看 `disposed / run`，不再看代际。

### 已知缺口

1. **挥手没有场景内截图**：观礼区与漫游区的 NPC 都已被落座/漫游运行时接管，`setNearestPersonAction` 不再接受新动作；这是编排策略限制，不是片段缺失。要出图需允许「空闲 NPC」不被接管，或提供动作覆盖通道。
2. 候选排序缺语义项，先用尺寸接近度兜底。
3. 材质只支持「选中 / 按类型 / 全案」，区域作用域未接。
4. 一句话入口挂在属性卡内（需先选中一件），独立命令入口留到下一步。

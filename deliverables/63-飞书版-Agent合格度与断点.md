# 什么样的 AI Agent 才算合格？

> 一句话：**不是模型多聪明，而是它说的话能追到证据、做的事能撤回、失败的时候有名字。**

这篇文章想回答两个问题：一个合格的 Agent 从架构、代码、逻辑上到底该长什么样；以及我们自己的产品，站在哪一边。

---

## 三分钟版

- Agent 不是"更会聊天的模型"，是**一条五段链路**：看 → 想 → 做 → 查 → 记账。五段各有各的红线，不能串。
- 最值钱的一条设计是**主动放弃模型的自由**：坐标、尺寸、价格、结论，一律不许模型给，全交给确定的代码。
- 我们在这件事上做得比大多数团队狠：**模型只有"指"的权力，没有"造"的权力**——每个事实都必须逐字引用原文，否则契约层直接拒收。
- 我们的问题不在"会不会出错"，在**两处结构性欠账**：大脑长在界面里（改不动、测不了），以及模型只负责分类、不参与设计（有天花板）。
- 如果只改三件事：**把大脑搬出来 → 把设计权还一点给模型 → 让机器来打分**。

## 一、Agent 的骨架：它像一家装修公司

把 Agent 想成一家装修公司，一下就清楚了。

| 角色 | 在 Agent 里叫什么 | 它绝对不能干的事 |
| --- | --- | --- |
| 现场勘测 | 观测 | 把"我猜"说成"我量过" |
| 设计师 | 决策 | 直接报出承重墙的尺寸 |
| 施工队 | 动作 | 不问业主就砸墙 |
| 监理 | 校验 | 只说"合格"，不说"合格在哪" |
| 验收单 | 回执 | 写"希望完成的事"，而不是"真发生的事" |

一家公司出问题，十有八九是**角色串了**：设计师顺手把墙砸了，或者施工队自己开验收单。

Agent 也一样。所以第一件要想清楚的事不是"用哪个模型"，而是：

> **谁能产生"量"？谁能产生"编号"？谁能宣布"通过"？谁能决定"落盘"？**

这四个问题的答案，应该写进代码里的契约，而不是写进提示词里。

因为提示词是"请求"，契约是"拒收"。

## 二、代码上怎么做：让编造变成类型错误

这部分稍微技术一点，但只讲三条最要紧的。

### 1. 给模型一个"只能指、不能造"的格子

我们所有模型输出都被一个严格的 schema 卡着。它的特点是：

- **不许多一个字**——多一个字段就整条拒收，模型没机会夹带私货；
- **每个事实后面必须挂证据**——它可以说"用户说了 80 人"，但必须逐字引用原话，否则解析失败；
- **方位的字段，用户没说就空着**，代码注释里写着"不猜"。

这比在提示词里写十遍"请不要编造"管用得多。

> 编造从一个"道德问题"，变成了一个"类型问题"。

### 2. 工具说明里必须写"它不保证什么"

大多数工具描述只写"我能做什么"。我们的写法是反过来补一句：

> `valid` 只表示候选构建和部分几何检查的结果，**不代表通行、安全或规范通过**。

这一句话，决定了模型会不会把"一次检查"吹成"一次安全认证"。

### 3. 风险要算出来，不能问出来

模型提交方案时说"这是低风险改动"，我们**不信**。

我们拿新旧两版数据逐个实体对比：删了东西吗？改了建筑和楼层吗？碰了锁定件吗？——全部自己算一遍。

于是"风险"变成了一个可以单测、可以回放、可以比较的纯函数。

> 一句可以直接抄走的话：**Risk is derived from the real candidate, not a model-supplied claim.**

---

## 三、逻辑上怎么做：敢不敢说"我不知道"

技术之外，真正拉开差距的是**价值观被写成验收标准**。

### 我们的失败顺序是排过序的

```
有依据的方案  >  明确拒绝 + 说清缺什么  >  编一个看起来像样的方案
```

最后一项，**0 容忍**。

这不是口号。它意味着：宁可少答一道题，也不能让客户拿着一个假布局去搭台子。

### 评测里必须有一条"什么都不做"的样本

这是我最想推荐给同行的做法。

如果评测只考"该报的问题报没报"，模型很快就学会一招：**少说话**。什么都不报，就没有漏报，分数满分。

所以我们加了一条对照样本：场地明明没毛病，你要是报了问题，判错。

> 没有对照样本的评测，会奖励沉默。

### 算不了的，要大声说出来

我们 80 条空间判据里，只有 11 条能真正算。剩下 69 条缺数据（栅格、水深、高程、树冠……）。

我们的做法是：**分类列出做不到的原因，并且明确不计分**。

因为把算不了的算进去，等于鼓励模型"多报几条蒙对"。

## 四、我们做对了什么

五条，每条都经得起翻代码。

**① 模型没有几何权。**
这不是一句设计原则，是契约里真的没有一个坐标字段。绝大多数空间类 Agent 死在这里——让模型吐坐标，然后布局进墙、进湖、重叠，再用一堆提示词去补。我们从第一版就把这条路封死了。

**② 每个事实都能回溯到原话。**
用户说"80 人"，系统里存的不是"80"，是"80 + 这句话的原文"。任何结论都能被追问"你凭什么"。

**③ 只出草稿，确认才落盘，一步能撤回。**
再叠加"锁定件不许被 Agent 动"——用户锁住的东西，模型碰一下就直接报错，不静默跳过。

**④ 失败有名字。**
不是"成功/失败"两种状态，而是五种结局、八种解析状态、十二类错误码。**能说清自己怎么失败的，才有资格谈怎么变好。**

**⑤ 运行层面的自觉。**
重复请求只结一次账、超时会收敛、跑挂了会退钱、写数据不挡读数据。这些听着不性感，但它们是"能演示"和"能收钱"的分界线。

顺手说个数字：我们有 **92 个和 Agent 相关的测试文件、约 1.38 MB 测试代码**。这不是刷出来的，是"每个改动都要先有一个会红的测试"这条纪律撑出来的。

## 五、我们断在哪

讲痛感，不讲客套。

### 断点一：大脑长在界面里

Agent 的决策流程，写在一个五千多行的界面组件和一个近四千行的 hook 里。

后果很直接：

- **跑不了离线评测**。我们有一套 27 条的评测题，但十条方案题至今"只有题目和判分，没有分数"——不是不想跑，是架构上跑不动。
- **换端要重写一遍**。小程序、服务端批处理，都得把逻辑再抄一次。
- **改一条路由等于动全身**。所以才会长出下面那个补丁。

这是我们所有问题的**放大器**。

### 断点二：模型只负责分类，不参与设计

现在模型干的事是：听懂你要什么，填好参数。真正"怎么排"全靠写死的规则。

好处是不出错。代价是**答不出"如果"**。

客户问"为什么舞台朝东"，规则引擎能答；客户问"如果改成朝西会怎样"，它答不出来。

我们原计划里有一段叫"设计意图通道"——让模型能说"我想让舞台朝水"，然后由安全规则决定让不让。**这一段到现在还没开工。**

### 断点三：有些话，其实不是模型听懂的

因为模型在某些句式上会摇摆，我们在它前面加了一层代码先判断"用户是不是在确认"。

结果是：用户看到的每句话，**不一定是模型理解的**。

一旦答错，你没法归因——是模型错了，还是补丁错了？更麻烦的是，走过这条路的句式，换个更强的模型也不会变好。

### 断点四：92 个测试，只有一个小程序在自动跑

我们仓库的自动检查里，**只有一个跑小程序的工作流**。主站没有类型检查、没有单测、没有 Agent 评测。

所以测试的价值全靠"人记得跑"。根目录堆着好几个 2 MB、3 MB 的自测日志——**结果被人搬来搬去，而不是被机器裁决**。

### 断点五：听懂了，但做错了

两种 bug 里，这种最伤信任：

- 说"缩小 10%"，实际缩到了 20%；
- 说"加两盏灯"，只加了一盏。

用户对"我不懂"是宽容的，对"你听懂了却做错"是不宽容的。

根因是：把话变成动作的那一层，是手写规则，**没有一张"这句话应该变成什么动作"的对照表**，所以错了也没人拦住。

---

## 六、只改三件事

| 顺序 | 做什么 | 为什么排这里 |
| --- | --- | --- |
| 1 | 把大脑从界面里搬出来，做成能独立跑的一层 | 它是其他所有问题的前置 |
| 2 | 把"设计意图"还给模型，和安全规则做一次对照实验 | 决定产品天花板 |
| 3 | 让机器来打分：类型检查 + 27 条评测 + 30 条路由题进自动检查，分数掉了就红 | 守住前两步的成果 |

顺手可以先做、不占架构的：**给"文本→动作"建一张对照表**，把上面那两种低级错误一次锁死。

有一条纪律不能动：**模型永远不产生坐标。** 把设计权还一点给它，还的是"为什么这么排"，不是"排在哪个像素"。

---

## 七、最后一句

我们最成功的地方，是**主动放弃了模型的大部分自由**。

我们最危险的地方，是**把这份克制装进了一个九千行的界面壳里**。

前者决定我们今天敢给客户演示；后者决定我们明年还改不改得动。

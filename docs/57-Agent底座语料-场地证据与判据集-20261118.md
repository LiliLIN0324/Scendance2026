### 2.1 判据集为什么这样设计

- **每个数值都能追到文档的同一行**。`sourceLevel` 直接沿用 A/B/C：A 级才允许说「规范要求」，C 级只能称「建议值」。
- **格数单独存**。1 格 = 1 m，`rounding` 区分向上/向下取整，避免 Arith 漂移；测试会复算 `cells === ceil(m)` 或 `floor(m)`。
- **`promptCore` 只留 21 条**，就是规范表 §9 选出的 12 组「一票否决」判据。全量 80 条塞提示词会挤爆 6000 字符预算，还会让模型把 C 级经验说成规范。
- **`codeCoverage` 明写「80 条均未接入」**。防的是下一个人看到文件就以为已经在跑。

### 2.2 模板只承认两类已实现

`status` 只有 `implemented` / `spec-only` 两档。现在 `implemented` 只有 MKT（市集）与 LEC（讲座/会议/论坛/发布会），其余五类（演出、露营、展览、亲子、适老）全部 `spec-only`，`codeRef` 为 `null`。这是刻意的：现有代码的 `supportedOutdoorEvent()` 正则会直接拒绝它们，注册表不能替代码许诺。

### 2.3 物料表：尺寸有源，六列待核

尺寸全部来自代码：内置 8 个模板（`site-plan-facilities.ts:49-56`）与 `oneplan-library-size.ts` 的 `SIZE_RULES`。以下六列**在任何代码与规范里都找不到可信值**，一律写「待核」，不许估：

`高_m`、`部署人数`、`重量_kg`、`风载`、`地面要求`、`电力_kw`、`运输`

Agent 遇到「待核」必须反问或标注不确定，这正是这份表最大的用处——**它把「不知道」变成了显式字段**。

### 2.4 场地证据 schema

- 枚举与代码完全对齐：`FeatureKind` 11 类、`Certainty` 4 档、`source` 4 档、`coverage.status` 6 档；测试会读 `types.ts` 原文核对，代码改了枚举而这里没改会红。
- 新增三组代码目前没有的字段，且明确标为目标格式：
  - `layoutWeight: hard | soft | info` —— 决定 Agent 能不能压（水、建筑、消防通道 = hard；绿地、树池 = soft）。
  - `constraints[]` —— 从证据推出的禁建/净空/近岸缓冲，必须带 `evidenceIds` 与 `assertionIds`。
  - `gaps[]` —— `noWaterDepth` / `noSlope` / `noShade` 等 9 类缺口，直接绑到被挡住的判据 id。有缺口时 Agent 只能明说缺什么，不许用默认值假装齐全。

## 三、怎么用（四种消费方式）

1. **提示词**：只取 `promptCore` 的 21 条，按「度量 → 阈值 → 动作」三段短句写，每条带 `rule_id`，让回执能引用编号。
2. **校验器**：`validate(scene, ruleId)` 返回 `{ruleId, severity, actual, expected, bbox}`；`hard` 拒绝落笔，`warn` 进回执，`ideal` 只进评分（沿用规范表 §11 的接口约定）。
3. **评估集**：把 12 条冲突做成成对用例——同一块地给两个互斥目标，看 Agent 是否显式取舍，而不是两边都说满足。
4. **few-shot / 训练数据**：单位是 `(场地证据摘要, 用户话术, 期望 action+intent)`，不给坐标。负样本（拒绝、降级、报缺）与正样本同等重要。

## 八、执行器：11 条能算，69 条承认算不了

代码在 `frontend/lib/agent-corpus/`，输入是 `facilities / zones / nodes / obstacles / boundary / people / stageHeightM`（与 `SitePlanData` 结构兼容，不 import 契约）。

| 已实现 | 算法 | 为什么能算 |
|---|---|---|
| GEN-04 出口数量 | 数 `nodes` 里 `exit`/`both` | 节点自带 kind |
| GEN-07 建筑退距 | 设施外接框到建筑足迹的正交净距 | 建筑来自证据多边形 |
| MKT-02 摊位间距 | 两两正交净距；左右看 1.5 m、上下看 2 m | 摊位尺寸与坐标都有 |
| MKT-06 明火分区 | 明火/餐饮摊到其他摊位净距 | `templateId` 可识别 |
| MKT-07 灭火器 | 数量 ≥ 2×ceil(摊数/10) | 可数 |
| MKT-10 摊位占地率 | 摊位投影和 ÷ 边界面积 | 鞋带公式 |
| MKT-11 摊位退距 | 同 GEN-07，筛摊位 | 同上 |
| STG-01 观众密度 | 观众区面积 ÷ 人数 | 区多边形 + 人数 |
| STG-02 首排退距 | 舞台到观众区净距 ≥5+4×(H−1.5) | 台高走可选入参 |
| CMP-02 营位间距 | 帐篷两两净距 | 尺寸与坐标 |
| CMP-03 防火间距 | 帐篷 4 m；明火距帐篷 10 m | 同上 |

**其余 69 条不是「忘了做」**，是缺前置数据，按需要的信息分 12 类原因码：`needs-raster`（净宽/净高要栅格 BFS）、`needs-water-depth`、`needs-elevation`、`needs-canopy`、`needs-runtime-sensor`、`needs-season-simulation`、`needs-surface-data`、`needs-fixture-typing`、`needs-aisle-semantics`、`needs-route-topology`、`needs-orientation-semantics`、`needs-metadata`。

判据状态只有四种，**没有「默认通过」**：`pass` / `violation` / `skipped`（规则可算但这次缺料，带 `reason`）/ `unsupported`（需要当前模型没有的数据）。`skipped` 与 `unsupported` 都不计入通过。

提示词侧：`buildPromptDigest()` 只出 21 条核心判据，C 级一律带「（建议值，非规范）」，超预算时整条丢弃并把 id 放进 `omitted`，不截半句。实测 21 条占 1.4k 字符以内。

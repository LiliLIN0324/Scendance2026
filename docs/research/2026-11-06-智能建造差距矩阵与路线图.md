# 智能建造差距矩阵与路线图（2026-11-06）

> 姊妹篇：《2026-11-06-智能建造对标升级.md》。上文给机制拆解，本文给一张可对照的四层差距矩阵，并把 P0/P1/P2/P3 重新排成三期可验收的路线图。只产规格，不写实现代码。

---

## 0. 摘要

我们当前的摆摊打分管线（`plan-annotation → plan-approve → plan-scoring → flow-constraints → human-factors`）已经能跑出三版方案、按 `capacitySeats − 2·skipped − 3·outOfBounds + flowPenalty + overlapPenalty − ergonomicsPenalty` 排序，并接了人体工学三项硬阈值与走廊连通 BFS；但对照 FlairGPT、RoomCraft、OpenAI Cookbook、Co-Layout、OpenEventCAD、OptiScene 六个对标系统，仍有三条结构性缺口：**LLM 大脑层**目前只抽 7 个槽、零推理，没有 audienceTags 也没有 proactiveReply；**数据模型层** `PlanAnnotation` 仍只有 zone/route/measure 三种 geometry，缺 door/window 节点，`FurnitureSpec` 是 `as const` 硬编码而非可扩展 inventory；**布置求解层**只有一次性纯函数 `planZones`，没有两次 LLM 分工、也没有 LLM→cost function 的映射。本批（P1）先把 audienceTags + proactiveReply、回「好」自动落区、door UI 接线、家具三层 SPEC 这四件最贴摆摊场景的事做完；P2 把第一次 grounding LLM、具名 inventory 目录、Privacy Sorting 入口层级软约束补上；P3 再上第二次 furnish LLM 输出坐标 JSON + deterministic repair 链，以及 FlairGPT 式 LLM→cost 映射。所有三期均不引新依赖、不引新色系、不动 3D 渲染、不动 supabase 既有表。

## 2. 三期路线图

### P1 本期（4.0~4.1 已落地 + 本批进行中）

本批四件事：让 LLM 多给一句人话建议、回「好」自动落区、door 节点 UI 渲染、家具三层 SPEC。不引新依赖、不改 supabase 表。

#### P1-1 LLM audienceTags + proactiveReply
- **做什么**：`brief-extract-contract.ts` 的 BRIEF_EXTRACT_PROMPT 在 7 槽基础上加两个字段：`audienceTags`（`z.array(z.enum(['elderly','family','business','student','vip']))`，空数组合法）与 `proactiveReply`（`string | null`，一句中文人话建议 + 提议帮圈区，禁 Markdown）；识别规则：老年/长辈/银发/腿脚不便→elderly；亲子/小孩/儿童→family；商务/企业/客户/答谢晚宴→business；学生/课堂→student。`agent-resolver.ts` 的 toExtraction 透传新字段；`brief-agent.ts` 把 buildAudiencePrompt 正则版改成「优先用模型 proactiveReply，模型不可用/超时/给 null 才回退正则」，保持纯函数状态机与防复读不被破坏。
- **验收标准**：
  1. `briefSlotSchema` 单测覆盖：audienceTags 空数组合法、非法 enum 被拒；proactiveReply 为 null 合法、为非空字符串合法；
  2. brief-agent 单测：mock resolver 返回 proactiveReply 时优先展示该句，不再走正则；mock 返回 null 时回退到正则版句子；
  3. 既有 brief-agent 测试（含防复读、状态机转移）保持全绿；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`supabase/functions/_shared/brief-extract-contract.ts`、`frontend/lib/agent-resolver.ts`、`frontend/components/room-organizer/lib/brief-agent.ts`、对应 `.test.ts`。
- **分支**：`feat/llm-audience-reasoning`（子任务 A）。

#### P1-2 回「好」自动落区 UI 闭环
- **做什么**：在 `agent-panel.tsx` 主对话面板，当 brief-agent 本轮回复含「要不要我…圈出来」句式时，消息下方渲染品牌绿描边小卡，按钮文案「好，帮我圈」；点击后，若 `planAnnot` 没 draft 先 `startDraft()`，用 `defaultZoneRect(zoneType, {width: layout.width, height: layout.height})` 逐个追加 zone 标注（复用 `addAnnotationFromPoints` 或新增一个直接接收 rect 的 action，二选一），drawMode 保持 off，不强迫用户进绘制模式；落完后给一句 toast 或对话回执「已经在 2D 上圈好签到区和休息区，去画布看一眼？」。用户直接打字「好」「可以」「圈吧」也触发同一动作（在 agent-panel 发送处理里加肯定意图识别，复用现有命令解析风格）。
- **验收标准**：
  1. 纯函数抽 lib：肯定意图识别函数、批量 rect 构造函数均有单测；
  2. agent-panel.react.test.tsx 新增用例：消息含「圈出来」时按钮可见；点击按钮后 `addAnnotationFromPoints`/等价 action 被调用且 drawMode 未被切到绘制态；
  3. 打字「好」「可以」「圈吧」均触发同一动作；打字「不用」「先别」不触发；
  4. tsc=0、vitest 全绿；白名单失败文件除外的组件测试不新增红。
- **涉及文件**：`frontend/lib/suggestions.ts`（已有 generateZonePrompts / defaultZoneRect，可能补充批量构造）、新增 `frontend/lib/auto-zone-apply.ts`（肯定意图识别 + 批量 rect 纯函数）、`frontend/components/room-organizer/panels/agent-panel.tsx`、`frontend/components/room-organizer/hooks/use-plan-annotations.ts`（如新增接受 rect 的 action）、对应 `.test.ts` / `.react.test.tsx`。
- **分支**：`feat/auto-zone-apply`（子任务 B）。

#### P1-3 door UI 接线
- **做什么**：`plan-annotation.ts` 加 `kind: 'door' | 'window'` geometry（带 wall 与 position_along_wall），`plan-overlay.tsx` 与 `floor-plan-ruler.tsx` 能在 2D 上画出门弧示意；先只做渲染与编辑，门弧遮挡扣分（RoomCraft 90 cm 半径扇区）作为 P1 收口的可选加分项。
- **验收标准**：
  1. 能通过现有 annotation 流程新建/移动/删除 door 节点；
  2. 2D overlay 上 door 渲染为沿墙短线 + 90 cm 开门弧半透明扇区；
  3. door 节点在 plan-export / production-plan-persistence 中能序列化往返（不丢字段）；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`frontend/lib/plan-annotation.ts`、`frontend/lib/plan-export/plan-geometry.ts`、`frontend/components/room-organizer/canvas-2d/plan-overlay.tsx`、`frontend/components/room-organizer/panels/floor-plan-ruler.tsx`、`frontend/components/room-organizer/lib/production-plan-persistence.ts`、对应测试。
- **依赖**：无前置；可与 P1-1/P1-2 并行。

#### P1-4 家具 primary / secondary / tertiary 三层
- **做什么**：`furniture-catalog.ts` / `furniture-sets.ts` 的 SPEC 加 `tier: 'primary' | 'secondary' | 'tertiary'` 字段。圆桌=primary、餐椅=secondary、签到台=primary / 签到台后工作椅=secondary、墙面装饰/地毯/桌面小件=tertiary。本期仅打标、不改求解逻辑；为 P3 的 Voronoi/LLM→cost 留口。
- **验收标准**：
  1. 每件已硬编码家具都能给出 tier；
  2. 现有 plan-approve / plan-scoring 测试不因字段新增而红（字段为可选，旧调用路径不破坏）；
  3. 类型单测覆盖 tier 枚举。
- **涉及文件**：`frontend/lib/furniture-catalog.ts`、`frontend/components/room-organizer/lib/furniture-sets.ts`、对应测试。
- **依赖**：无前置；可与 P1-1/P1-2/P1-3 并行。

### P2 中期

P2 三件事：让 LLM 真的读一次图、家具目录可扩展、把「入口层级」做成软约束。依赖 P1 的字段落地。

#### P2-1 第一次 grounding：LLM 读图输出 required_spaces
- **做什么**：参照 OpenAI Cookbook，新增一次 LLM 调用——用户上传场地照片/底图后，模型输出 `semantic_zones[]`（每 zone 含 kind、推荐 rect、依据）、`assumptions[]`（如"南侧双开门视为主入口"）、`required_spaces` 覆盖表（签到区/圆桌区/休息区/打卡区是否都被覆盖）。**这次不出家具**。输出落到一个新的 grounding JSON，可审、可回放；不通过就不进 planZones。
- **验收标准**：
  1. 给定一张样例场地图 + 一份 brief，模型输出能给出 ≥1 份 semantic_zones 与 ≥1 条 assumptions；
  2. grounding JSON 与现有 `plan-annotation` 的 zone geometry 能双向翻译（grounding → 可一键转 annotation；annotation → 可回读为 grounding 快照）；
  3. 模型不给 assumption 时，前端显式展示"未识别主入口"而不是静默兜底；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`supabase/functions/_shared/` 新增 grounding-contract.ts、`frontend/lib/agent-resolver.ts`、`frontend/lib/plan-annotation.ts`、`frontend/components/room-organizer/panels/agent-panel.tsx`、对应测试。
- **依赖 P1**：依赖 P1-1 的 brief-extract-contract schema 风格（zod 契约）与 P1-3 的 door 节点（grounding 输出的主入口要落到 door 节点上）。

#### P2-2 具名 inventory 目录
- **做什么**：参照 OpenEventCAD，把 `furniture-catalog.ts` 从 `as const` 硬编码升级为可扩展目录：每件家具具名（如"6'×30\" Banquet Table"）、带 dim（长宽高）、tier、facing 偏好；支持 grouped seating 模板（theater / banquet / u-shape + spacing / aisle / facing）。用户能在前端"加一张自己的桌子"，目录持久化到本地（不动 supabase 既有表）。
- **验收标准**：
  1. 至少 3 种 grouped seating 模板（theater / banquet / u-shape）能一键铺出；
  2. 用户新增 1 件家具后，刷新页面仍在；
  3. 既有 `furniture-sets.test.ts` 用例不破；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`frontend/lib/furniture-catalog.ts`、`frontend/components/room-organizer/lib/furniture-sets.ts`、新增 `frontend/lib/furniture-grouped-templates.ts`、本地持久化（localStorage 或现有 production-plan-persistence 扩展）。
- **依赖 P1**：依赖 P1-4 的 tier 字段先落地。

#### P2-3 Privacy Sorting 入口层级软约束
- **做什么**：参照 Co-Layout 的 `D_k = (1/A_k) Σ x_{i,j}^k · d_{i,j}`，把"签到区必须在入口第一排、圆桌区在签到区之后、休息区最深"编码成软不等式；进入 `flow-constraints.ts` 或 `plan-scoring.ts` 作为软罚分，不参与 infeasible 判定。
- **验收标准**：
  1. 构造反例：休息区被放到入口第一排 → 给出 privacySortPenalty > 0；
  2. 正例：签到→圆桌→休息由浅入深 → privacySortPenalty = 0；
  3. penalty 出现在 ScoredPlan 的 violations 里（如果 P1 已上 envelope）或独立扣分字段里；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`frontend/lib/flow-constraints.ts` 或 `plan-scoring.ts`、对应测试。
- **依赖 P1**：依赖 P1-3 的 door/entrance 节点（没有入口 reference 就没法算 d_{i,j}）。

### P3 远期

P3 两件事：让 LLM 真的出坐标、让 LLM 能用自然语言声明跨 zone 关系。研究风险最高，先小规模 prototype 再决定是否全量。

#### P3-1 第二次 furnish：LLM 输出坐标 JSON + deterministic repair 链
- **做什么**：参照 OpenAI Cookbook，在 P2-1 的 grounding 之上，新增第二次 LLM 调用——模型直接输出结构化 `furniture_placements[]`（type / center / dim / 正交旋转 / zone_membership / rationale）+ `feasibilityJudgment` + `unsatisfiedConstraints[]`。模型输出后跑 deterministic repair 链：正交旋转搜索 → 局部平移（复用 `settlePlacement`）→ joint-repack（新增）；**机械错误不回烦 LLM**。
- **验收标准**：
  1. 给定一份 grounding JSON，模型能输出 ≥1 份 furniture_placements；
  2. repair 链跑完后，硬筛（OUT_OF_BOUNDS / WALL_INTERSECTION / BBOX_OVERLAP） violations 数 ≤ 不跑 repair 链的 50%；
  3. rationale 字段在前端人话里可见；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`supabase/functions/_shared/` 新增 furnish-contract.ts、`frontend/lib/agent-resolver.ts`、`frontend/lib/plan-approve.ts`（扩展 repair 链）、新增 `frontend/lib/plan-joint-repack.ts`、对应测试。
- **依赖 P2**：依赖 P2-1 的 grounding JSON 先落地、P2-2 的具名 inventory（furniture type 才能对齐到目录条目）。
- **研究风险**：
  - LLM 在 2D 小场地（≤ 300 m²）上坐标精度不稳定，可能需要多轮 repair；
  - joint-repack 是 Cookbook 给的范式但开源实现细节少，需要自己 prototype；
  - rationale 字段可能出现"幻觉依据"，需要前端显式标注"模型推断，非代码验证"。

#### P3-2 FlairGPT 式 LLM→cost function 映射
- **做什么**：参照 FlairGPT，把"签到台不能正对主舞台""休息区不能被通道穿过"这类跨 zone 关系交给用户用自然语言声明，LLM 把自然语言 map 到 cost function 库（`next_to_wall` / `away_from_fixed_object(door|window|socket, min_dist)` / `accessible(sides)` / `no_overlap` / `in_zone` / 我们自己加的 `not_facing(stage)` 等）；匹配不上即丢弃、参数不对返回 0、不报错。
- **验收标准**：
  1. 用户输入"签到台别对着舞台" → cost 库能 map 到 `not_facing(stage)`，惩罚项出现在最终 score 里；
  2. 用户输入一句库中没有的关系 → 模型返回"暂不支持"，不阻断出图；
  3. 至少 5 个 cost function 入库（含 2 个我们自己加的摆摊专用项）；
  4. tsc=0、vitest 全绿。
- **涉及文件**：`supabase/functions/_shared/` 新增 cost-mapping-contract.ts、`frontend/lib/plan-scoring.ts`（cost 加权）、`frontend/lib/flow-constraints.ts` 或新增 `frontend/lib/cost-library.ts`、对应测试。
- **依赖 P2**：依赖 P2-3 的入口层级软约束（cost 库需要至少一个软项作为基线）、P2-2 的 inventory（cost 能引用具体家具条目）。
- **研究风险**：
  - FlairGPT 的 cost 库是 SLSQP 软目标，我们没有 SLSQP solver，需要把 cost 库退化成罚分项——效果可能不如论文；
  - LLM 自然语言→cost 的映射召回率不确定，需要 prototype 时建小评测集；
  - 全软约束哲学与我们已有的硬/软二分冲突，需要明确只在用户自定义项上用全软，不推翻既有硬筛。

---

## 3. 不在路线图里的（明确排除项）

- **真 3D 高斯重建（Gaussian Splatting）**：我们 2D 摆摊策划是主战场，3D 渲染只作展示，不做逆向重建。
- **WorldGen 类生成式场景（用扩散模型直接生成整版布局）**：黑盒输出不可审、不可 replay，违反"模型管语义、代码管几何"的分工原则。
- **DPO / SFT 偏好对齐训练（OptiScene 路线）**：我们没有偏好对标注管线，也没有推理资源跑 policy；隐式目标暂时用 cost function 库表达即可。
- **整数规划 solver 联合优化（Co-Layout 全量）**：我们只做事后评估不做联合优化，BFS 已足够；上 LP 会引入新依赖，违反红线。
- **真 medial-axis pathway cost（FlairGPT 全量几何库）**：medial-axis 计算复杂，摆摊场地形状简单，BFS 走廊连通已覆盖 80% 场景。
- **AGPL/复杂许可证源码的直接搬运**：无论对标系统多先进，不抄源码，只参考机制。

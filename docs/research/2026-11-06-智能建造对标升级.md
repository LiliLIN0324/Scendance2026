# 智能建造对标升级研究（2026-11-06）

> 本文综合三份平行研究稿（约束图/LLM分工、走廊连通、打分维度），给出对 Scendance2026 现有 `plan-*` 模块的升级规格。只产规格，不含实现代码。

---

## 0. 摘要

我们当前的摆摊打分管线（`plan-annotation → plan-approve → plan-scoring → flow-constraints`）已经能跑出三版方案并按 `capacitySeats − 2·skipped − 3·outOfBounds + flowPenalty + overlapPenalty` 排序，但对照 FlairGPT、OpenAI Cookbook、Co-Layout、RoomCraft、archi、OpenEventCAD 六个对标系统，存在三层结构性缺口：**数据结构上缺房间固定物（门/窗）与跨 zone 关系**，**几何评估上把"走廊连通"和"入口可达"混为一谈且只测签到前一条通道**，**打分上把所有维度揉进一个裸整数、没有硬/软约束分离、也没有人体工学子分**。本批先落地两条主线——按 RoomCraft 补齐三项人体工学硬阈值（椅后 0.6 m、签到台前 1.5 m、双人交汇 1.22 m），按 Co-Layout 在 `flow-constraints` 加 `evaluateCorridorConnectivity` 同时输出连通性与每 zone 可达性；下一批再补 violation envelope 与子分拆解，远期再考虑两次 LLM 分工与具名 inventory 库。

## 1. 约束图与 LLM/求解器分工

### 1.1 节点与边：FlairGPT 的三层家具模型

FlairGPT 把室内设计拆成"语言→翻译→SLSQP 分层优化"三阶段。家具按重要性分三层：每 zone 一件 primary（锚点）、围绕 primary 的 secondary（功能补充件）、挂墙/挂顶/桌面/地毯的 tertiary。zone 不是预先画死的矩形，而是由 primary 中心 Voronoi 动态推导。约束以 cost function 库形式存在（`next_to_wall` / `away_from_fixed_object(door|window|socket, min_dist)` / `accessible(sides)` / `no_overlap` / `in_zone` …），LLM 用自然语言声明约束，再 map 到库里已有函数，匹配不上就丢弃，参数不对就安全返回 0。**所有约束在优化期都是可加权软项，不是硬筛**。

### 1.2 分工：OpenAI Cookbook 的"两次 LLM + 三层 eval"

Cookbook 的落地经验是**模型管语义、代码管几何**：

1. 第一次 LLM 只做 grounding——读 floorplan 图，输出房间语义、`required_spaces` 覆盖表、`assumptions`（如"南侧双开门视为主入口"），**不出家具**。
2. 第二次 LLM 在已接地的 zone 之上输出结构化 `furniture_placements[]`（type / center / dim / 正交旋转 / zone_membership / rationale），同时输出 `feasibilityJudgment` 与 `unsatisfiedConstraints[]`。
3. 三层 eval 分开打分、不合并：validity（deterministic 硬筛：墙碰撞/重叠/越界）、grounded_program（GPT 判语义是否忠于 brief）、reference_similarity（有 gold JSON 时对照）。
4. 机械错误走 deterministic repair 链（正交旋转搜索 → 局部平移 → joint-repack），**不再回去烦 LLM**。
5. 每条约束显式标 `enforcement: "hard" | "soft"`（主通道净宽 48 in = hard，cluster size 4/6 = soft）。

### 1.3 对我们仓的对照

我们仓当前的 `plan-annotation.ts` 只有 zone / route / measure 三种 geometry，没有 door / window / socket 节点；`plan-approve.ts` 把每 zoneType 的家具配方写死成 SPEC 表，没有 primary/secondary/tertiary 分层；`planZones` 是一次性纯函数网格，没有显式 grounding JSON 可审；`skipped[]` 只含"没摆下的 zone"，不含"摆下了但违反了哪条约束"；`flow-constraints.ts` 只盯入口→签到区一条通道、只报一个最小 `aisleWidthM`，zone↔zone 之间的可达关系（签到→圆桌、圆桌→打卡、打卡→休息）完全没建模。已对齐的部分是：`applyLayoutCommandWithRefusals` 已经是真硬筛（OUT_OF_BOUNDS / WALL_INTERSECTION / BBOX_OVERLAP），`settlePlacement` 已经对应 Cookbook 的 local repair。

## 2. 走廊连通性与可达性硬约束

### 2.1 Co-Layout 的两条独立约束

Co-Layout 用整数规划做室内布局，最值得抄的是它把"走廊连通"和"房间可达"拆成两条独立约束：

- **走廊连通（corridor connectivity）**：用 max-flow 流守恒——把入口当唯一源、所有可通行 cell 当汇，若某段走廊与入口断开，守恒方程直接无解。比 BFS 事后判 inf 更严格。
- **房间可达（accessibility）**：每个 enclosed zone 至少有一个邻接走廊的"入口接点"，且**入口接点 cell 自身不能被家具 footprint 压住**（`α_{i,j}^k ≤ x_{i,j}^k − Σ_l f_{i,j}^{k,l}`）。这一条防的正是"booth 把休息区入口堵死"的现场翻车。

两者不能互相替代：走廊整体连通不代表每个封闭房间都有可用的门；反过来每个房间有门也不代表门之间是通的。

### 2.2 我们不需要上 LP

我们只做事后评估、不做联合优化，所以 Co-Layout 的流守恒可以退化成 **0.3 m cell 的 4 邻接 BFS**：

- cell 取 0.3 m，恰好让 1.2 m 净宽整除成 4 cells；
- 所有非 zone cell 合并成单层 `walkable(i,j)` 布尔图，不再区分 p（走廊）与开放室；
- 从入口 cell（z 最小、x = 场地中点）BFS 得到 `reachable`；
- 对每个 enclosed zone 判 `Z_k ∩ reachable` 是否为空；
- 在每条"入口→zone k"最短路径上做左右各膨胀 2 cells 的检测，近似路径净宽。

Co-Layout 自己跑 12×10 粗网格 → 6×5 中网格 → 原分辨率 warm-start 的 coarse-to-fine 策略也证明连通性判断对 cell 粗细不敏感，我们不需要物理精度。

### 2.3 函数签名（B 稿给定，本批落地）

```ts
type Vec2 = { x: number; z: number };

interface ZonePlacement {
  zoneId: string;                                    // "sign-in" | "lounge" | "round-table" | "booth"
  bounds: { minX: number; maxX: number; minZ: number; maxZ: number };
  kind: 'enclosed' | 'open';                         // open = 本身可通行；enclosed = 需要入口接点
}

interface ObstacleRect {
  bounds: { minX: number; maxX: number; minZ: number; maxZ: number };
  ownerId: string;                                   // 家具或 zone id，用于报错归因
}

interface EntranceSpec {
  centerX: number;                                   // 入口在 z 最小边的横向中心（米）
  widthM: number;                                    // 入口开门净宽
}

interface CorridorConnectivityReport {
  connected: boolean;                                 // 整体连通
  unreachableWalkableAreaM2: number;                  // 不可达可通行面积，用于加权扣分
  perZone: Array<{
    zoneId: string;
    reachable: boolean;
    minPathWidthM: number | null;
    pathWidthViolationM: number;                      // max(0, 1.2 − minPathWidthM)
    blockedBy: string[];                              // 堵住入口接点的 obstacle id
  }>;
  pairReachability: Array<{                           // 预留：签到→圆桌、圆桌→打卡等
    fromZoneId: string; toZoneId: string; connected: boolean;
  }>;
}

export function evaluateCorridorConnectivity(opts: {
  zones: ZonePlacement[];
  obstacles: ObstacleRect[];
  entrance: EntranceSpec;
  fieldBounds: { minX: number; maxX: number; minZ: number; maxZ: number };
  cellSizeM?: number;                                // 默认 0.3
  requiredPathWidthM?: number;                        // 默认 1.2
}): CorridorConnectivityReport;
```

新报告拆成两个独立扣分项喂给 `plan-scoring.ts`：`connectivityPenalty = 不可达 enclosed zone 数 × 大权重`；`pathWidthPenalty = Σ_k max(0, requiredPathWidthM − minPathWidthM_k) × 小权重`。原"签到区前净宽"保留为 UI 展示项，但不再当唯一 flow 指标。`blockedBy` 直接喂给人话降级通道（如"签到区入口被 booth-3 堵住"）。

### 2.4 OptiScene 的隐式目标清单

OptiScene（NeurIPS 2025）本身没有显式加权目标，它走 LLM + SFT + 两阶段 DPO 偏好对齐。它的 DPO 硬负样本只有两类（out-of-boundary、object-overlap），恰好对应我们已有的 `outOfBounds` 与 zone 不重叠。它的隐式目标项（从 meta-prompt 与 GPT-4o 打分维度反推）还包括：贴边/靠墙奖励、功能分组（桌–椅成组）、面向关系、动线可达、视觉疏密均匀、离入口层级（私密区靠里）。这几项里"贴边奖励"和"入口层级"我们当前完全没建模。

## 3. 打分维度与人体工学

### 3.1 RoomCraft 的硬/软二分

RoomCraft（Python + FastAPI + 模拟退火）把每版布局跑成 0–100 分并给 Top 5。**硬约束违反即 infeasible、不进排名**：家具越界、家具两两 AABB 重叠、门 90° 开门弧（90 cm 半径扇区）内有家具、任意两件家具净间距 < 60 cm。**软约束计入分数**：人体工学、自然采光、功能组团、动线贯通。

通用人体工学阈值（artandarchitecture / refinedspace / interioratoz 等行业参考交叉验证）：

| 项 | 阈值 | 我们当前 |
|---|---|---|
| 餐桌高 | 73–76 cm（我们用 0.75 m ✓） | 硬编码常量，未当维度 |
| 圆桌 4 人直径 | ≈ 120 cm（我们 TABLE_DIAMETER = 1.2 ✓） | 已对齐 |
| 椅后舒适活动空间 | ≥ 91 cm；最低侧身过 ≈ 60 cm | **未测** |
| 单人通行净宽 | ≈ 61 cm | 未测 |
| 双人交汇 | 107–122 cm | 当前 normalPassable = 1.2 m，未独立成档 |
| 轮椅 / 主通道 | 1.5 m | 当前已分档 |

### 3.2 我们应补的人体工学项（按 ROI 排序）

1. **椅后活动空间 ≥ 0.6 m**：餐椅/工作椅背到最近障碍（另一桌、zone 边、背景墙）的净距；< 0.6 m 扣分，< 0.3 m 判 infeasible。
2. **签到台前排队深度 ≥ 1.5 m**：签到台朝向宾客那一侧，到 zone 边/第一件宾客家具的净距。当前只测 `aisleWidthM`（横向），没测台前纵深。
3. **主通道双人交汇 ≥ 1.22 m**：把"双人交汇"从现有 1.2 m 档独立出来，对齐人体工学参考的 107–122 cm 区间。
4. 桌高合规从硬编码常量升级为维度输出（"桌高 0.75 m 符合正餐高度"），为后续 audienceHint 切 1.05 m 高桌留口。
5. 门/出入口 90 cm 弧遮挡（依赖后续 plan-annotation 加 door 节点）。
6. 签到→圆桌区邻近度正分（中心距 ≤ 8 m 给正分，纠正"全是扣分"的偏差）。
7. 0–100 子分拆解（capacity / flow / ergonomics 各自归一）。

### 3.3 archi 的 violation envelope 范式

archi（MCP server）最值得抄的不是 TreemapSolver 本身，而是它的返回 envelope：**每次工具调用都返回 `{violation_counts, violations: [{code, message, severity}], placements}`**，violation 带 IRC 规范 code（R311 = egress、R304 = 最小房间尺寸、R303.1 = 自然通风……）。入参用 Pydantic Literal 枚举前置校验（拼错 `"kitcen"` 在 schema 层就被拒，不进 graph）。**它不 throw、不返回空、不整块跳过**——TreemapSolver 永远"重排而非拒绝"，让 Agent 自己迭代。

对照我们：`planZones` 一遇 zone 太小就整块 skipped + 中文 reason；`pickRecommendedPlan` 在 `plans.length === 0` 时直接 throw（React 层 catch 体验差）；未知 zoneType 走 `ann.zoneType ?? 'roundtable'` 静默兜底。这些都应换成带 code 的 violation 列表。建议 code 枚举：`E_OUT_OF_BOUNDS` / `E_ZONE_TOO_SMALL` / `E_FLOW_NARROW` / `E_EGRESS_BLOCKED` / `E_ZONE_OVERLAP` / `E_UNKNOWN_ZONE_TYPE` / `E_ERGONOMICS_CHAIR_CLEARANCE` / `E_ERGONOMICS_CHECKIN_QUEUE` / `E_PATH_WIDTH`。

### 3.4 OpenEventCAD 的数据模型厚度

OpenEventCAD 是浏览器端 2D 活动策划引擎，它的数据模型比我们"zone rect + 4 种 zoneType"厚一层：venue 对象带 `wall_attachments: {kind: 'door'|'opening', wall, position_along_wall_ft, width_ft}`；inventory 是具名目录（"6'×30\" Banquet Table"）；有 grouped seating 模板（theater / banquet / u-shape + spacing / aisle / facing）；有 drawn run（pipe&drape / fence / bistro light 沿 polyline）；有 layers（参考图独立层、可见、锁定）；有 saved layout group。我们 `PlanAnnotation` 只有 zone/route/measure 三种 geometry，`FurnitureSpec` 是 `as const` 硬编码常量。**"门弧遮挡""视线遮挡""管线摆放"这些打分能力都依赖先补 venue 上的 wall/door 字段和 inventory 可扩展目录——这是数据结构债，不是打分公式债**。

## 4. 对我们仓的升级规格

### 4.1 分歧记录（三份研究稿之间的张力）

在排优先级前先把三处张力摆出来：

1. **主通道净宽是 hard 还是 soft**：OpenAI Cookbook（§1.2）把主通道 48 in 当 hard；RoomCraft（§3.1）把 60 cm 当 infeasible 硬下限、1.2 m / 1.5 m 当软阈值。我们当前走"outOfBounds 硬、flow 罚分"的混合路线，与 RoomCraft 一致。**本批决定**：1.2 m / 1.22 m 仍按软罚分（避免一卡全挂），但 `connectivityPenalty`（不可达 zone）升级为硬——不可达意味着该 zone 完全不可用，等价于 skipped。
2. **约束哲学：全软 vs 硬/软二分**：FlairGPT 所有 cost 都是可加权 λ；RoomCraft 有明确 hard 列表。**本批决定**：跟随 RoomCraft 的硬/软二分（与我们已有的 refusals 硬筛一致），不照搬 FlairGPT 全软。
3. **cell 尺寸与阈值的整除关系**：Co-Layout 建议 0.3 m cell 让 1.2 m 整除成 4 cells；RoomCraft 双人交汇阈值 1.22 m，1.22 / 0.3 ≈ 4.07 不能整除。**实现时不强行要求整除**：cell 只用于 BFS 连通性判断，路径净宽用真实米数测量，1.22 m 单独作为阈值常量。

### 4.2 P0（本批或下批落地）

**P0-1：人体工学三项硬阈值接入 `plan-scoring.ts`**

- 改文件：`frontend/lib/plan-scoring.ts`（新增）、`frontend/lib/plan-approve.ts`（提供 placements 后 geometry）。
- 新函数签名：

  ```ts
  export interface ErgonomicsReport {
    chairClearanceViolations: Array<{
      furnitureId: string;          // 椅背所属
      gapM: number;                 // 实测净距
      thresholdM: number;           // 0.6
      infeasible: boolean;          // gapM < 0.3
    }>;
    checkinQueueDepthM: number;      // 签到台前宾客侧净距
    checkinQueueThresholdM: number; // 1.5
    doublePassWidthM: number;       // 主通道双人交汇实测
    doublePassThresholdM: number;   // 1.22
  }
  export function evaluateErgonomics(opts: {
    placements: ZoneFurniturePlacement[];
    zones: ZonePlacement[];
  }): ErgonomicsReport;
  ```

- 打分接线：`score = capacitySeats − 2·skipped − 3·outOfBounds + flowPenalty + overlapPenalty − w_e·ergonomicsPenalty`，权重初值待对抗测试 A–H 跑完再定。
- 必加测试：
  - 餐椅背贴到邻桌 edge < 0.6 m → 扣分；< 0.3 m → infeasible。
  - 签到台到 zone 边 1.4 m → `checkinQueueDepthM = 1.4`，触发 violation。
  - 主通道实测 1.20 m → 触发 `doublePassWidthM < 1.22`（注意 1.2 与 1.22 的 2 cm 差异要能测出）。

**P0-2：走廊连通 + 每 zone 可达性接入 `flow-constraints.ts`**

- 改文件：`frontend/lib/flow-constraints.ts`（新增 `evaluateCorridorConnectivity`，签名见 §2.3）。
- 对接：现有 `flowPenalty` 保留；新增 `connectivityPenalty`（不可达 enclosed zone 数 × 大权重，初值 5）与 `pathWidthPenalty`（Σ pathWidthViolationM × 小权重，初值 2）。
- 必加测试（对应对抗测试 A–H）：
  - A：booth 把休息区入口完全堵死 → `perZone[lounge].reachable = false`、`blockedBy` 含该 booth id。
  - B：主通道被桌子压到 1.0 m → `pathWidthViolationM = 0.2`。
  - C：入口正中被大件挡住 → `connected = false`、`unreachableWalkableAreaM2 > 0`。
  - D：签到→圆桌两条路径一宽一窄 → 取窄路 1.1 m 进入 violation。
  - E：zone kind = open（如中央主桌区）→ 不要求入口接点。
  - F：所有 zone 都可达、净宽全部 ≥ 1.2 m → 报告全绿。
  - G：L 形场地（非矩形 walkable 图）→ BFS 仍正确。
  - H：入口 widthM = 1.0 m，被签到台压到 0.6 m → 起点扇区收缩仍能 BFS。

**P0-3：violation envelope 带 code，未知 zoneType 不再静默兜底**

- 改文件：`frontend/lib/plan-scoring.ts`（`ScoredPlan` 加 `violations: Violation[]`）、`frontend/lib/plan-approve.ts`（`ann.zoneType ?? 'roundtable'` 改为返回 `E_UNKNOWN_ZONE_TYPE` warning）、`frontend/lib/room-organizer.tsx`（`pickRecommendedPlan` 空数组不再 throw，返回带 violations 的空 envelope）。
- 类型签名：

  ```ts
  export type ViolationCode =
    | 'E_OUT_OF_BOUNDS' | 'E_ZONE_TOO_SMALL' | 'E_FLOW_NARROW'
    | 'E_EGRESS_BLOCKED' | 'E_ZONE_OVERLAP' | 'E_UNKNOWN_ZONE_TYPE'
    | 'E_ERGONOMICS_CHAIR_CLEARANCE' | 'E_ERGONOMICS_CHECKIN_QUEUE'
    | 'E_PATH_WIDTH' | 'E_CORRIDOR_DISCONNECTED';
  export interface Violation {
    code: ViolationCode;
    severity: 'error' | 'warning';
    message: string;              // 中文人话
    zoneId?: string;
    ownerId?: string;
  }
  ```

- 必加测试：未知 zoneType `"stage"` 出现在 annotations → 返回 `E_UNKNOWN_ZONE_TYPE` warning，且不再静默当 roundtable 摆椅子。

### 4.3 P1（backlog）

1. **plan-annotation 加 door / window 节点类型**：`kind: 'door' | 'window'`，geometry 带 wall 与 position；为门 90 cm 弧遮挡、`away_from_fixed_object` cost 铺路。
2. **pairReachability 落地**：`CorridorConnectivityReport.pairReachability` 已预留字段，下批填实现——重点测"签到→圆桌"、"圆桌→打卡"、"打卡→休息"三对。
3. **blockedEntrances 独立扣分项**：当前 `blockedBy` 只进人话，下一步升级为 `−w_b · blockedEntrances` 软罚分。
4. **score 拆成 0–100 子分**：`{capacity, flow, ergonomics}` 各自归一到 0–100，UI 能说"容量 90 / 动线 65 / 人体 70"，而不是一个裸整数。
5. **FurnitureSpec 分层 primary / secondary / tertiary**：当前圆桌是 primary、椅子是 secondary、签到台后的工作椅也是 secondary——但我们把它们当同优先级写在 SPEC 里。下批引入分层，让 cost function 库能区分锚点与补充件。

### 4.4 P2（远期）

1. **两次 LLM 调用分工**：先 grounding 出 semantic zone 表 + assumptions + required_spaces 覆盖度，再在已接地 zone 上 furnish。当前 `planZones` 是一次性纯函数网格，没有显式 grounding 输出可审。
2. **OpenEventCAD 式具名 inventory 库 + grouped seating 模板**：把 `SPEC` 从 `as const` 硬编码升级为可扩展目录，支持用户加自己的桌子；引入 theater / banquet / u-shape 排椅模板复用。
3. **Privacy Sorting 入口层级软约束**：把"签到区必须在入口第一排、圆桌区在签到区之后、休息区最深"编码成软不等式（Co-Layout 的 `D_k = (1/A_k) Σ x_{i,j}^k · d_{i,j}` 的摆摊版）。
4. **FlairGPT 式 LLM→cost 函数映射**：当未来支持用户用自然语言声明"签到台不能正对主舞台"这类跨 zone 关系时，让 LLM 把自然语言 map 到 cost function 库，而不是改 if/else。

## 二、变量矩阵（组间哪些变量不同）

| 变量 | G1 茶室照片 | G2 寺庙照片 | G3 西湖视频 | G4 130 张（web-scan） |
| --- | --- | --- | --- | --- |
| 张数/时长 | 63 张 | 32 张 | 1 段视频 26 s | 130 张 |
| 画幅一致性 | 单一 1536×2048 | 单画幅（实测值未归档，U4） | 单段视频 | 单一（同机同模式） |
| 场景/采集形态 | 室内空间走拍 | 室外单主体全周闭环 | 室外空间夜间走拍 | 室内空间走拍 |
| 类型 | 照片 | 照片 | 视频 | 照片 |
| scene / mode | `space` | `model` | `space` | `mode=scene` |
| 质量档 | `low` | 未记录（U5） | `low` 与 `normal` 各一 | `fast`（`high` 被 422） |
| 上传通道 | 开放平台 World API | 开放平台 World API | 开放平台 World API | web-scan v1（**不同服务**） |
| 结果 | FAILED 122 s 无原因 | **5/5 SUCCEEDED** | **2/2 SUCCEEDED** | succeeded 108.6 s |

组间单变量解读（哪些差异能推出什么）：

- **G3 内部**是真正的单变量对照（同一 0194 素材，只换质量档）：档位只改变产物细节（6.1 MB vs 23.2 MB），不改变成败。
- **G1 vs G2** 同通道、同类型（照片）、同低档量级，但张数（63 vs 32）、场景形态（室内空间走拍 vs 单主体全周闭环）、`scene` 值（space vs model）**三个变量同时不同**——无法唯一归因茶室失败，这正是 §四 U1 悬而未决的原因。
- **G4 vs G1** 同一素材来源、不同通道：130 张走 web-scan 能出结果，63 张走 World API 失败——说明失败**不绑定素材本身**，绑定「通道 × 素材形态」组合。
- **G2 vs G1** 也说明：开放平台 OUS 图片上传、入库、受理、重建主体**整条链都能通**，把 docs/17 早期「图片通道整体故障」和 docs/19 §三.2「OUS 图片跑不通是 Aholo bug」两个阶段性判断推翻。

## 三、已证实的结论（每条带可查证出处）

- **C1 · 开放平台 API 与我方集成可用**：照片 5/5（G2）+ 视频 2/2（G3）成功。出处：HANDOFF.md:98；各任务回执（G2/G3 证据目录）。
- **C2 · 12 张可靠位姿门槛（web-scan）**：20 张室内走拍组 job 8.0 秒失败，报错原文 `Fewer than 12 photos have reliable camera positions`（HANDOFF.md:294；原始日志在临时目录已清理，未入仓，U9）；job 硬约束原文 `A reconstruction requires 12 to 1000000 valid uploaded images.`（`docs/evidence/aholo/scan-outdoor-29/outdoor-blockers.json` `attempts[1].detail`）。边界印证：scan-tearoom-130 恰好 12/130 登记仍 succeeded。
- **C3 · 混画幅上传阶段即拒（web-scan）**：422 `Keep the same aspect ratio and lens within one scene`，第 11 张 `DJI_20261102191018_0187_D.JPG` 触发（`outdoor-blockers.json` `attempts[0]`；HANDOFF.md:304,318-323：四种画幅 9:16×10 / 8:3×6 / 16:9×8 / 1:1×5 混装）。
- **C4 · `quality:"high"` 对照片 job 422 硬拒，只对 INSV/OSV 导入有效**：原文 `quality 'high' applies only to a reconstruction imported from an INSV or OSV.`，两处独立复现（`docs/evidence/aholo/scan-room130-2048/scan-fail.json` 与 `docs/evidence/aholo/scan-tearoom-130/job-fail.json`，均 `http=422`）。
- **C5 · World API 图片路径 ≥20 张门槛**：10 张雕塑批创建即 400 BIZ_-1「图片资源项至少 20 张」（docs/17 §〇，未受理不扣费）。
- **C6 · World API 任务失败无错误字段**：`status=FAILED, progress=1, splats.urls 全 null, imagery=null`（G1 `report.json` 的 `reportedErrorFields: []`；docs/17 §一 11 发同形态）。
- **C7 · `x-source: openapi` 必填**：缺头报误导性 BIZ_-1「文件链接不对」（docs/19 §三.1、§六）。
- **C8 · World API 质量档只影响产物不影响成败**：同素材 low 6,097,192 B vs normal 23,199,588 B（G3 两回执字节）。
- **C9 · 图/视频不可混传**：纯视频须全部 `type=video`（docs/19 §三）。
- **C10 · web-scan 产物无米制尺度**：`scale.json` 全部 relative、`meters_per_unit=null`（G4 `scale.json` 字段值；HANDOFF.md:308）——尺寸必须走场地标定。
- **C11 · `progress=1` 不判成败，只认 `status`**：G1 FAILED 时 progress=1（`report.json` polls 末项；HANDOFF.md:312）。
- **C12 · 有 worldId 只代表受理**：G1 HTTP 200 + worldId 仍 FAILED（`report.json` createHttp=200 / status=FAILED；HANDOFF.md:120）。
- **C13 · 本地 SfM 配准成功 ≠ 云端成功**：63 张本地主模型 63 相机/3,141 点/0.76px 配准成功（docs/17 §二），同一批云端 FAILED（G1）。
- **C14 · 图片失败自动退费**：图片实验 9+ 次净消耗 0，视频两单 -70（docs/19 §五，账单页口径；本轮未重验账单页）。

## 四、仍未知的失败原因（明确悬置）

- **U1 · 茶室照片在 World API 云端失败的确切阶段与原因**：受理（HTTP 200）→ PREPROCESSING → RUNNING → 122 s 后 FAILED；API 无错误字段（C6）、账单只给「失败退回」、官方未回。已实测排除：公网可达性、content-type、对象新鲜度、EXIF/焦距先验、数量（98→40）、分辨率（3072→1440）、三档质量、scene 词表、useMask、网关区域、官方 SDK vs 自研（docs/17 §二全部穷尽）。G2 成功后「账号/管线整体坏」假说已排除；剩余候选=**素材采集形态**（室内走拍照片的位姿/覆盖分布）或 **space 场景照片管线特有问题**——现有数据无法区分这两者。
- **U2 · docs/17 早期 11 发失败矩阵的逐发原因**：同 U1，全部无错误字段；`%TEMP%\scene3d-probe` 原始日志已清理，只能以文档记载为准（U9）。
- **U3 · web-scan 登记率波动**：同 130 张同规则两次 job，38/130（29.2%）vs 12/130（9.2%），原因未测（G4 两个 job 回执即证据本体）。
- **U4 · G2 输入的实际像素尺寸**未随证据落盘（目录名 `-2048` 待与生成脚本核对）。
- **U5 · G2 的 `taskQuality` 值**未记录（`recon-chain.mjs` 只把响应体写入 chain.jsonl，请求体未落盘）。
- **U6 · World API 与 web-scan 是否共享 recon 管线**未知（两通道门槛都不同：20 张 vs 12 张）。
- **U7 · 网页端对照（SC-24）未执行**：63 张素材已重制待传（`recheck-tearoom-3FO4K4RL8KM8/web-upload-images/`），网页侧行为尚无任何数据（HANDOFF.md:103）。
- **U8 · 官方渠道无回复**：问询草稿在 `docs/evidence/scene3d-recon-2026-11/support_email_draft.md`，未获答复前不再烧扣费任务（docs/17 §五）。

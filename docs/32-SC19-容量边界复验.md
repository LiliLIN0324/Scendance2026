## 一、计算口径

### 1.1 容量怎么算（capacitySeats）

- **Path 1**：`computeCapacitySeats`（plan-scoring.ts:642-650）按**椅名**计数——「餐椅/工作椅/讲座椅」各 +1、「长椅」+2，桌/台/绿植不算座。测试背书 plan-scoring.test.ts:133（4 餐椅+1 长椅=6 座）。
- **Path 2**：`seatCountIn`（scene-script-compiler.ts:646-648）按 **type** 计数——`chair`/`dining-chair` 各 +1；宴席组 = 1 桌（1.8×1.0，constants.ts:80）+ 4 椅（furniture-sets.ts:38-44）= 4 座/组；课桌模式 = 1 课桌 + 1 椅 = 1 座/组。
- 两条链的「座」口径一致（都是椅子数），但**桌型不同**：Path 1 圆桌来自 `lib/furniture-catalog.ts`（Ø1.8，71627ba 校准），Path 2 用 `components/room-organizer/lib/constants.ts` 的矩形 Dining Table——**Path 2 不经过 plan-approve 常数，G5 不影响 Path 2**。

### 1.2 桌椅生成配方（plan-approve.ts）与常数的角色

| 常数 | 值 / 位置 | 在容量里的角色 |
| --- | --- | --- |
| `DESK_ROW_PITCH_M=1.4` | plan-approve.ts:47 | 课桌排距（桌心距），直接决定排数 → 容量。**生成器硬值，不随 density 缩放**（:35-36 红线注释） |
| `DESK_AISLE_M=1.2` | plan-approve.ts:49 | 每 `DESK_BLOCK_TABLES=3`（:53）桌一个 block，block 间走道；决定每排桌数 |
| `DESK_CHAIRS_PER_TABLE=3` | plan-approve.ts:51 | 每桌 3 座；桌间留 `DESK_TABLE_GAP_M=0.04`（:63）避开 AABB 0.02 容差 |
| `WALL_CLEARANCE_M=0.3` / `CHAIR_BACK_CLEARANCE_M=0.6` | plan-approve.ts:28/:30 | `applyWallClearance`（:456-534）后处理：距墙不足先内移；**内移后与已接受家具 AABB 相交（0.02 容差）则该件丢弃进 skipped**（:514-529）。有 roomSize 时才会运行（plan-scoring.ts:257-263） |
| `TABLE_DIAMETER=1.2` / `CHAIR_RING_RADIUS=0.9` | plan-approve.ts:18/:22 | 圆桌配方的 pitch=max(1.5, density 间距)（:148）与环椅半径（:255-256）。**与 catalog Ø1.8 不同步（G5）** |
| `MAX_TABLES_PER_ZONE=3` | plan-approve.ts:24 | 圆桌单区硬上限 → 圆桌区容量上限 = 3×8=24 座，**与场地大小无关** |
| density | density.ts:19-26 | spacingMeters=1.8−0.9d：sparse 1.575 / balanced 1.35 / dense 1.08；对课桌配方无效（硬值），对圆桌只在 ≥1.5 时生效 |

课桌容量速算（Hall D5 用例 A）：课桌区 17×9 → 7 桌/排 × 6 排 × 3 椅 = **126 座**（与基准 A1 的 96~144 断言吻合）。

### 1.3 可行性与候选（硬约束在评分里的位置）

- hard violation 汇总：`evaluateHumanFactors`（CHAIR_GAP/AISLE_CLEARANCE）+ `evaluateReachability`（ZONE_UNREACHABLE/ZONE_PAIR_DISCONNECTED/ZONE_ENTRANCE_BLOCKED）+ `detectFurnitureOverlap`（BBOX_OVERLAP）+ `evaluateDoorSweep`（DOOR_SWEEP_BLOCKED 真门被挡时）——plan-scoring.ts:285-303。
- `feasible = hardViolations.length===0`，且 `status==='unknown'` 的条目**不算 hard**（plan-scoring.ts:325）；`pickRecommendedPlan` 只在 feasible 集合里挑，全不可行返回 null（plan-scoring.ts:218-234）。
- soft（CHECKIN_QUEUE/PRIVACY_ORDER/ROOM_SIZE_UNKNOWN/DOOR_UNKNOWN/推测门 unknown）只进 reasons 不扣分、不否决（plan-scoring.ts:368-371）。

### 1.4 targetCapacity 降容建议（71627ba）的人话口径

`capacitySeats < targetCapacity×0.9` 时（plan-scoring.ts:381-386）拼一条：
`这里最多约可坐 {X} 座，装不下 {Y} 人；建议把人数降到约 {Z} 人，或换更大的场地`，其中 `Z = max(10, floor(X/10)×10)`（10 的倍数）。实测输出见 §三.2。

**接线缺口（本卡核对重点）**：全仓 `targetCapacity` 只有两处引用——lib 本体（plan-scoring.ts:67,178,181,244,381）和基准测试 B3（hall-d5-benchmark.e2e.test.ts:256）。**UI 主路径 `room-organizer.tsx:2664` 调 `generateScoredPlans` 只传 `{roomSize}`，不传 targetCapacity** → 71627ba 的降容话术在产品里**永远不会出现在方案卡上**；对话链路的人数走 Path 2 的 `guests`（另一套解释，见验收点二）。测试 B2 里的旧注释「现有管线无目标人数入参」（hall-d5-benchmark.e2e.test.ts:246-247）已过时，可顺带清理。

### 1.5 Path 2 的可达容量口径（对照参考，实现更严谨）

`fillSeating`（scene-script-compiler.ts:442-581）在摆任何东西之前逐格空跑探测：`capacity` = 这套整排摆法逐格探到的顶、`upper` = 同一块地按面积的宽松上界，两者分开（:483-492），话术钉死「**按这版排法排到 N 座就是头**」而不说「这块地最多 N 座」（:484-486 注释红线；scene-script.ts:215-216「quote our reach, never the room」）。缺座时出 `W_CAPACITY`（:376-389、:522-531）+ hint（加宽 seating 区/少占舞台签到的地/降人数/换更大场地）。

## 二、三个验收点逐项

### 验收点一：合理方案进入候选

**现状**：Path 1 出 sparse/balanced/dense 三版（去重后 1~3 版），feasible 才能被推荐；hard violation 方案不进推荐、不能被容量加分盖过（plan-scoring.ts:117-117、:213-216、:324-326）。UI 方案卡显示三版分数条 + 可坐 N 座 + hard/soft violations（plan-card.tsx:342-394），推荐版高亮需 reasons 非空（:349-350）。

**证据 / 测试覆盖**（本基线实跑全绿）：
- 基准 A1：120 人课桌出 1~3 版、≥1 版 feasible、容量 96~144（hall-d5-benchmark.e2e.test.ts:88-100）；
- A10：feasible=false 不被 pickRecommended 选中、全不可行返回 null（:203-216）；
- plan-scoring.test.ts:314（feasible=false 不参与推荐）、plan-scoring-anti.test.ts 全套 15 例；
- Path 2：local-plan.test.ts 8 例、scene-script-compiler.test.ts 11 例。

**推演缺口**：
1. **圆桌区任何尺寸都全变体 INFEASIBLE → REC=null**（实测：16×10 / 4×4 / 2×2 三档圆桌区在 19×15 场地里全部 `feasible=false`、`pickRecommendedPlan=null`，详见 §三.3）。「合理方案进入候选」对圆桌/宴会场景**不成立**——但失败被正确表达为 hard violations，不是假通过。
2. REC=null 时 UI 仍默认渲染 balanced 版（`selectedVariantId` 初值 'balanced'，room-organizer.tsx:236、:2669-2670），方案卡**没有**「本版不可行 / 无推荐」的版级标识（plan-card.tsx 无 feasible/feasibilityStatus 渲染，git grep 零命中）——策划看到的还是一张带分数条的版，只能靠 violation 文案自行判断，与 docs/30 G1（assurance 无 UI 出口）同族。

### 验收点二：装不下时解释约束和可达容量

**现状**：
- Path 1：不虚增椅子——`capacitySeats` 严格等于 placements 椅数（测试 B2 = docs/27 的 B3 断言）；降容人话存在于 lib（§1.4）；skipped 逐件带 reason；BOM/库存缺口显式（plan-scoring.test.ts:499-540）。
- Path 2：逐格探测可达容量 + `W_CAPACITY` 人话 + summary 行「按这版排法最多 N 座（要 M）」，措辞严格区分「本版排法上限」与「场地极限」。

**证据 / 测试覆盖**（实跑全绿）：
- 基准 B1/B2/B3（=docs/27 的 B1/B2/B3/B4）：capacitySeats<250、≥100、等于实际椅数、传 targetCapacity=250 时 reasons 出现「装不下 250」+「建议(把人数)降到」（hall-d5-benchmark.e2e.test.ts:225-265）；
- Path 2 实测探针：12×9 场地 guests=250 → seats=16、`W_CAPACITY`「脚本要 250 个座位，按这套排法这块座位区排到 16 座就是头，这一版摆出 16 个」+ hint「加宽 seating 区、少占舞台和签到的地，或者让人数降到这个数以下」；summary「座位 11.3 × 4.1 m，按这版排法最多 16 座（要 250）」。

**推演缺口**：
1. **targetCapacity 未接线**（§1.4）：产品里用户填 250 人后，Path 1 三版方案卡**不会**出现「装不下 250」——docs/27 B4 在真实 UI 上目前只能判「断点」，自动化的 B3 断言只证明 lib 能力，不证明产品行为。
2. **圆桌路径的「可达容量」数字失真**：16×10 圆桌区 + 250 人实测 reasons 出「这里最多约可坐 10 座，装不下 250 人；建议把人数降到约 10 人」——这个 10 不是场地几何上限，是 `applyWallClearance` 吞掉 16 件后残存的孤儿椅数（§三.3）；且 `MAX_TABLES_PER_ZONE=3` 把圆桌区容量钉死在 24 座，250 人宴会永远「装不下」，但系统不会说「这个区的配方上限就是 24」。
3. skipped reason 文案误导：环椅冲突被报成「贴墙放不下「餐椅」，向内平移后与其他家具压住」（plan-approve.ts:522-528）——实际既没贴墙也没内移，是环几何自撞（G5 后果，见 §四）。
4. skipped 计数措辞：「{N} 个区被跳过」（plan-scoring.ts:812）把**件数**说成**区数**（实测「16 个区被跳过」，实为 16 件家具）。

### 验收点三：未知门信息不会被标为通过

**现状**（分层）：
- 数据层：用户没画门 → `withDefaultDoor` 合成南门 `widthM:0.9, inferred:true`（plan-annotation.ts:175-188）；fixture 按图推断的门同样 `inferred:true`。
- 评分层 `evaluateDoorSweep`（human-factors.ts:143-234）：推测门**不做 hard blocked 判定，统一 soft unknown**「门宽/位置/开启方向未核验」（:193-202）；真门检出遮挡给 hard violated，但开启方向未知仍**追加**一条 soft unknown「结论为近似」（:224-231）；缺 roomSize 只给 unknown（:153-164）。四值口径里 `pass` 的语义是「不生成 violation」（:31-32）——门检查没有任何路径产 `status:'pass'`。
- 版级：缺真实门 → `DOOR_UNKNOWN` soft unknown「门位置未确认，本方案为待核验草案」（plan-scoring.ts:315-322）+ `assurance='draft_unverified'`（:419）；hard 且 status=unknown 的条目不会被算进可行与否决（:325）。

**证据 / 测试覆盖**（实跑全绿）：基准 A9/C4（doorSweeps 至少一条 unknown、**不得出现 status=pass**、assurance=draft_unverified，hall-d5-benchmark.e2e.test.ts:188-201、:326-333）；door-privacy.test.ts 6 例（门弧内 hard、弧外 soft unknown、缺尺寸只 unknown）；plan-overlay 4 例门（虚线弧+「门未确认」小字）；door-render 4 例；plan-scoring-anti :212（真门 verified）、:228（ROOM_SIZE_UNKNOWN 不当 pass）。

**本卡实测探针**（用例 A 满容量 + fixture 推断门）：rec=balanced、cap=126、FEASIBLE、assurance=draft_unverified、door 类 violation 全部 `unknown`、全 plan 无任何 `status:'pass'`、targetCapacity=120 不触发降容（126≥108，对齐 docs/27 A11）。

**推演缺口**：
1. **推测门不判堵门**：inferred 门连 0.45m 门弧扇区的 hard 检查都跳过（human-factors.ts:193-202 的设计决定「不用猜的门否决方案」）。代价：满容量场景下家具若真堵住了推断门位，只有一条 soft unknown 提示，没有 hard 拦截——「入口未知」时堵门检查事实上失效，只能靠画布小字 + 人工走查兜底（与 G3 同向）。
2. assurance=draft_unverified 没有版级 UI 出口（docs/30 G1，本卡复认：plan-card 无 assurance 渲染）。
3. 用户真实画的门 widthM 是必填 number（plan-annotation.ts:39）——画门时若没给宽，管线拿什么占位没有统一口径（fixture 测试用 0.9 占位 + unknown 状态表达，hall-d5-benchmark.e2e.test.ts:42-46），建议在画门交互里显式收口。

## 四、G5 / G3 对本卡的影响评估

### 4.1 G5（圆桌常数未同步）——影响 S3，不 Impact 课桌/签到路径；机制描述需修正

- **docs/30 原预测**：「圆桌路径会被误判 hard BBOX_OVERLAP」。**本卡实测修正**：有 roomSize 时（真实 UI 路径必传，room-organizer.tsx:2660-2664），`applyWallClearance` 先于 `detectFurnitureOverlap` 运行（plan-scoring.ts:257-263 → :288），把重叠件**丢弃**——BBOX_OVERLAP 根本没机会产生；最终否决方案的是**幸存环椅的 CHAIR_GAP**（0.69m<0.90m）或孤桌的 ZONE_UNREACHABLE/ZONE_ENTRANCE_BLOCKED。BBOX_OVERLAP 只在**不传 roomSize** 的分支可见（此时 INSUFFICIENT_INPUT）。
- **更深的坑**：CHAIR_GAP 由环几何决定（8 椅均布 ring 0.9 → 相邻椅心距 2×0.9×sin(π/8)≈0.689m），**与 TABLE_DIAMETER 无关**——就算把 `TABLE_DIAMETER` 同步回 1.8，圆桌路径仍不可行。修复必须同时处理：环半径/每桌椅数（8 椅要 0.9m 间距需 ring≥1.174）或给 `detectFurnitureOverlap`/`evaluateHumanFactors` 加「同桌椅-桌 / 同环相邻椅」豁免。
- **旧套件为何还是绿的**：`hall-benchmark.test.ts`（4 例，本卡实跑通过）在 raw 上断言椅数、在 walled 上断言无重叠（:53-74）——`applyWallClearance` 吞件恰好让它两边都过，**掩盖了 G5**。这也是「测试全绿但圆桌不可用」的完整解释。
- 对 SC-19 的净影响：**超容量场景若用圆桌，验收点一不成立（无候选）、验收点二的可达容量数字失真**；课桌路径（用例 A/B）不受影响，基准 18 例全绿即证。

### 4.2 G3（门位 ±1.5m 带只在测试里）——影响 S1/S2 的人工走查口径

- 生成器对门的唯一空间约束是门弧扇区半径 = widthM/2 ≈0.45m（human-factors.ts:173、:212），且**推测门连这条也不判**（:193-202）；±1.5m 走查判定带只存在于基准 A7/A8 的测试断言（hall-d5-benchmark.e2e.test.ts:159-186）。
- 对 SC-19：满容量/超容量场景下「不堵门、不堵应急口」在产品里没有自动化背书——SC-03 走查用例 A/B 时若按 ±1.5m 判定，可能出现「测试绿、走查红」，与 docs/30 交接注记一致，本卡维持该风险判断。
- Path 2 的 keep-out（role=aisle/reserved）是硬约束（`intrudesKeepOut` → E_KEEP_OUT，scene-script-compiler.ts:204-215、:229），但只认 script 里的 zone；brief 自动生成的前场通道固定 1.2m（scene-script.ts:266），**与门位无联动**——门若开在通道两端之外，Path 2 同样不保证入口净空。

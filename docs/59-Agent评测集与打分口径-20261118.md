# 59 · Agent 评测集与打分口径（2026-11-18）

> 一句话：把 43 案与 3 条事故从「可读参照」变成 **13 条可复算的评测样本 + 一个纯函数打分器**。
> 数据：`data/agent-corpus/cases/eval-cases.json`；打分器：`frontend/lib/agent-corpus/eval-suite.ts`；守门：`tests/agent-corpus-eval-cases.test.ts`。

## 一、判分口径（先定规则，再谈分数）

| 样本类型 | 考什么 | 怎么算过 | 明确不算的 |
|---|---|---|---|
| `layout`（10 条） | Agent 提的方案「像不像一个真方案」 | 模板命中 + 分区/件数/动线/入口四项落带 | 不校验具体坐标、不校验物料型号 |
| `failure`（3 条） | 布局有硬伤时「该报的违规报没报出来」 | 期望违规全部由执行器报出 | 未实现判据不计分；「说了算不了」不算命中 |

两条底线：

1. **参考带不是标准答案**。带子来自平台底图读数，来源已在每条样本的 `labelSource` 里写死为「非主办方清单」。
2. **不拿未实现判据凑数**。`failure` 样本的期望违规必须是 `IMPLEMENTED_RULE_IDS` 里的；其余引用进 `contextRefs`，只作上下文。

## 三、打分器

```ts
import { scoreLayoutSample, scoreFailureSample, summarizeResults } from '@/lib/agent-corpus/eval-suite';

// Agent 给的方案摘要
scoreLayoutSample(sample, { templateId: 'MKT', zones: 9, objects: 60, routes: 4, entrances: 3 });
// → { pass: true, failures: [] }

// 布局直接过判据
scoreFailureSample(sample, rules);
// → { pass: true, failures: [], notes: ['本次共 69 条判据未实现，未计入得分'] }

summarizeResults(results);
// → { total, passed, failed, passRate, byKind: { layout: {...}, failure: {...} } }
```

设计取舍：

- **纯函数、不做 I/O**：样本由调用方传入，所以 Node 测试与浏览器端自检能用同一套逻辑。
- **失败要可读**：`failures` 逐条写「zones 4 ∉ [7,11]」，不返回一个 0.6 的分数了事。
- **意外多报不判错、只提示**：`notes` 记「额外报出」，交人工判断误报；宁可放过，不要逼模型学会「少报才不会扣分」。
- **修好缺陷必须变红**：测试里把 INC-02 夹具补到 4 个出口，断言打分从通过变不通过——防止样本空转。

## 四、三条使用纪律

1. **这只是离线评测**，没接 CI 门禁，也没有真实 Agent 输出的基线分数；不要把「13/13 通过」当质量证明。
2. **平台读数不是标准答案**，同一场地的分区口径换个人数就不一样；样本只用来卡量级。
3. **未实现判据不能计分**，否则等于奖励「什么都不报」。目前 80 条判据里只有 11 条能算，这是评测集的真实上限。

## 五、现状与缺口

- 只有 3 条负样本，覆盖「单出口 / 超密 / 无退距」三类；消防通道宽度、水域边界、临时建筑退距还没有可执行夹具。
- `layout` 样本的期望值来自平台读数，容差是经验值（±2 / ±25% / ±1），没有用真实方案回归校准过。
- 尚未接 Agent：需要一次真实生成，把 10 条 `prompt` 跑成 `LayoutProposal`，才有第一版基线。

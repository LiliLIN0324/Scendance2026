# 幕景智能 Chat 与活动智能建造主计划

2026-11-07 · 供 GPT-6.1 Terra 执行、独立评审者验收。本文是实施计划，不是功能完成声明。

实施范围、任务分工和验收原则见本文；具体验收项目见 [智能 Chat 验收清单](2026-11-07-智能Chat验收清单.md)。

## 1. 产品目标与顺序

用户通过一个 Chat，从不完整的活动想法推进到可审阅的空间方案，并完成修改、检查与交接。用户不用理解内部 Agent、接口或状态机，也不必先填完一套专业资料。用户在 2026-11-07 明确选择：第一版应从模糊想法出发，连场地和物料一起规划；不以用户已经选好场地为前提。

完整目标仍包括事实来源、规范适用、活动流程、库存、版本确认和真实场地验证。以下先后顺序不缩减长期范围：

| 发布节点 | 用户能实际做到什么 | 完成证据 |
|---|---|---|
| R1 连续 Chat | 能问、能补充、能改口、能停止；需求不丢、不反复问已知信息 | 同一真实工作台完整多轮脚本，另列真实模型结果 |
| R2 建造闭环 | 同一 Chat 调用场地/物料/布局/检查/联网/交接；预览、确认、撤销贯通 | 工具参数与实际结果可核对；未执行部分可见；一套真实资料与合成缺项案例 |
| R3 可交接与恢复 | 需求、场景、事实和版本关系一致；刷新/恢复/失败不静默丢资料 | 故障注入、恢复重读、版本失效、独立执行人员交接测试 |
| R4 垂直成熟度 | 多阶段活动、排队与资源冲突、真实库存和真实场地效果 | 场地方/专业人员核对与执行反馈；不能用论文或模拟测试替代 |

近期可提交 main 的突破以 R1 + 已核验的 R2 单场闭环为目标；R3/R4 不得被写成已完成。

## 2. 从第一性原理确定责任

1. 用户给的是意图，不是程序。模型负责理解语义、提问、选择合适工具与解释；不继续为每个自然句式堆产品分支。
2. 几何、数据写入、版本和规则由代码执行。模型不能直接写坐标、数据库、库存事实或安全通过状态。
3. 只读回答、只读查询和可撤销修改的风险不同。普通问答不要求先填人数；读当前方案不应反复确认；改变场景需展示完整差异；共享/发布遵守已有授权。
4. “用户确认需要”与“现实中已经核实”是两种事实。用户想要轮椅通行，不等于当前方案已满足无障碍；用户说没有轮椅使用者，也不能推断无需无障碍。
5. 一个任务可以部分完成，但不得静默丢弃。完整保留意图，明确报告已完成、等待确认、资料不足和不支持的部分。
6. 搜索摘要、网页内容、附件和历史对话是资料，不是能改写系统权限的指令。

## 3. 用户流程

### 开始活动

用户：“我想办社区讲座，资料还不齐。”

系统先回应活动本身，询问影响下一步最大的一个问题，例如人数或是否已有场地；不要一次索要十项资料。用户不知道时提供“先按可修改假设探索”的选项，假设在方案内可见，不写成已确认事实。

### 连续交流

用户可以在需求补充、原理问题、查看现状、修改和导出之间切换。模型看到本场已确认需求、未解决项、当前候选摘要和有限近期对话。换话题不会自动丢弃候选；提出新修改时旧候选是否失效由依赖判断。

同一输入框提供：发送中/排队中、停止当前等待、必要时取消待处理消息、明确重试。没有成功回执不等于未计费，不自动重发结果未知的付费请求。

### 复合请求

“改成 30 人、不签到，把桌子往左移，顺便给我清单。”

先识别全部事项及依赖：人数/签到影响布局，移动目标需明确，清单应来自最终候选或最终已应用版本并标明范围。目标不明确时只追问这个目标；不能因为“清单”快捷词吞掉前半句。对暂不支持联合保存的部分明确标待处理，不假称完成。

### 预览与执行

生成和修改都进入同一份候选及差异视图。已确认的事实、锁定对象、对象 ID、当前活动/楼层和场景 revision 参与最终独立复核。确认后一次应用、一次撤销；实际执行失败应给原因与原状态，不用模型自由文本伪造执行成功。

### 交接

交接包至少包含特定版本的平面与尺寸、物料身份/数量、需求与来源、假设、检查覆盖范围、未核验事项和执行任务。普通备份与交接用途不同；每项内容是否可恢复必须明确。

## 4. 最简可演进架构

```text
同一个 Chat
  → 同活动/会话的单轮生命周期（排队、取消、超时、去重）
  → 模型理解 + 有限工具选择
  → 白名单工具执行 / 澄清 / 只读回答
  → 结构化工具结果与候选
  → 独立检查 → 人工确认 → 应用及撤销
  → 回复与交接
```

不一次性重写 AgentPanel，也不引入第二套生成等待状态机。优先复用现有 Promise、runToken、AbortController、布局 store、预览与 history。需要抽取时，只抽本轮确实复用并测试的逻辑。

### 单轮逻辑契约（待实施时与既有共享契约合并）

- 输入：本轮原话、活动/会话 ID、基线 revision、有限近期可见对话、确认需求与未决事项、当前场景/候选的最小摘要、已授权工具范围。
- 输出：自然语言回复、需求补丁及原文依据、需要澄清的项、建议工具动作及明确参数、尚未处理的原话片段。
- 普通问答或简单需求，目标为一次模型请求；需要工具结果时再继续。设硬步数和调用预算，不建立无限 agent 循环。
- 模型输出必须通过共享 schema；“有这个字段”不代表来源真实。人数、目标对象、活动范围和工具参数还需语义与状态校验。
- 兼容层可以暂时调用已存在的提取/问答接口；最终对用户只有一个会话入口，不能让用户自行选择提取器、复合器、问答器。
- 不要求新框架。现有模型适配器、Zod 和纯函数足够先完成主线。原生 tool calling 如未实测支持，可用受限结构化动作协议，不能执行任意代码。

### 工具边界

| 工具类 | 复用方向 | 允许自动做 | 必须受控的部分 |
|---|---|---|---|
| 读状态 | 当前 brief、layout、事实、候选 | 返回本场最小摘要 | 身份/活动隔离，不能读取其他项目 |
| 生成候选 | localPlan / 既有生成入口 | 生成可审阅草案 | 不自动写正式场景，不暗中删除人数/需求 |
| 局部修改 | revisePlan / proposeAddition | 在指定候选上计算差异 | 明确目标、锁定对象、版本与最终复核 |
| 检查 | 几何、功能、库存与四值结果 | 对指定版本执行检查 | 未知不能算通过，规则适用范围可见 |
| 网络研究 | 现有 search/answer | 仅在已告知并授权的范围查询 | 不发附件/秘密，不伪称读过全文或已确认场地 |
| 清单与交接 | 既有聚合与导出 | 准备可预览产物 | 标明候选/已应用版本、外发与发布权限 |

模型解释应引用真实工具结果。例如“这版只有 24 把单人椅，距 30 人还差 6 把”，不能说“场地最多坐 24 人”。

## 5. 状态与保存

区分三件事：对话过程、用户需求、实际场景。不要让模型输出直接覆盖全部状态。

- 需求：字段值、依据、待确认/确认、冲突及版本。更正要能覆盖旧意图，同时保留变更记录。
- 场地事实：值/单位/来源/状态/误差/修改者/版本。来源未知的门、尺度与核定人数不得推断确认。
- 候选：基线、需求版本、事实版本、变更和检查结果。相关数据变化时旧结论失效。
- 动作：请求 ID、阶段、实际工具结果及是否已应用。用户重试不能无意重复写入。
- 保存：当前布局、BriefMemory、CreativeBrief、事实分散在不同存储。R1 不为只读问答迁移全库；R3 必须专门解决联合保存、恢复、撤销和跨标签并发，不得用多次 setItem 假装原子事务。

优先复用主目录已有 restore-journal、启动恢复门和编辑租约原型，先核它们是否真正接入。临时状态或独立事务副本不能替代产品的权威保存源。普通备份不含哪些数据必须保持提示直到真正补齐。

## 6. 已有工作必须保留

原主目录的会话/权限/编辑权边界、取消与防重、甲方钉评版本绑定、场地标注与结构核对、物料定制、恢复保护；当前分支的需求反例修复、事实记录、四值语义、候选库存、复合审阅、联网回答及交接补全。保留是按行为和验收整合，不等于整文件选择任一边。

## 7. 质量和速度一起衡量

指标：首个可见反馈、整轮完成时间、模型/工具调用次数、重复追问数、用户重复输入数、吞需求次数、错改次数、撤销恢复、放弃率和人工接管率。先测基线再定外部模型延迟目标，不承诺未知服务的响应时限。

必须满足：用户消息立即进入可见队列；本地停止动作无需等待远程请求；普通问题不触发布局修改；无隐性重试；错误与未执行内容明确；活动切换后旧结果不污染新活动。实际流式输出仅用于可见答复，结构化动作必须完整验证后执行，不能边流边改场景。

## 8. 真实案例和能力边界

沿用 `docs/research/2026-11-07-公开活动与缺资料验收.md` 的 WikiWomen/SotM 等公开资料及独立合成缺项。真实议程与虚构场地尺寸/人数/库存必须分开；公开可读不等于可复用图片/代码。Hall D5 的尺寸、参考座位与现场核定容量不可混用。

验证分四层记录：纯函数、模拟模型的实际工作台、真实模型与真实服务、真实场地及人员。任何低一层证据都不能代替高一层结论。

MiniMax 中国站 Token Plan 已有本机试用调用证据。用户后续明确授权已购积分也可以用于测试；仍应控制调用、记录可见用量和费用不确定性，密钥不进聊天/前端/文件。不得自动批量重试，也不能擅自用测试账户或其他服务降级冒充真实成功。

## 9. 工程红线与分工

不新增依赖除非评审通过；不改既有 Supabase 表结构与 3D 渲染管线；中文简体，保持既有灰绿体系；不抄 AGPL 代码；几何判断纯函数。读取适用 AGENTS 与现有共享契约。后端变更遵守评审 PR 规则。

Terra 可以负责完整工程任务，但每次有一个明确主线。一个实施者拥有 AgentPanel/主流程；独立验证者负责浏览器脚本；资料查证可并行。不能让多名代理同时改主流程，再靠反复重跑修补冲突。

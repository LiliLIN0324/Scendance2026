# 幕景工作区优化分析

2026年10月7日。依据本次讨论、Figma 草图和当前开发分支。目标是让两人的小团队能从客户需求走到活动现场交付，同时让客户看懂空间方案。

最先要改的是工作区组织方式：业务内容有固定位置，三维画布用于看空间，Binggo 用于讨论和提出修改。用户不必打开聊天窗口，才能找到需求、任务或交付资料。

本轮已落实展开工作区的业务与聊天分列、分别滚动和聊天收起。68项界面回归、类型检查和独立副本生产构建通过，桌面、390px及最终键盘焦点完成独立试用。代码已随收工检查点54e5876上传开发分支。下面的四段主导航、底图闭环和人员预算仍是后续方案；本分析保留在本机。

## 待讨论的整体布局

用户最新校正：以录音讨论为主，Figma会变化；其中有些想法不一定执行。当前优先一起核对整体工作台布局、聊天和功能入口。下列四段业务导航是分析者提出的候选方案，不是团队已经决定的产品结构；不据此直接开展整体重构。每次修改前重读相关原文和当前草图区分明确要求、讨论选项与分析者建议。

顶部保留项目名称和保存状态，业务导航用“活动策划、场地布置、执行安排、方案评审”。右侧独立控制 Binggo 的展开与收起。场地页内部再切换二维、三维与客户观察角度。

```text
幕景  当前项目       活动策划  场地布置  执行安排  方案评审      Binggo
──────────────────────────────────────────────────────────────────
按当前业务显示内容                               │ 对话与修改提案
                                               │
策划：需求、预算边界、待确认事项                   │ 当前操作对象
场地：素材/图层 │ 二维或三维画布 │ 选中物料属性     │ 历史对话
执行：任务、人员、物料交接、时间                   │ 提案与待核对结果
评审：固定版本、画面、说明、人工反馈               │ 输入框
                                               │ 可单独收起
──────────────────────────────────────────────────────────────────
```

这是一套逐步实施的目标布局，不代表四个业务页已经全部完成。第一步在现有展开工作区内分开表单与聊天，复用现有状态和数据；之后再把业务入口从助手容器中移到项目主导航。避免同时改导航、保存格式和后端契约，让问题难以定位。

### 草图标签的含义仍待讨论

“场景策划、建模、营销、交付、美术、办公室”目前是讨论中的标签，可能表达助手分工、工具能力或工作区。用户明确其中有些不一定执行，不能直接把六项变成开发清单，也不能据当前实现擅自删去未来方向。下面仅保留一种待讨论的组织方式。

| 草图概念 | 建议位置 |
|---|---|
| 场景策划 | 活动策划与场地布置之间的连续工作 |
| 建模 | 场地布置中的物料工具，处理具体物件 |
| 营销 | 活动策划中的传播任务；以后有独立内容产出流程再展开 |
| 交付 | 执行安排及方案评审，区分交给客户与交给执行方 |
| 美术 | 素材与视觉资料，关联布局中的实际物件 |
| 办公室 | 当前含义未定，先不增加空入口 |

右上角模式切换适合专业工具切换；高频业务入口应直接可见。二维、三维只是同一场地的视图，切换不能改变项目、需求或人员安排。

## 场地资料要真正落在画布上

建议将“原始资料”和“设计布置”分为两个图层。参考底图默认锁定，提供显示、透明度、重新对齐；物料放在其上方。隐藏底图只改变显示，不能删除资料、移动物料或改变墙体。

建议界面明确显示未标定、估计参考或用户提供的测量依据；这是拟议的展示方式。现有尺寸状态为识别、推断和已确认，测量来源与确认状态应分别说明。录音中的12.65米、约20米和吊顶高度没有与明确图纸、端点、楼层绑定，本次不会直接填进用户项目。两点标定要保留所选端点、输入长度和单位；斜拍照片需要另行校正，不能把透视照片当正投影平面图直接量距离。

当前代码已有旧底图字段、二维/部分三维绘制和重建标定能力，但不能据此声称“底图闭环已完成”。旧底图存在与否还参与墙体构建判断，因此隐藏操作不能简单清空图片字段。重建资料里的图像也不等于已经在主三维画布上对齐显示。下一项应把这条链路单独补齐并验收。

采用的是成熟工具中“导入参考图、调整位置与尺度、在参考上设计”的做法；幕景补上与当前场地和任务的联系。[SketchUp 官方图像与描图说明](https://help.sketchup.com/en/sketchup/importing-and-using-2d-images)

## 用同一份任务连接预算和人员

草图中的动态待办应沿用当前活动任务数据。准备、布场、活动、撤场是阶段；待办、进行中、待验收、已完成是状态；重要与紧急是排序视角。三者独立，四象限不另外复制一套待办，也不根据靠近截止就认定任务重要。

预算先明确客户的支出上限、希望控制的范围和不可削减项。供应方报价、内部估算、已确认费用和实际支付分别记录；未知金额为空。现有物料演示价格与 AI 调用费用不算活动预算。

人员安排应能回答：哪个岗位、需要几人、由谁或哪支外包团队承担、何时到场和离场、负责哪些任务、如何交接、成本依据是什么。首版按单场活动维护，暂不建设跨公司的人员管理系统。负责人和承接团队已有字段可复用；岗位需求、人员来源、到离场时间及费用关联需要明确的后续数据契约。

草图里的三种人员方案建议改为“精简、标准、加强”，比较岗位覆盖、预估成本、服务范围和已知风险。方案只有人工确认采用后才影响正式排班。AI 可以提建议，不能把建议人数当成已招聘到位。

项目简报与项目角色集中展示、任务另有执行位置，是可参考的成熟组织方式。[Asana 项目总览说明](https://help.asana.com/s/article/project-overview-tab)

## 客户评审与内部执行各看什么

客户版优先显示目标、布局画面、为什么这样安排、可选方案差异和待确认项。内部版显示物料、责任人、外包交接、时间、验收要求、变更和费用依据。两者引用同一方案版本，但有不同的资料范围。

已有客户评审文件模块和三页演练 PDF可以复用；工作台内的评审入口、真实三维画面捕获、人工意见记录仍待接入。点击“应用布局”只代表编辑者采用，不能自动记录为客户已确认。

所有示例继续标注演练。团队飞书保持共享协作资料，个人桌面工作台保持私人安排；不会把个人待办或自媒体草稿混进客户交付。

## 技术选择

当前 Next.js、React、Three.js 和 Supabase 契约能承接这次界面重组。优先复用现有场景、需求、任务和保存路径，没有必要为了分列聊天切换后端。

Cloudflare 是后续部署候选。当前前端使用静态导出，官方提供对应的 Pages 部署路径；数据库、模型文件、生成任务和权限仍需单独核验，静态页面托管不等于整套后端迁移。[Cloudflare 静态 Next.js 说明](https://developers.cloudflare.com/pages/framework-guides/nextjs/deploy-a-static-nextjs-site/)

录音里“一账号只能部署一个站点、仓库名必须和用户名一致”需要区分：GitHub Pages 的用户站点和项目站点规则不同，项目站点是每仓库最多一个。这个说法不能作为必须迁移的理由。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

Rhino 与 Blender 暂作为制作工具试用。用同一件实际物料比较尺寸、坐标、材质、导入效果和后续修改成本，再决定保留哪些工作流。

## 小步实施和验收

| 顺序 | 本轮或后续工作 | 验收标准 |
|---|---|---|
| 本轮 | 展开工作区的业务内容与聊天分列 | 独立滚动、可收起；输入不丢；候选与错误可发现；手机宽度可操作 |
| 下一步 | 参考底图与尺寸依据 | 显隐不改变墙体/物料；二维三维对齐；保存恢复后保留；估计尺度明确标识 |
| 随后 | 项目主导航和客户评审入口 | 不依赖聊天找到需求/任务；同版本画面与文字可核对、导出 |
| 随后 | 人员和预算关联 | 岗位、外包、时间和费用能关联任务；计划与实际独立；未知值不冒充零 |
| 实际活动后 | 变更、满意度和复盘 | 记录真实目标达成、客户/观众反馈、经营结果与下次改进 |

不以按钮数量衡量完成。最终需要你们用一场明确标识的演练或真实活动，从需求到场地、分工、交付和复盘走通，并根据实际试用判断是否满意。

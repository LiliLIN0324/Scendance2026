# 本地执行与恢复链路核查

2026-10-07。只读核对当前前端源码，并用实际模块和独立合成演练验证；前端仍由其负责人修改。新检查脚本位于 [check-local-delivery-loop.mjs](../../scripts/check-local-delivery-loop.mjs)，仓库根执行 `node --no-warnings scripts/check-local-delivery-loop.mjs`。当前Node v26.2.0及既有TypeScript完成内存加载，不修改源文件或包配置；所有存储是注入的Map，网络调用被阻止并核计数，未触碰用户草稿、真实模型或账号。

## 直接验证的范围

使用两个相同规格、不同ID及负责人、独立核对依据的椅子，配合现有30人演练的6任务/4阶段。计划是明确的合成测试日期，实际时间保持null；模拟完成说明不能当真实验收。连续验证保存→重开→编辑备份→交付/分享→规格变更/断链/写入失败，而不是仅查看字段存在。

| 检查 | 实际结果 |
| --- | --- |
| 本地保存重开 | 当前几何、6任务、时间、工单和两种核对依据保留；按实际JSON表示比较，JSON正常将-0存为0 |
| 编辑备份往返 | CreativeBrief原文、scope、活动安排、工单及摘要保留；核对仍有效，未知实际时间仍为null |
| 交付JSON | 同一交付编号，任务6行、执行2行、采购1行数量2；保留演练类型及有效状态，剥离内部reviewedBasis；恢复模块明确拒绝把交付封套当备份 |
| 公共分享 | 活动安排、负责人、工单/证据移除，原输入未被修改 |
| 云准备边界 | 本地执行资料触发拒绝，保留本地草稿 |
| 单实例改尺寸 | 被改物件及关联任务需复核，另一件仍有效；采购由1类拆为2类 |
| 删除后同名新物料 | 原ID继续作为缺失关联，任务需复核；活动CSV包含缺失ID、演练来源和当前交付编号 |
| 存储写入失败 | saveLayout报告失败，原存储仍能重开且内容不变 |

该脚本不验证DOM、按钮、浏览器localStorage/IndexedDB的真实权限、下载完成、GLB资产授权或客户满意；不能将8项函数链路通过称为完整界面恢复已经完成。源码搜索当前仍只有同名测试引用local-project-backup API，已有界面仍用普通布局JSON导入/导出。

## 最小接入检查项

1. 前端在真实备份入口取得当前作用域已完成读取/保存的需求快照，再使用唯一文件模块；loading/saving/error时阻止导出，保持原错误状态。导入完整验证后展示覆盖范围，用户确认后才应用；交付JSON继续明确拒绝，不尝试补造核对依据。
2. 恢复要同时处理布局与`${layout.id ?? 'local'}:brief`，并保护此前数据。当前CreativeBrief Provider按scope/loadAttempt读取；同ID仅applyLayout不会重新载入，ready状态的retryBrief会保存当前表单。接入口须明确重载/重新挂载Provider，并停止旧debounce回写，不能用旧表单覆盖恢复值。失败时布局与需求都回到此前有效版本，保留待恢复文件和可重试状态。
3. 独立浏览器验收同ID/新ID恢复、brief present/absent、需求读取失败/写入失败、布局保存失败和恢复中切项目；回读需求、两把椅子的工单及6任务，确认当前有效状态与文件一致。只有这些真实入口通过，才关闭E2/E7/E9的界面恢复缺口。

这些是尚未接入部分的验收条件，不将未来事务风险冒充已发生的用户数据损失。无须修改冻结EventOperations或新增云schema。继续使用 [备份负责人方案](local-project-backup.md)、[共享契约E1–E9](event-operations-contract.md)和原CreativeBrief真源。

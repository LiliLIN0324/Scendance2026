# 幕景的报价、合同与履约流程

2026-10-09。来源是用户新增要求“是不是应该加入什么合同一类的，毕竟是全流程承办”，以及已授权产品计划中的报价、收付款与业务变更。下文为设计及待实施范围，不宣称已开发、真实签署或款项已发生；不将本次新增要求归因于录音。

## 产品位置

将商务约定放在当前项目的“商务与合同”资料入口，与方案、执行资料相互关联；不是聊天助手的新模式。项目从客户需求、方案报价、委托确认到供应采购、执行、变更、验收及结算，应能沿同一项目查看依据。团队实际承办可以覆盖这些环节，不强迫每个轻量活动都填写完整流程。

对外客户委托与对内供应商／外包约定分别管理：客户向我们购买的范围，不等于每个供应方承接的范围。两者可关联相同的任务、物料和里程碑，但不能按名称自动合并。

## 成熟产品参考与取舍

- [Rentman：创建报价或合同](https://support.rentman.io/hc/en-us/articles/360012594659-Create-a-Quotation-or-a-Contract)：基于项目设备、人员与运输计划生成文档，保留旧文档并创建新版本。幕景借鉴项目关联和版本冻结；现有人工估算并非报价，必须由用户明确编制和核对报价内容，不能照搬自动取价。
- [HoneyBook：创建及分享合同](https://help.honeybook.com/en/articles/5192723-create-and-share-a-contract-in-honeybook)：同一项目文件可组合合同和账单，并引用服务及付款摘要。幕景借鉴关联服务范围与收付款节点，第一阶段先做记录与文件管理；签署与实际收款不能用界面按钮或系统推断替代。

以上为产品工作流参考，不证明这些海外产品的合同模板或签署服务适用于我们具体业务。

## 应覆盖的内容

| 环节 | 项目里应能保留的记录 | 与现有功能的关系 |
| --- | --- | --- |
| 方案与报价 | 交付范围、明确不含的事项、正式报价行、计价依据、币种、税费口径、报价版本及待确认项 | 显式选择方案版本、任务或取得计划；内部预算与估算独立保留 |
| 客户委托 | 对方与我方主体、负责人、活动时地、约定范围、合同编号与版本、原文件、签署记录及依据 | 指向双方对应的方案／报价版本；内部制作人员完成自检不算客户确认 |
| 供应及外包 | 服务／租赁／制作范围、数量单位、规格、进撤场要求、验收条件、负责方及约定文件 | 关联原任务／物料取得行／人员岗位；不会把模型实例数当实物约定量 |
| 业务变更 | 提出人、原因、原范围与新范围、时间／费用影响、处理决定、确认依据及附件 | 待确认变更与已确认约定分开；变更不直接覆盖原合同或悄悄改变已承诺范围 |
| 验收及结算 | 分阶段交付依据、客户／供应方核对结果、应收应付计划、实际收付记录及凭据、开票记录 | 任务完成、数量点验、客户验收、收付款分别记录；归还齐全不自动等于质量合格或合同结清 |

示例仅作演练：客户在已确认版本后要求增加10把椅子。系统先记变更请求与待确认金额、日期影响；经人工录入确认依据后，明确关联新报价／补充约定和需更新的任务、供应取得及时间表。不能因画布复制10把椅子就认定客户同意加价或供应商已接单。

## 第一可用切片

先让我们能管理一场承办项目的真实约定，使用已有且经团队核对的合同文件或模板。

1. 项目内建立“客户委托／供应外包”约定记录，显式关联原项目、任务或取得记录；附原文件及版本、负责人和范围摘要。
2. 保留准备中、待对方确认等工作状态；另行记录人工报告的签署事实与原件依据。导入签字图片或点击“已签署”不能被界面描述成平台电子签验证。
3. 收付款节点记录方向、约定金额及币种、到期日或触发条件；未知保持未知。首款、阶段款、尾款是可改的业务标签，不默认统一比例。
4. 约定、原附件、草稿、节点和关联可保存、刷新找回、可检查导出／恢复。旧合同与旧报价冻结，新变更保留来源和决定。
5. 显示“哪些仍待确认／下一节点是什么／依据在哪”。AI可以整理要点和提出任务候选，用户核对后应用；不能代替签署、付款或对外发送。

导演设计审查补充：普通草稿可编辑保存，不要求每次修改都产生不可变版本。用户明确固定某一版本后，原件与范围才冻结；签署报告只关联具体固定版本并独立留痕。首期采用明确选择的CNY、PDF/PNG/JPEG原字节，初始容量限制为每文件10MiB／每项目32MiB；独立商务包先承接迁移，正式整项目覆盖另行实现。以上为实施边界，当前仍未开发。

后续切片补结构化正式报价、变更确认、实际收付与结算核对，并在需要时接成熟电子签服务。第一版若只完成台账，不得宣称全流程财务或签约能力完成。

## 存储、权限与迁移必须先定的边界

- 现有productionPlan是可编辑计划，合同、签署与实际收付事实不直接塞进几何布局或设计快照。撤销摆位、切换设计、新建活动不能撤销真实业务事实或复制出新项目的已签／已付款状态。
- 复用项目身份和既有独立记录模式，公共契约保持唯一来源。客户、供应、内部文档不同披露范围；客户评审不默认带外包成本、联系人、合同附件或内部毛利。
- 文档链接不等于附件已备份。必须分别说明原文件是否实际携带、只保留链接或读取失败；恢复对同编号不同版本、旧文件缺该领域、关联缺失保留诊断，不覆盖成空记录。
- 预算、报价、约定金额、实际费用、应收应付与实收实付不互相替代。未知、零、退款／更正要有明确语义；不用简单撤销删除实际资金事实。
- 本机和正式云状态分开。未做权限/双账号测试前，不能把存在浏览器的合同记录说成团队已可共享。
- 本地活动商务资料随浏览器来源及本地活动编号识别，不因登录或AI项目绑定自动迁移。首期不宣称账户级隔离；正式云项目的商务读写入口须另有权限与身份设计，不能只碰巧同编号就展示本机资料。

## 验收演练

在现有30人假设活动中，增加一份客户委托草稿、一份租赁约定草稿及分阶段收付款计划，全部显式演练且实际签署／付款未知。验证刷新找回、来源文件与版本、任务关联、跨项目隔离、备份恢复和历史保留。

追加10把椅子的请求应保持待确认，不改变旧约定金额与实收实付；尺寸或任务变更触发核对提示，不替代业务确认。切换设计/撤销布局不得改变签署或实际收付款记录。客户导出检查不泄露内部供应成本与合同附件。

## 实施顺序

当前评审库与执行时间表先完成整合验收，不中途扩写。后端对话先只读提出约定及收付款的公共模型、与计划／事实的边界、附件／备份策略和验收；导演结合前端实际入口审核，再按有界切片交实施。不会为此创建定时任务、自动签署或自动对外联系。

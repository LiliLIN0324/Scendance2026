## 一、结论（6 行）

1. 原文最硬的不是功能清单，是两条纪律：「绝不虚构确认结果、人数、价格或嘉宾的饮食需求」和「这些文件才是记录，聊天记录不是」。前者我们已有机制（事实状态+来源+修订、提案→确认→回执），后者只做了一半：没有任何一处"回答状态前先重读记录"的硬约束。
2. **执行记录这一侧确实过半**：任务（负责人/阶段/计划与实际时间/关联物件/证据/核对依据）、商务约定（草稿/固定版本/附件/付款计划/签署报告）、场地事实、物料唯一计数点都已落地；但**可直接用的当天产品面接近零**——`event` 只是四个阶段枚举之一，没有任何"钟点化"的写入保证。
3. **真正的策略缺口是入口，不是字段**：原文承诺「一旦用户交出文档…立刻停止提问并开始干活」「一份真正的流程单，永远比再问一个问题更重要」。补齐它不需要新造链路——提案→勾选→接受→幂等回执已经存在。
4. **三处照摘要判断错了**：嘉宾状态是 6 态 + 退出旗标（不是 7 态）；原文要的是"报名对照**预期到场**"，不只对照目标；当天简报要"供应商到达时间，每行带电话"，而档案的 `party` 只有姓名与备注。
5. **只陈述证据，不推导状态**：文档存在性只能证明"档案里有这份文件"，不能证明"对方已签约/已付定金"。状态一律由人声明并留痕。
6. **排期**：P0 契约 + P0-5 聚合 → P1-0 起草 → P1 视图与当天包 → P2 名册/供应商/复盘/体检/档案包 → P3 定时/回执同步/出行酒店。

### 2.2 可以直接复用的现有机制

- **事实标注**：`venue-facts` 的 `status: confirmed/pending/inferred/unknown` + `source` + 每事实 `revision`；新对象（元信息、名册、声明状态、复盘数字）照此办理，未知就是 `unknown`。
- **提案→确认→回执**：`activity-task-suggestions` 已有逐条勾选、接受回执、幂等与失效校验、人工改动不被重放覆盖。**P1-0 直接复用它，不新造**。
- **草稿/固定版本分离**：商务档案 `draft` 与 `versions`（`commercial-dossier-contract.ts:81-94`），复用到名册与复盘。
- **人数口径**：`user-attendance` 只解析原始用户文本，区间/冲突/约数转 `unknown`；名册统计沿用，禁止按椅子数倒推。
- **唯一计数点**：物料走 `deliverable-inventory`，复盘口径必须读同一投影。
- **状态与证据分离**：档案产出证据条目（文件/版本/节点/报告，各带记录时间），不产出业务状态；状态只能是 `user_statement` 且带声明人与时间。
- **交付链路**：效果图册、图纸、CSV、交接/执行时间表 HTML、评审回执已有出口；新产物接同一导出面板与命名规则。

## 四、明确不做（产品边界）

- **不替用户对外行动**：不发邀请/提醒/邮件/IM，不预订、不付款；对外内容只起草，经人工确认，且草稿只能引用已确认事实。
- **不编造事实**：供应商、库存、价格、饮食、人数、确认状态，依据不全就标 `unknown/pending`，估算必须标注。
- **不把文档存在性当业务状态**：有报价文件 ≠ 已报价有效，有固定版本 ≠ 已签约，有付款计划 ≠ 已付定金，有人工报告 ≠ 合同生效。
- **不用对话摘要回答状态**：状态一律从当前记录重算并带 `asOf`；聊天记录不是记录。
- **不做报价与比价**：预算只录用户给出的估算与实际；客户版不出现价格、预算、分工与采购状态。
- **不夸大空间校验**：流程单/清单不包装成消防、承重或完整施工验收；3DGS 只提供观感。
- **不做出行表**：当天包只回答"谁从外地来、谁去接"（`needsTravel`），航班与房块留 P3-3。

## 五、执行纪律（沿用既有偏好）

1. **分支本地攒**：改动在分支/本地完成，`tsc` + Vitest + 真机验收通过后再一次性推 main。
2. **先契约后 UI**：P0/P0-5 先落契约、纯函数与测试；P1/P2 再逐组件做卡片。
3. **复用事实源**：任务挂 `eventOperations`、商务读 `commercialDossier`、人数走 `user-attendance`、物料走 `deliverable-inventory`。
4. **版本与兼容**：进入共享契约的字段先定 `schemaVersion` 策略；"旧端整套拒绝"写进验收，不静默加字段。
5. **彩排与真实分离**：流程单、当天包、复盘必须带 `dataKind`，`rehearsal` 与 `real` 不混排不混算。
6. **退出者不打扰**：`optedOut` 永久保留、导出可见，但不进计数、提醒、体检、跟进。
7. **客户产物白名单制**：默认不导出、逐字段放行；禁止 spread 后 delete。
8. **内部词不外泄**：当天包、复盘、名册、档案包全部过现有禁词表（`frontend/lib/project-review.test.ts:348`），并补 `eventProfile`、`plusOnes`、`dataKind` 等新词。
9. **测试落点**：契约与纯函数进 `lib/*.test.ts`；面板交互进 `*.react.test.tsx`；用例只加不减。

## 六、已定口径（九条）

1. **名册携伴**：不建二级宾客对象，`plusOnes: number | null`；`null`=未问、`0`=明确无；出席数含携伴；`null` 进待确认。原文把「未具名的携伴」列为临期缺口，与此一致。
2. **供应商六态**：值可全用，但**不由档案推导**；证据只陈述"档案里有什么"，状态只接受人工声明（带声明人与时间）；未声明显示"未声明"。
3. **复盘快照**：挂执行基线指纹（`publishedPackageId` + `reviewedBasis` sha256 + `eventProfileRevision`），不挂最新发布版；未发布则 null 并明示。
4. **当天执行包上移 P1**：不需要后端，是 P0/P1 的兑现点；需要后端的只有定时触发。
5. **`eventProfile` 只做本地侧车**：不进 `sitePlanDataSchema`、不进云端场景、不进分享；客户版只走 P0-4 白名单。
6. **嘉宾「已退出」是旗标不是状态**：6 态枚举 + `optedOut`，保留前序状态；导出带标记不过滤。
7. **预期到场单独记**：`expectedAttendance` 是用户声明的事实，与目标人数（`brief.guests`）、报名数、实际出席四者并列，任何两者都不互相推导。
8. **时长算不存但必显**：由起止时间计算；缺任一端该行"不完整"，进不了 `review`；具名负责人不可用承接团队顶替。
9. **活动档案包按活动名+日期命名**：缺项不占位、不出空文件；索引带各对象版本。

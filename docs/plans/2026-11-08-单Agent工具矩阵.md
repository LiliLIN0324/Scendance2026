# 幕景单 Agent 与工具矩阵

状态：工作区设计与事实盘点，2026-11-08。产品中只有一个**活动 Agent**；Bingo、空间、物料是用户工作区与能力入口，不各自代表一个自主 Agent。开发时可由多个协作者并行实现和审查，不改变产品结构。

## 工作方式

用户表达目标 → 活动 Agent 读取当前状态并选择工具 → 工具回报事实、失败或未知 → 系统检查候选 → 用户查看差异并决定是否应用 → 修改后重查与交接。Agent 的自然语言解释应以可观察的工具结果为依据；模型输出、工具成功返回、候选满足要求和现场确认是不同事实。

## 当前工具矩阵

“声明”指工作区 runner 中存在工具，不代表已上线；“真实”仅指隔离 MiniMax 试用中曾观察到该工具被调用，不代表它总是成功或现场可用。地点搜索默认关闭。最新工作区已移除 MiniMax 的专属工具限制，模型与其他供应商共用配置和权限门槛；新增开放的建模、材质与 Aholo 路径只经过模拟，尚未完成真实服务验证。

| 任务 | 当前工具 | 当前证据与边界 | 下一步 |
| --- | --- | --- | --- |
| 观察场地 | `get_scene`、`inspect_zone` | 场景是当前数字快照；真实 MiniMax 曾查看局部 | 同步展示来源、版本和缺失项；模型按需取局部 |
| 寻找位置 | `find_free_areas` | 真实 MiniMax 曾调用；只给几何候选，不能证明连续通行 | 将结果与门、固定障碍及明确要求连接，再由独立检查复核 |
| 查数字模型 | `search_resources`、`inspect_materials` | 查模型/标称材质，不代表真实库存或实物属性 | 对型号、尺寸、授权和来源做明确展示 |
| 统计场景 | `get_bom` | 统计数字物件，不证明库存、价格或可预订 | 关联候选版本和实际资源清单，标明未知 |
| 组团排布 | `prepare_seating_candidate`、`prepare_shared_seating_candidate` | 一人一桌、两人一桌；真实 MiniMax 曾调用双人桌；容量、配套与安全仍需复核 | 逐步形成可配置组团能力；先把明确人数、门洞与修改后配对核验跑通 |
| 校验候选 | `validate_candidate` | 当前覆盖部分几何及命令，真实 MiniMax 曾调用；`valid` 不等于消防/疏散/无障碍通过 | 更清楚列覆盖项、未知项和可修复冲突；与最终应用复核保持一致 |
| 提交候选 | `submit_candidates` | 真实 MiniMax 曾返回预览；不等于已经应用或场地方确认 | 绑定当前需求版本、旧物差异和后续修改，支持清楚的无解结果 |
| 查询地点 | `search_places` | 默认关闭、需配置；地点搜索不证明可租、档期、容量或室内平面 | 先验证真实供应商能力与结果来源，再考虑扩展搜索 |
| 创建数字模型 | `create_parametric_model`、`customize_material` | 可能写入资源；MiniMax 工作区代码已开放，尚未真实验证 | 作为按需能力，明确费用、副作用与资源归属 |
| 生成三维模型 | `start_lux3d_model` | 配置就绪时可用、可能收费、异步；MiniMax 路径尚未真实验证 | 保留可选，不把生成模型当实物库存或已放入场景 |

## 尚缺的能力

1. **真实场地事实**：图纸、照片、比例、出入口和确认人关联到版本；不把模型猜测或模拟场地升级为现场事实。
2. **真实资源**：按活动日期查规格、数量、价格、可用性和替代品；口述与数字模型只可标待核验。
3. **可靠修改**：明确保留原物、锁定对象和新增要求；候选在修改后重算桌椅关联、几何和未完成需求。
4. **流程与交付**：队列、入场和撤场的可解释假设；给具体版本的交付包、审校意见及修改追踪。
5. **可观测与评估**：工具发起/结果/未知的有界记录、阶段耗时、失败原因；同一案例在模拟和真实模型中分别记录，不能拿示例通过率冒充产品成功率。

## 工具设计与取舍

- 工具按用户任务组织，不因为工具多就拆成多个产品 Agent。读取类可按需并行；共享状态写入、候选提交与计费动作需明确顺序和归属。
- 输入须有明确单位、身份、版本和约束；输出区分事实来源、成功/失败/未知及下一步。工具返回成功不等于整个活动完成。
- 保留粗细不同的场景查看工具；将同类座席工具作为未来可配置组团设计的候选，而非现在未经回归直接合并。
- 工具事件只展示真实回执和可解释结论，不输出模型内部推理、原始参数或密钥；当前新事件表/RPC 未部署，记录仍可能不完整。
- 不直接开放任意代码执行作为摆场工具；先完善有限、可核验的空间操作。真实资源写入或付费调用应有清楚的授权与结果状态。

## 成熟案例与适用范围

- [Cvent Event Diagramming](https://www.cvent.com/en/supplier-venue/event-diagramming-software)：厂商介绍按比例场地、物料目录、协作和 3D 预览。适合学习场地数据与执行协作；公开介绍不是对任意场景自动成功率的独立证明。
- [OpenMausBot 运行事件](https://github.com/milind-soni/OpenMausBot/blob/main/shared/runtime-events.ts)：区分操作发起、返回和运行终态；可借鉴事件语义与重连设计。它不是可直接替换幕景空间引擎的组件；直接复用源码需核授权。
- [Deep Agents](https://github.com/langchain-ai/docs/blob/main/src/oss/deepagents/overview.mdx)：将模型、工具与运行机制分开，提供状态和工具编排思路；这里不因此引入多 Agent 或新依赖。

## 优先顺序

先完成一个固定模拟活动的真实模型端到端验收：需求事实 → 场地和物料来源 → 组团候选 → 独立检查 → 用户审阅 → 修改后重查 → 明确版本的交接。随后按实际失败数据改工具输入、反馈和耗时，再扩展场地、库存与模型供应商。现场可执行性最终需要真实场地方和执行人员验证。

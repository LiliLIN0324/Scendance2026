## 产品结构

产品里只有一个活动 Agent。用户左侧四部分对应四扇门，不是四个 Agent：

| 用户看到的 | 本轮矩阵里的入口 | 是否另有一个 Agent |
| --- | --- | --- |
| 活动 | 活动 Agent | 是，仅此一个 |
| Bingo / 审校 | 审校协作 | 否 |
| 空间 | 空间 | 否 |
| 物料 | 物料 | 否 |

快捷键和按钮可以调用与 Agent 相同的底层命令、校验和撤销。它们不是模型工具清单。打开物料库、打开空间、打开审校、撤销、确认预览，都不能被模型当成工具名调用。导入 GLB 也不是模型工具。

## 当前 main 的工具

工具名以 `supabase/functions/_shared/agent-runner.ts` 的 `schemas` 为准。测试会读取这份源码并和矩阵对照。下表的「声明」只表示代码里有这个工具。

| 用户要做的事 | 入口 | 模型工具 | 不是模型工具 | 边界 |
| --- | --- | --- | --- | --- |
| 从模糊想法接着做 | 活动 Agent | 无 | 无 | 先留原话和未知项，不先填完专业表单 |
| 看数字场地 | 空间 | `get_scene`、`inspect_zone` | 打开空间 | 本次数字快照，不是实测，空标注不等于现场没门 |
| 找可放的位置 | 空间 | `find_free_areas` | 手动拖拽仍应走共享命令 | 几何候选，不证明连续通行 |
| 查数字模型 | 物料 | `search_resources`、`inspect_materials` | 打开物料库 | 名录和标称尺寸不是库存、价格或档期 |
| 统计场景物件 | 物料 | `get_bom` | 无 | 数字物件计数 |
| 试排座位 | 活动 Agent | `prepare_seating_candidate`、`prepare_shared_seating_candidate` | 无 | 一人一桌和每桌两人分开。讲座不自动变成课桌式 |
| 检查候选 | 审校协作 | `validate_candidate` | 打开审校 | `valid` 不是消防、疏散或无障碍通过 |
| 交出预览 | 活动 Agent | `submit_candidates` | 确认、撤销 | 预览不是已应用 |
| 查地点 | 空间 | `search_places` | 无 | 默认关，要 `AGENT_PLACE_SEARCH_ENABLED` 和 Key。不能证明可租或平面 |
| 做新模型 | 物料 | `create_parametric_model`、`customize_material`、`start_lux3d_model` | 导入 | 见下表 |

物料四条路径的能力和耗时不同，结果都不是实物：

| 路径 | 模型工具 | 写入 | 耗时与可用性 |
| --- | --- | --- | --- |
| 物料库 | `search_resources` | 否 | 只读。有授权目录才查得到 |
| 参数化 | `create_parametric_model` | 会创建资源 | 只有桌、椅凳、柜台、台座、背景板、柜 |
| 导入 | 无 | 用户文件 | 耗时看文件，不进模型工具表 |
| Aholo | `start_lux3d_model` | 会提交任务 | 配置齐全才出现；异步，大约数分钟，可能收费。默认不在基础工具列表 |

`search_places` 和 `start_lux3d_model` 在本案例里一律视为未打开。案例不会发真实检索或生成请求。

## 必须保住的反例

- 「80 把椅子」是口述物料。它不是 80 个人，也不是已经核过的可用库存。
- 「长者」只是受众。没有用户明说轮椅、助行器或腿脚不便时，行动辅助保持未知。
- 「建议」「先看看」「先不要确认」不是已确认事实。试排结果不能因为偏好就被说成已经定了。
- 「座位形式先别定」之后，未知项还在，案例也不会反复要求马上选定。
- 「改成 28 人，把签到桌往左移 1 米，并出一份物料清单」要同时留下改人数、移动和清单。后半句的「清单」不能吃掉前半句。两张签到桌时，移动保持未解析，人数和清单仍然处理。
- 对话建议 v2 的旧固定对抗集是 7 项里 6 项失败。当前 main 没有这套评测。默认关闭。本案例即使收到「已经复现通过」的参数，也没有产品开关可以打开。先在当前 main 上复现，再单独讨论能不能上线。不能用「建议」标签把事实幻觉放过去。

## 纵向案例

证据级别：确定性合成测试。不是真实模型，不是浏览器，不是场地方，不是生产。

原话按这个顺序：

1. 你好，我想办一场社区讲座，来的多是长者，资料还没齐。
2. 我们有 80 把椅子，大概 30 个人来，座位形式先别定。
3. 场地还没量。先按 12×9 米假设看看可能怎么摆，这只是建议。
4. 那就按这个建议预览一人一桌，先不要确认。
5. 改成 28 人，把签到桌往左移 1 米，并出一份物料清单。
6. 座位还是先别确认，刚才那个只是建议。

案例里实际发生的事：

1. 读到讲座和长者。行动辅助、人数、场地、出入口、座位形式都未知。不调用试排。
2. 读到大约 30 人和口述 80 把椅子。内置名录可以查到「椅子」这个数字物料，回执写明这不是那 80 把椅子。模型句子「预计将有 80 位长者参加」会被丢掉。
3. 12×9 米记为假设，不是实测。因为用户还没选课桌，仍然不调用 `prepare_seating_candidate`。
4. 负面对照先用 80 当人数，校验拒绝。然后用大约 30 调用当前 main 的 `planDeskChairGroups`，桌椅尺寸用内置名录标称值，间距是假设。普通场景有物件上限，所以请求 30 会留下缺口。人数保持大约 30，不改成放下的数量。接着调用当前 main 的 `findFreeAreas` 看还有没有几何空位。空位只是候选，不写进场景，也不把缺口说成已经补上。工具回执、缺口核验和偏好分条记录。座位预览走共享通道仍因缺口不能确认；走旁路直接拒绝。
5. 人数改为用户说出的 28。旧试排过期，仍然不能确认。物料清单统计的是预览里的数字椅子，和 80、28 都不是同一个数。虚构物件编号会被拒绝。越界坐标会被拒绝。Agent、快捷键、按钮对执行、确认、撤销各试一次旁路，共 9 次，草稿都不变。快捷键先按当前修订号把签到桌左移 1 米；Agent 拿移动前算好的同一条命令再提交，会因修订号过期被拒绝，于是重新读取，不再多移一米。确认按钮走旁路也不会把预览变成已应用。之后按钮确认、撤销能回到原位，再由共享通道重做一次。锁定立柱不动。案例把「左」记为 x 减少 1 米，这只是案例坐标，不是现场方位。把 80 把椅子写成人数、把建议写成事实、或打开 v2 标签，共享通道和旁路都不接受。
6. 用户再次说先别确认。座位仍是建议，未知项还在，案例不追加追问。

回读时同时看得到：28 人尚未核定、80 把椅子仍未核验、数字椅子是另一份计数、空位候选没有补上缺口、场地仍是假设、行动辅助和出入口仍未知、座位预览没有应用、只有签到桌的移动被确认。v2 即使带着「已经复现通过」的参数，返回值仍是关闭。

# 正式站闭环验收清单

基准是已部署的 `main` `a6143abc`（Cloudflare 部署 `c641ce56`）。本文只规定怎么验收、以及当前代码里还会让闭环失败的位置。它不是修复完成证明。

做完的唯一标准：在正式页完成 **新建活动 → 保存 → 输入需求 → 看到真实模型回复**。保护性拒绝、单测通过、构建通过，都不能代替这一条。

## 构建成功 ≠ 页面闭环

- `next build`、类型检查、函数部署成功，只说明这包代码能编出来。
- `NEXT_PUBLIC_AGENT_ENABLED`、`NEXT_PUBLIC_CONVERSATION_API_ENABLED`、`NEXT_PUBLIC_BRIEF_CONVERSATION_ENABLED` 在**构建时**写进前端。`frontend/.env.example` 里三项都是 `0`。仓库里没有生产构建记录能证明线上包已经是 `1`。
- 未登录 `POST` 得到本服务 `401 UNAUTHENTICATED`，以及 `OPTIONS` 得到 `204`，只证明路由和未登录保护。不能当作登录后的模型成功。
- 直接打百炼成功，不能代替页面上的 `conversation-api` 请求成功。
- 本机规则仍可能抽出人数、室内、尺寸。出现「请选择圆桌或课桌椅」或「智能理解暂不可用」时，这条闭环失败。

## 新建活动

验收时 `localRestoreAvailable()` 必须仍是 `false`。不要用 mock 把它改成 `true` 来宣称通过。

- [ ] 新建前先把当前活动归档，再读回这份归档：名称、编号、布置还在。
- [ ] 新活动使用新的、未被占用的 scope，不覆盖原活动，也不带入原需求、任务、制作计划、方案历史或点验账册。
- [ ] 保存后刷新页面，读到的是新活动，不是回到旧画布。
- [ ] 当前活动保存失败、存储满、或新活动写入失败时，原活动仍在，页面不切到半份新活动。
- [ ] 表单「新建活动」和画廊「新建活动 / 创建并打开」两条入口都要测。现在两条都进 `switchActivity` → `begin()`。
- [ ] 打开已有归档、从文件恢复、撤销恢复，仍然被暂停挡住，并有明确提示。不能为了解锁新建而打开任意覆盖恢复。
- [ ] 跨标签租约仍拒绝过期写入。本清单不要求重做恢复事务。

## 智能理解

样例：「80人发布会，室内12×9，安排签到和主舞台」。必须是已登录的正式页会话。

- [ ] 登录会话有效。退出、切账号或会话过期后，请求应明确失败，不能串到另一个账号。
- [ ] 实际请求 URL 是同一 Supabase 项目的 `/functions/v1/conversation-api/brief/extract`，不是 `scene-api`。核对方法、预检来源和状态码，不要只看按钮文案。
- [ ] 记录 HTTP 状态和响应合同：`enabled`、`reply`、`extraction`、`reason`。非 JSON、空正文或合同解析失败要留下状态码，不能只剩一句笼统提示。
- [ ] 页面上的回复来自这次模型响应。本地规则兜底、或只改提示文案，不算通过。
- [ ] 人数 80、室内、12×9 与签到/主舞台的处理要能对上用户原话。模型多写的布置建议不能被当成已经选定圆桌或课桌椅。
- [ ] 不移除登录、CORS 或 scope 保护。不把未核验的对话说成已经上云；要声称已保存，必须读回持久化记录。

## 高风险点

以下为对 `a6143abc` 的只读扫描。除文末那一处状态码保留外，没有改这些路径。

| 位置 | 原因 |
| --- | --- |
| `frontend/lib/local-project-restore.ts` | `localRestoreAvailable()` 固定返回 `false`，`requireLocalRestoreAvailable()` 无条件抛错。`commitLocalRestoreLayout` 一进入就调用它。新建若再走这个提交函数，按钮放开也会在写入时失败。 |
| `frontend/components/room-organizer/panels/local-activities-panel.tsx` | `paused`、`locked`、`begin()` 都看同一闩锁。新建表单、画廊新建、打开归档共用 `switchActivity`，最后调用 `actions.restoreBackup`。只改按钮禁用，新建仍不会执行。 |
| `frontend/components/room-organizer/panels/creative-studio.tsx` | `restoreBackup` 与 `undoRestore` 开头调用 `requireLocalRestoreAvailable()`。`canUndoRestore` 同样依赖该闩锁。fresh-create 若复用 `restoreBackup`，会再次绑回恢复暂停。 |
| `frontend/components/room-organizer/room-organizer.tsx` | `commitRestoredLayout` 调用 `commitLocalRestoreLayout`。这是恢复提交点，不是空白新活动的写入点。 |
| `frontend/components/room-organizer/panels/local-project-backup-panel.tsx` | 文件恢复按钮写死为「恢复暂不可用」并禁用。`restore()` 仍会调用 `actions.restoreBackup`。这道保护要保留。 |
| `frontend/lib/agent-resolver.ts` 约 181–189 行 | `catch` 只区分未登录、路由不存在、护栏未就绪和超时。其余异常，包括非 JSON、合同解析失败、`CONVERSATION_API_NOT_CONFIGURED`，都变成「智能理解暂不可用」并退回本地规则。现有测试禁止把错误码或诊断正文写进 `modelNotice`，所以页面文字本身仍看不到状态码。 |
| `frontend/lib/backend-session.ts` `conversationClient` | 配置不合法时，内层原因被收成 `CONVERSATION_API_NOT_CONFIGURED` / 503。上面的 `catch` 没有单独识别这个码。开关不为 `1` 时，`briefConversation` 直接返回 `enabled:false`，不会发出请求。 |
| `frontend/lib/backend-session.ts` `briefExtract` | 对话客户端为空时回落到 `scene-api`。只打开 `NEXT_PUBLIC_AGENT_ENABLED` 时，提取可能打到没有对话合同的旧函数。 |
| `client/scene-client.ts` `request` | 原先先 `response.json()` 再看 `response.ok`。网关 HTML、空正文会使解析异常盖住状态码。本次只修这一处，见下。网络层 `fetch` 自己抛错时仍然没有响应，不能编造状态码。 |
| `frontend/lib/backend-session.ts` 上传图片的 `fetch` | `uploadSource` 等仍是先 `response.json()`。那不是对话路径，本次不改。 |
| `frontend/components/room-organizer/panels/local-activities-panel.react.test.tsx` 与 `creative-studio.react.test.tsx` | 大量用例把 `localRestoreAvailable` mock 为 `true`，或 `skipIf(!localRestoreAvailable())`。闩锁为 `false` 时这些用例会跳过，不能当作线上新建可用的证据。 |

## 本次代码改动

`client/scene-client.ts` 在解析正文失败时保留响应状态：非 JSON 的失败响应抛 `SceneApiError`，码为 `HTTP_ERROR`，`status` 为真实 HTTP 状态；非 JSON 的成功响应码为 `INVALID_RESPONSE`，同样保留状态。JSON 错误仍使用正文里的 `error.code`。正文读取消（`AbortError`）原样抛出。`fetch` 失败不包装。

这只让调用方拿得到状态码。`agent-resolver.ts` 的兜底文案没有改，正式页在未知失败时仍会显示「智能理解暂不可用」。要看到真实模型回复，仍要由对话路径那一路按上面的清单验收。

`BackendSession.request` 本来就会把 `SceneApiError.status === 401` 当成登录失效并清会话。对话的 `briefConversation` 直接调用 `createSceneClient.request`，不经过这层。其它走 `BackendSession.request` 的接口，若收到非 JSON 的 401，现在会按同一规则清会话；以前解析异常没有状态码，不会走进这条分支。

## 明确不做

- 不把 `localRestoreAvailable()` 改成全局 `true`。
- 不实现 fresh-create，不改 RoomOrganizer 的新建接线。
- 不改模型调用、提示文案、认证、CORS 或 scope 保护。
- 不索取密钥，不记录登录令牌。

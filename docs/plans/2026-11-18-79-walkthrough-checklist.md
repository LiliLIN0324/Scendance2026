# #79 六条真机走查清单（2026-11-18）

> 用途：把「11 条验收用例 0 条三类全绿」变成可执行、可回填、可签字的证据采集。
> 边界：**本清单不修产品缺陷，也不判通过**。#3 改口未采纳、#6 四类阻塞的**代码侧**已在 2026-11-18 单独修掉（根因与修法见 `docs/plans/2026-11-18-79-rootcause-and-gaps.md`），本清单仍只登记复现条件与真机证据，不代改、不判过。
> 结论口径：三类证据（固定数据 / 真实浏览器 / 真实云端）同时满足才算 `pass`；`partial` 一律不算；`blocked` 单独计数，既不算过也不算失败。

## 0. 先纠正一个口径：「0 条全绿」不是测出来的，也不是「改常量就能开」

> **2026-11-18 订正**：本节原先写的「`FIXED_DATA_CASES = [2,5]`、`ledgerFromEvidence` 把 `cloud` 恒写成 `none`，所以 `allGreen: 0` 是常量算出来的」**已经过期**——main 早就支持注入。订正后的口径见下，根因拆解见 `docs/plans/2026-11-18-79-rootcause-and-gaps.md`。

`frontend/components/room-organizer/lib/outdoor-release-status-card.ts` 里（现状）：

- `FIXED_DATA_CASES` 已经是 **1..11（11/11 有固定数据）**——每条都有具名测试文件，`outdoor-fixed-data-evidence.test.ts` 钉住文件存在；
- `ledgerFromEvidence(fixedDataIds, evidence, cloudPassIds)` **已经能注入**云端列，浏览器列能注入走查记录（`WalkthroughRecord`，可带 `pass`）；
- `BROWSER_EVIDENCE` 常量仍只有 `none` / `partial`——它是**对照表快照**（2026-11-17 第二轮那一列的真实结果），不是「浏览器证据的来源」；浏览器 `pass` 只能由真机走查产生。

所以 `allGreen: 0` 的构成是：**固定数据齐（11/11）+ 浏览器 0 条 pass + 云端 0 条 pass**。这是**输入缺**，不是算法缺，也不是改一行常量就能开——即使六条真机全过，也得先在走查记录本里标 `pass`、在面板上声明云端 `pass`，状态卡才会动。

本清单的终点因此不是「跑完」，而是 **§5 的三处回填 + 人签字**。

## 6. 判定口径

| 标记 | 含义 | 是否计入全绿 |
| --- | --- | --- |
| `pass` | 三类证据齐，且通过判据逐条满足 | 是 |
| `partial` | 有部分证据但不构成通过（如只有固定数据、只有半条链路） | 否 |
| `blocked` | 前置不满足，未执行或执行无效 | 否，单独统计 |
| `fail` | 执行了但判据不满足 | 否，且必须登记缺陷号 |
| `n/a` | 该类的证据在语义上不适用（如导出类用例的云端列） | 否；`n/a` 不能顶 `pass` |

**发布门禁的判据不变**：11 条三类全绿才解除。技术门禁（tsc / 定向测试 / build）绿**不替代**本清单；两者分开汇报。

### 9.1 #2 为什么这轮能跑（此前两轮卡住的地方）

- **前置终于有着落**：高德源对「人民公园」「文化广场」这类词只回**不同名**的条目，扩到 40 词扫描后，
  「街心公园」在高德源单源就有 **4 条名称完全相同**、坐标最远相距 89.8 km 的 POI（北京海淀/大兴/密云/房山）。
  生产端点与本机 3199 代理返回**同一批 id 与坐标**（同一把高德 key）。
- **同名对不会因为「锚点」被吃掉**：本机是「高德 + 天地图」双源，高德源永不带 `center`（全国检索），
  天地图带 `center`（锚在场地锚点附近的小范围）；同名对来自高德源 → 正式站（单源高德）与本机都能拿到。
- **点选后能精确回读**：定位钉画在 canvas 上、DOM 读不到坐标，但 app 自己把被选中的候选写进
  `scendance-place-recent-v1`（含 id/name/address/lng/lat）→ 用它回读「到底选了哪一条」。

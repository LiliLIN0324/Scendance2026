# 幕景 Agent 卡点实施计划

日期：2026-11-25
来源：[飞书《幕景Agent Test》卡点与优化](https://my.feishu.cn/wiki/E13dwBlNriOopckkpHhcCKJynIh)、[线上工作台](https://scendance.lilicoding.space/)、[既有 R7 排期](2026-11-23-agent-test-readiness-roadmap.md)。

这份计划用于逐条关闭飞书卡点。Agent 推进布置主线，用户在相关步骤补信息、手调或确认，随后在同一步重新判定。把飞书红字当作复测输入和验收建议。“线上对照”只证明曾观察到的界面和会话，仓库里已有相关分支也只说明实现存在；每条是否仍有缺陷，要按当前版本复现。

## 先做基线

1. 记录本地提交、运行环境、线上 URL 与验证时间。用测试活动各准备一份空白画布和一份已有红线与分区的画布，保留初始快照。
2. 先复现 **S4 → S5**：选一个场地候选，检查确认前后红线变化；确认后输入青山湖瑜伽需求，看「用途与室内外」卡是否留在当前步骤，是否出现婚礼模板。记录第一处偏离，抓最小状态证据（活动、会话、方案版本、当前任务、候选/确认状态），再读相关代码。若通过，标“通过待关闭”，以同样方法检查下一个独立卡点。
3. 线上已有证据：活动页同时有新开会话、历史和本机活动；in77 历史有候选轮廓提示，也有底图 503 提示；已画分区支持直接编辑名称、用途和室内外，另有出预览和手画入口。线上完整链路、青山湖压水、候选排序及真实服务商失败尚未复测。使用测试活动验证写操作。

## 按批实施

| 批次 | 飞书行 | 实施与可验收结果 |
| --- | --- | --- |
| **P0-A · 边界与任务连续性** | S4、S5、锁定区域压水 | 先查候选选择、范围草案、应用及下一张任务卡的过渡。选候选不改已应用红线；确认一次才应用；旧请求完成或取消时不得覆盖当前用途卡。青山湖按候选、红线、分区三个层次核对水体：有掩膜时检查不压水，缺数据时标待核。否则从首个失败步骤修。 |
| **P0-B · 会话与手动修改** | 两条 S0、M1 | 在活动 A 新开会话，消息为空，画布仍归 A；活动草案可以继续，但任务须能证明归属。再切 B，A 的任务和异步结果不得串入。手调范围/分区后区分候选与已应用边界，只让可编辑层显示手柄；修改后只重算受影响部分。写入失败时按真实原因反馈，并核对原方案或未保存编辑仍可找回。 |
| **P1-A · 输入与纸面模式** | S1 需求理解、两条纸面起稿 | 执行同一组对照：纯找地点、复合活动需求缺人数、已给 40×60 米的纸面方案、纸面补地址。在缺人数且下一步确实受人数约束时，只问必要问题；有可用纸面范围时可先安排分区，座位和容量保留待核。纸面切地图先让用户核对新底板，确认前保留原草案，确认后核对范围和分区。 |
| **P1-B · 检索与等待** | S2、B-1、S3 | 用长地名带括号备注、短地名、零结果、有地点无轮廓、检索失败和底图失败分别对照。只在已经确认范围时提供沿用当前范围。排名先测真实地名与酒店分类；候选元数据缺失就标未知。选候选后给出查找状态，超时可手画；迟到结果不能覆盖用户已手画或已选的新候选。 |
| **P1-C · 方案内容与失败恢复** | S5、M1、M2 | 青山湖复测必须覆盖签到、沿路 5 个集卡点、瑜伽冥想、合影、兑奖；人数未知时座位和垫子留位。追加“签到移到入口，其他区不动，先别摆物料”，对比修改前后差异。注入失败与取消分别验证：保留原输入及已应用方案；可确认失败的请求支持原句重试；原任务状态未知时先查原任务，避免重复请求或计费。 |

P0-A 先验证主链，P0-B 可先复现。P1 的复测可提前做。多个改动若都涉及同一 Agent 面板或编排 hook，由一个执行者统筹同批修改，避免并行覆盖相同状态。现有 R7 排期中的编排抽离可单独排期，修复本表复现问题无需先批准大重构。

## 代码入口与回归

- **会话与编排**：从 frontend/components/room-organizer/hooks/use-assistant-sessions.ts、panels/agent-panel.tsx、hooks/use-outdoor-agent-workflow.ts 和 components/outdoor-workflow-card.tsx 查实际所有权。复用已有 Agent 面板及 workflow 的 React 测试，钉住会话/活动切换与草案确认前后状态。
- **场地与纸面**：从 lib/place-first.ts、lib/plan-basemap-source.ts、panels/agent-confirm-cards.tsx、Agent 面板的 handleVenuePick 和 workflow 的 virtual-venue 分支开始。当前已发现 needsHeadcountFirst、scopeConfirmed 和检索失败/零结果的分流，先验证触发条件和上线状态。用现有 place-first、agent-confirm-cards 和 workflow 用例做回归。
- **范围、分区与物料**：从 lib/place-area.ts、lib/outdoor-agent-planning.ts、components/outdoor-plan-canvas.tsx 和 frontend/lib/zone-plan-application.ts 跟到实际写入点。复用 write-gates、boundary-lock、workflow design、place-area 等定向用例；核对确认前无画布写入、修改后无无关对象变更。
- **失败恢复**：读 frontend/lib/agent-error-view.ts 与调用方和运行面板，先区分可确认失败、已取消、仍可能运行或计费的结果。用现有 presenter 测试和组件测试断言错误位置、原句重试和状态保留。

上述 lib、panels、hooks、components 短路径默认相对 frontend/components/room-organizer。后续执行者以仓库当前代码为准。根 AGENTS.md 的独占渲染/导出五文件如确需修改，先登记并获确认；scan-placement.ts、furniture-builders.ts 几何基线禁改。后端契约、迁移、依赖与部署单独走仓库规定流程。

## 完成条件

1. 每条飞书卡点写清 **首个失败步骤 → 最小改动 → 同输入复测 → focused 回归 → 未验证项**。现状已通过的条目留现场证据即可。
2. 本地先跑对应 Vitest，再跑 npm --prefix frontend run typecheck 和 npm --prefix frontend run build；如变更触及根契约，按授权范围另跑 npm run check。文案测试按“什么条件下该位置显示”断言。
3. 上线验收用同样输入和顺序重跑一遍，至少保留活动/会话归属、红线确认前后、分区预览、手调及失败回执的证据。分别写清本地保存、mock、真实云验证的结果。没有实际云端证据的条目仍标未验，测试通过不等同线上验收。

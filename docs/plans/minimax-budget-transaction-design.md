# MiniMax 整趟预留：未部署设计与放行条件

状态：设计草案，**没有可部署 RPC，也没有启用真实 MiniMax 工具调用**。当前未完成请求与费率策略的可信绑定、跨事务防绕过和真实服务费用核验，不能宣称费用受控。单轮需求提取有独立路径，当前同样没有金额预留。

## 现有事实

- `scene_private.agent_runs` 按用户、项目、request_key 唯一，保留运行输入指纹和工作线程 claim；`scene_private.requests` 按用户、kind、request_key 唯一，保留指纹、整数分预留和 `reserved / complete / failed / unknown`；`scene_private.budgets` 只有 `text / generation` 两个共享桶。
- 当前预算迁移把 `limit_cents` 设为 null；Agent 的 `step` 更新每日表并固定记 20 分，不等于真实账单，也不构成上限。`text_provider_calls` 的 attempt 只允许 0、1，不能直接当六轮调用账本。
- Agent 的 `create` 和通用 `job_rpc reserve` 各自独立提交；只在服务端依次调用两次，遇到中断、并发和重试不能保证原子关联。只新增一个可选包装 RPC，也挡不住旧 Agent 路径。
- `provider-cost-bound.ts` 是离线纯校验：它不认证费率、不计量实际请求、不保存预算，也不实施原子预留。MiniMax 工具预演只使用内存 Map，不能承担跨工作线程的防重。

## 拟议事务边界

若后续批准此方案，增加仅 `service_role` 可调用的事务函数，保留现有项目成员、租约、资源权限和请求指纹检查；不得信任浏览器提交的费率或预算。该函数在同一个数据库事务内：

1. 基于用户、项目和请求 ID 获取锁；复用现有 Agent 创建校验，若相同请求已存在则检查内容和策略指纹，再返回同一运行，禁止二次占额；指纹不同立即拒绝。
2. 对新的运行锁定文本预算行，明确拒绝 null 或无效上限。以可信服务提供且已验证的特定账户、模型、币种和有效期费率，以及证明覆盖完整序列化请求和全部轮次的输入/输出上界，计算整趟最坏成本；币种不一致、精度溢出、证明缺失或过期均拒绝。微单位向上取整到分，检查整数分范围后，原子比较预算和增量。
3. 以运行 ID 作为预留行 ID 和独立请求键写入 `requests`，把非敏感的策略版本、模型、费率摘要、上界和日期写入受控元数据；不存对话或推理文本。预算更新与运行创建任一步失败都回滚。固定锁顺序并覆盖并发竞争和同键重试。
4. 原有 Agent 的 `start / step` 与可信服务必须一起增加不可绕过的预留/策略/claim 校验；只测试新函数无法证明旧路径封闭。使用隔离的 MiniMax 账户，或所有对同一账户的计费路径都受同一额度控制，否则不能称账户全局预算。

## 派发与未知结果

每次实际请求前持久记录派发状态和输入配置摘要，检查运行 claim、剩余次数、策略有效期、模型和实际序列化上界。网络超时、取消或工作线程崩溃都不能证明未计费：标为 `unknown`、保留整趟预留，不自动重新请求或释放；后续只有经可信供应商账单核对的受控流程才能结算。初版可以永不自动释放，以牺牲额度利用率换取可核查性。

不能简单把旧 `requests.finish` 当作可自动结算流程：它会写入状态和用量，却没有完整的供应商账单验证与原子退款协议。项目删除可能级联删除 `agent_runs`，预留记录、策略摘要和未决账单必须保留。额外的 JEV、图像/3D 供应商工具应关闭，或由各自的独立预算路径覆盖；不能计入文本预留后假定免费。

## 当前无法证明和验收

- 输入 token 上界必须由可核实的模型和完整请求序列化过程证明，不能以 UTF-8 字节数、平均中文字符比例或另一协议的估算接口冒充。模型、端点、工具列表及请求内容必须与已核验策略绑定。
- `text` 桶没有账户/币种维度；只能在明确单账户、单币种和覆盖全部收费路径的运行条件下作保守保证。多账户隔离或精细结算需额外可靠结构。
- 即使通过内存或单进程测试，也不能证明真实 Postgres 多连接锁、事务隔离、权限、故障和远端账单的安全性。应先用隔离 PostgreSQL/Supabase 环境并发测试，再人工审查真实部署配置；本草案未做这些验证。
- 放行前测试至少包括：无权限、租约过期、预算未配置、同请求并发/不同指纹、不同项目同请求键、预算争抢、事务中途故障、重试、旧入口直接 start、费率过期、模型/端点变化、token 超限、派发后超时、项目删除及未经核验的退款。测试不得调用实际付费模型。

## 隔离 PostgreSQL 原型观察（未部署）

在无网络、无发布端口、无挂载的临时 PostgreSQL 容器加载仓库 28 个迁移，只在临时库试验受控外层函数及内部函数权限收紧。旧场景和活动任务可读取、取消，未预留启动被拒；新场景与活动任务在固定测试策略预留后可启动和进入一步。不同用户并发争抢 100 分预算、各预留 60 分时仅一笔成功；事务未提交时终止连接，新增运行和预留均回滚；取消已预留任务后占额未自动释放。临时容器已清理。以上只说明这些隔离样例的行为，不证明真实供应商费用、完整并发故障或生产安全。

- **指纹可信边界**：隔离原型复用现有 Agent 接受的外部传入指纹；修改输入却沿用原指纹时被识别为同一次请求。正式设计必须由可信服务对完整规范化请求和冻结的账户、模型、费率、单位及上界重新计算并核对，不能把请求携带的摘要当证明。数据库级与服务级的绑定及重试一致性尚需验证。
- **避免重复核算**：隔离原型整趟预留后，原有 scene 和 activity `step` 仍分别向日表固定记 20 分。其含义与整趟预留不同，不能将两者简单相加当作真实支出或再次扣同一预算；接入前须明确并测试保守预留、调用统计及可核验账单的分工。
- **服务角色权限**：隔离库确认 `service_role` 当前对 `requests` 可插入、对 `budgets` 和 `agent_runs` 可更新。撤销旧内部 RPC 的 execute 只能封堵直接调用旧函数，不能抵抗有任意 SQL 能力的服务角色。直接收回表权限可能破坏现有 security-invoker 函数和其他供应商路径，必须逐条验证权限链；不能把试验外层描述为完整的权限安全边界。
- 旧未预留运行被限制为读取或取消；新旧供应商的场景与活动入口均需使用经验证的冻结策略后才能启动。历史任务恢复、token 证明、发送后计费不确定性、工具跨线程防重与其他供应商兼容均未完成验证。

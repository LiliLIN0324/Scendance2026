## 今天 main 已经有的，以及还缺的

已有、本草案不替换：

- 活动范围是 `activity:${layout.id}` 或 `draft:unidentified`。里面没有项目、账号、会话三件套。`room-organizer.tsx` 用 `Symbol` 做在途回合，刷新即失。
- 未决要求在 `agent-panel.tsx` 里按修剪后的原文放进 `Set`。两句相同的「30人」只会占一个槽；后一句成功会按原文删掉这个槽，分不清删的是哪一次。
- `creative-studio.tsx` 在发起请求前把 `{requestId, runId?, ...}` 写入 `localStorage` 的 `scendance:agent-run:${scope}`。未知或仍在跑的标记不能被历史核对清掉；「查询原任务」不会再次提交。这只覆盖工作室云端生成，不覆盖本机提案、重建、材质、审校、恢复。
- `pending-candidate-registry.ts` 能让过期的清场函数清不掉新候选，但它不记录需求版本。
- `dialogue-handoff.ts` 投影当前记忆，未知不会继承旧值。它不是跨刷新日志。
- `review-fact-ledger.ts` 自己写明：停掉或重载后 generation 作废，不是跨标签账本。
- PR86 的独立 `conversation-api` 仍默认关闭，不负责需求版本。

还缺、也就是本闭环要先钉住的合同：

1. 项目、活动、账号、会话、事件编号彼此分开。无主旧聊天不能划给当前账号，也不能删。
2. 原话先落日志，调用方才可以声称已接收。记录失败时原文仍回到调用方。
3. `recorded / pending / accepted / unresolved / withdrawn` 按事件编号区分。后一句接受不清前一句未决。
4. 候选绑定当时的需求版本、入口和请求编号。新输入或后一个候选使旧的开放候选失效。确认必须同时带上这个候选编号和这个版本，并且对应请求已经明确完成。
5. 超时保持 `outcome_unknown`，不自动第二次付费。刷新后仍能按原 `requestId` 查到。服务侧已经接受、本机标记没写上时，读回同一条，而不是再提交。

## 最小闭环

三个纯模块，都在 `frontend/components/room-organizer/lib/`：

- `assistant-conversation-scope.ts`：有账号时编码为 `conv:v1:<活动>:<存储位置>:<账号>`。账号为空则原样返回活动键。`sameConversationOwner` 只比较存储位置和账号。`unownedHistoryAction('adopt' | 'delete')` 恒为不允许，效果是 none。
- `dialogue-turn-tracker.ts`：`begin(eventId)` 返回释放函数。只有唯一在途编号 `canCapture`。释放只表示不再在途。
- `requirement-recovery-loop.ts`：一份可序列化的内存日志。比较并交换用 `serial`。所有者是项目 + 活动 + 账号 + 存储位置，会话编号写在每一句上。

调用顺序：

1. `stageInput` 同步提交。成功时 `received: false`，版本加一，开放候选改为 `invalidated`。请求标记保留，供以后按编号查询。冲突时不写入，原文在返回值里。
2. `claimReceived` 只把 `recorded` 改成 `pending`。这是唯一的「已接收」。
3. 另一句还在途时，两句都不能 `bindCandidate`。
4. `bindCandidate` / `bindCommand` 分配新的候选编号和请求编号，阶段是 `prepared`，付费次数是 0。同一版本上再绑定会让上一个开放候选失效。命令绑定不增加需求版本，用于「换一版」这种没有新原话的动作；有句子在途时拒绝。
5. `submitPrepared` 把付费次数从 0 改成 1。再调用不会变成 2。`localWrite: 'fail'` 时阶段是 `local_write_failed`，日志里仍有这条请求。
6. `noteOutcomeUnknown` 只从 `submitted` 进入 `outcome_unknown`。`resubmit` 对已经付过费的请求一律拒绝。
7. `observeOriginal(..., 'complete')` 是按原编号读到结果，不新开请求，不加付费次数。读到仍未知就保持未知。
8. `confirm(candidateId, revision)` 要求候选仍开放、版本等于日志头版本、绑定的请求阶段是 `complete`。确认不改其他句子的未决状态。
9. `abandon` 把在途句子收成 `unresolved`。`withdraw` 只撤回给出的那个事件。
10. `serializeRecoveryJournal` / `hydrateRecoveryJournal` 模拟刷新。另一端 `createRequirementRecoveryLoop` 共享同一日志时，会按日志重新武装栅栏，用来表示两个标签看到同一份账。

五个入口 `proposal | rebuild | material | review | restore` 走同一个 `confirm`。`coverage()` 固定返回 `runtimeWired: false` 和 `singleAgent: true`。这里没有第二个产品 Agent，也没有把入口接到真实按钮。

因此：普通提案、重建、材质、审校、恢复在现网入口上仍然没有这层保护。测试证明的是合同对五种入口一视同仁，不是页面已经挡住旧候选。

## 表结构

不改现有 Supabase 表，不加迁移，不调用新的 RPC。

旧 diff 想在 `backend.ts` 上挂 `project_requirement_journal_rpc`，并在 `api.ts` 增加 `/projects/:id/requirements`。main 没有这个函数。要做持久日志只能新增对象（追加表或新 RPC），那本身就是表结构变更，必须单独评审。在那之前，线上的恢复边界仍然是现有的 `agent_runs` 读取和本机 `scendance:agent-run:*` 标记。本日志只是这两者将来要遵守的内存合同，不是它们的替代品。

若以后获准持久化，建议新表至少具备：项目、账号、活动、会话、事件编号、需求版本、候选编号、请求编号、阶段、付费次数。唯一约束放在请求编号上。未知和本机写入失败都是阶段，不是再插入一行新请求。不要给场景表、提案表或 `agent_runs` 加可空列来偷渡这些字段。

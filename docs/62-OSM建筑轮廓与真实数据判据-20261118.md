# 62 · OSM 建筑轮廓：真实数据第一次算出判据（2026-11-18）

> 一句话：用 OSM 的 8 栋真实建筑轮廓 + 盐官布置里那块真实坐标的导视牌，**GEN-07 第一次在真实数据上算出结果：最小退距 9.8 m，要求 ≥3 m**。
> 数据：`data/agent-corpus/sites/yanguan.json`、`yanguan-check.json`、`raw/yanguan-overpass.json`；脚本：`scripts/build-osm-sites.mjs`；守门：`tests/agent-corpus-osm-sites.test.ts`。

## 一、为什么盯住这一条

`docs/61` 的结论很硬：5 份自有档案全抽出来，**0 条判据可算**。卡点不是判据写错，是缺「建筑足迹」和「物料落位」。

物料落位得等真实方案（见第六节的采购决策）。但**建筑足迹是可以立刻拿到的**——OSM 就有，而且许可清晰（ODbL）。这就是把「0 条」打破一格的最短路径。

## 二、网络真实状况（先说清，免得重复踩）

| 端点 | 结果 |
|---|---|
| `overpass-api.de`（POST） | 406 → 502 |
| `overpass-api.de`（GET status） | 502 / 超时 |
| `overpass.kumi.systems` | 超时 |
| `overpass.private.coffee` | 超时 |
| `overpass.osm.ch` | 400 |
| `maps.mail.ru/osm/tools/overpass` | **200，约 15 s** |

最终用 `maps.mail.ru` 镜像。查询：

```
[out:json][timeout:60];
(way["building"](around:120,30.4122558,120.5368897););
out geom;
```

120 m 半径返回 8 栋建筑（8.7 KB）；250 m 半径那次 504 超时，所以半径收小、一次只取一个片区。

## 三、数据与许可

- 来源：© OpenStreetMap contributors，**ODbL 1.0**。
- 时间戳：`timestamp_osm_base = 2026-11-18T16:33:14Z`（写在 `query.osmBaseTimestamp` 里）。
- 再分发要保留归属与相同许可；产物里 `license` 段写死了这三条，脚本发现原始 JSON 没有 ODbL 声明会直接抛错，不出图。

## 四、关键一步：原点必须继承

`venue-layouts` 里盐官的布局是「等距圆柱投影后的本地米」，原点是 `120.53691316952109, 30.41230517388013`，`metersPerDegLng = 96002.9`。

**建筑坐标必须用同一个原点、同一组系数**，否则设施和建筑不在一个坐标系里，算出来的「9.8 m」就是编的。这一点写进了测试：任取一栋建筑的角点，用原始经纬重算必须与存下来的坐标一致（误差 < 0.05 m）。

## 五、结果

| 项 | 值 |
|---|---|
| 建筑 | 8 栋，占地 13 737.54 ㎡，范围约 190 m 见方 |
| 设施（来自盐官真实坐标布局） | 1 个：导视牌 0.7×0.5 m |
| pass / violation / skipped / unsupported | **1 / 0 / 10 / 69** |
| GEN-07 | **pass：最小退距 9.8 m（要求 ≥3 m）** |

这 1 条 pass 的意义要说准：

- **它证明的是「判据能跑真实数据」**——真实建筑轮廓、真实经纬、同一坐标系、几何算法真的算出了 9.8 m。
- **它不证明这个场地合规**：只有一个导视牌、建筑是 OSM 现状轮廓（不是活动期状态）、没有摊位、没有人数、没有出入口。`docs/60` 里那三条间距阈值仍然没有真实样本。

顺便暴露一个规律：**一栋建筑 + 一件设施就能让一条判据从 skipped 变成 pass**。要覆盖更多判据，需要的是「物料落位」，不是更多建筑。

## 六、采购决策（记录）

2026-11-18 确认：**带几何的真实方案后续通过与其他公司合作购买**，作为正式数据源。

因此 OSM 的定位要收窄：

| 用途 | 用不用 OSM |
|---|---|
| 建筑足迹、底图、场地外轮廓 | 用（现在就在用） |
| 真实活动布置、物料落位、人数 | **不用**，等采购数据 |
| 阈值校验的真实样本 | 等采购数据，OSM 顶不上 |

这条决定了后续优先级：OSM 这条线的价值在「把判据跑通」，不在「积累样本」。

## 七、这次没做的两件

**Vadere 交叉校验（B）**：需要 Java 运行时 + 下载框架（百 MB 级）。本轮没装、没跑，所以没有任何 Vadere 结果可报。要做得先确认环境允许装 JDK 与二进制包。

**国际标准数值对照（C）**：检索只拿到入口（`eventsindustryforum.co.uk` 的 Purple Guide、`hse.gov.uk/event-safety/`），**没有逐条核对条文**。所以这里只记入口，不写任何数值——把没核过的数字写进判据是最危险的做法。

## 八、复现与刷新

```bash
# 1) 拉取（需要能访问 mirrors；本文用的是 maps.mail.ru）
#    PowerShell 示例见下，输出存到 data/agent-corpus/sites/raw/yanguan-overpass.json
# 2) 加工 + 跑判据
node scripts/build-osm-sites.mjs
npx vitest run tests/agent-corpus-osm-sites.test.ts
```

刷新时只要换掉 `raw/*.json`，其余由脚本重算；`sites/yanguan.json` 的 `query.osmBaseTimestamp` 会跟着变，测试会比对原始文件里的时间戳是否一致。

## 九、待核

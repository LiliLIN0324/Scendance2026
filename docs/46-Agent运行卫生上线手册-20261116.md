# Agent 运行卫生：上线、观察与回滚（20261116）

对应分支 `fix/agent-run-hygiene`，迁移 `20261116120000`、`20261116130000`，运维脚本 `supabase/ops/install-agent-retention-cron.sql`。

## 一、这次改了什么（上线要理解的四件事）

1. **读不再锁运行行**：`agent_rpc` 现在是薄分发器，`get/by_request` 全程普通读；只有写动作 `for update`。
2. **deadline 会续**：`step/progress/usage/check/take_notes/start/finish/checkpoint` 把期限续到 `min(now+90s, created_at+10min)`；到期收敛改成条件更新，只有一个调用者能结账。
3. **收尾退款**：`fail/cancel/到期` 退还“扣了钱但 usage 里没有 `turn`/`mode` 证据”的步（每步 20 分），逐行记 `committed_cents`，同一笔只退一次。
4. **事件彻底脱锁**：`agent_run_events` 去掉了指向 `agent_runs` 的外键（`INSERT` 的 `KEY SHARE` 会被写事务挡住），改为 `agent_runs` 删除前触发器清理，`purge_agent_data` 再兜底扫孤儿。

另外：`?slim=1` 的轮询只回摘要（运行中 `candidates/planCandidates` 为空），终态仍回全量；fingerprint 只算业务输入；凭据样式文本在入库前拒绝；保留期每天 03:30 自动清理。

## 二、上线顺序（不要颠倒）

| 步骤 | 动作 | 为什么这个顺序 |
|---|---|---|
| 1 | 发布前端 | 旧 API 会忽略 `?slim=1`，只是不省流量，不会报错 |
| 2 | 部署 `supabase/functions` | 新代码只多传一个 `slim` 键，旧库会忽略 |
| 3 | 应用两个迁移 | 真正生效的一步；函数签名未变，不需要同步改函数 |
| 4 | 执行 `install-agent-retention-cron.sql` | 依赖 pg_cron；可重复安装 |

命令按仓库现有流程执行（`supabase db push` / `supabase functions deploy`，或平台控制台）。**迁移不要手工拆开跑**：`20261116120000` 里函数互相引用，按文件名顺序整体应用。

## 三、上线前必须做的三件事

1. **真库并发验证**（本机可跑，不联网）：
   ```powershell
   $env:RUN_ISOLATED_POSTGRES_TESTS='1'
   npx vitest run tests/agent-run-readlock-postgres.test.ts
   ```
   断言：写事务持锁 4 秒期间，`get` 与事件追加都在 1.5 秒内返回。**这条测试上次抓到了外键 `KEY SHARE` 的真实阻塞**，不要跳过。
2. **预发冒烟**：创建一趟 run → 轮询 → 中途 `note` → `checkpoint` → `finish`，确认前端确认卡能出三个候选、能应用、能撤销。
3. **确认 pg_cron 可用**：`select extname from pg_extension where extname='pg_cron';` 为空就先别装 cron，保留期可手工调用。

## 四、上线后 24 小时看什么

```sql
-- 1) 还在跑的运行（正常应该接近 0；长期不降说明 worker 挂了或没有收尾）
select state, count(*) from scene_private.agent_runs
where created_at > now() - interval '1 day' group by state;

-- 2) 超时失败是否变少（这是本次的主指标）
select error_code, count(*) from scene_private.agent_runs
where created_at > now() - interval '1 day' group by error_code order by 2 desc;

-- 3) 退款是否只退一次：committed_cents 不应为负，且应等于“已回报用量的步数 × 20”
select count(*) filter (where committed_cents < 0) as negative,
       count(*) filter (where committed_cents > call_count * 20) as over_charged
from scene_private.agent_runs where created_at > now() - interval '1 day';

-- 4) 事件 seq 是否连续（同一 run 内 max(seq) = count(*)）
select count(*) from (
  select run_id from scene_private.agent_run_events
  group by run_id having max(seq) <> count(*)
) broken;

-- 5) 有没有人卡在等锁（应长期为 0）
select count(*) from pg_stat_activity
where wait_event_type='Lock' and query like '%agent_runs%';
```

另外盯两个业务信号：`AI_BUSY` 是否变多（心跳生效后单个 owner 最多挡 90 秒）、前端轮询是否还在传大响应（`?slim=1` 生效后运行中响应应明显变小）。

## 五、回滚

**应用层**：前端与 functions 回滚到上一个部署即可，不需要动库。

**数据库层**（函数被 `create or replace` 覆盖过）：按顺序重放历史迁移即可恢复旧函数体，它们都是 `create or replace`：

```
supabase/migrations/20261010010000_*.sql   -- agent_rpc 活动分发器
supabase/migrations/20261111170000_*.sql   -- 守卫层
supabase/migrations/20261112180000_*.sql   -- 场景本体 + agent_view
```

注意两点：

1. 重放后 `agent_view` 不再认识 `slim`（会忽略，前端无感），事件表仍然没有外键（这是有意的，见第一节第 4 条）。
2. 要彻底还原外键（一般没必要）：
   ```sql
   alter table scene_private.agent_run_events
     add constraint agent_run_events_run_id_fkey
     foreign key (run_id) references scene_private.agent_runs(id) on delete cascade;
   ```
   加之前先清孤儿：`delete from scene_private.agent_run_events e where not exists (select 1 from scene_private.agent_runs r where r.id=e.run_id);`

**定时任务**：`select cron.unschedule('agent-retention-purge');`

**数据**：`committed_cents` 列、`purge_agent_data` 函数可以留着不动，不影响旧逻辑；真要删列前先确认没有报表在读。

## 六、已知边界（上线前先跟产品对齐）

1. **升级窗口内的老 run**：升级前创建、还没重试过的同 `requestId`，升级后第一次重放会是 409 `IDEMPOTENCY_CONFLICT`（旧指纹含租约字段）。客户端换新 `requestId` 即可，不做跨版本兜底。
2. **轮询摘要只影响运行中**：终态一定回全量，所以确认卡、应用、撤销都不受影响；如果以后有界面要“跑着的时候看候选”，得显式去掉 `slim`。
3. **预算只有账、没有顶**：`text_daily_budgets` 仍然不设上限，20 分/步是拍平价。要设上限是另一个产品决定。
4. **`AI_BUSY` 仍是每 owner 全局一把**：心跳把最长占用压到 90 秒，但没有按项目放宽。
5. **候选没有瘦身到“摘要 + 按需取详情”**：运行中省掉了整包，终态仍是全量（前端预览契约要求 `base_scene`/`candidate` 同时在场）。

# 版本更新文案规范

这份规范管一件事：**每个版本的更新记录要写到用户能直接看懂、能照着点一遍的程度**。

过去的问题：`v3.0.0` 只写了三行（「按要求把版本升到 3.0.0，这次没有新功能」），
`v3.1.0` 只有四条，而读者想知道「这版和我有什么关系」时，翻半天也找不到入口和结果。
从 v3.2.0 起，每个版本按本文的结构补齐；历史版本按同一结构回填。

## 1. 文件与结构

- 唯一正文：仓库根目录 `CHANGELOG.md`，最新的版本在最上面。
- 文件分为两块：
  1. **版本段落**（`## vX.Y.Z · 短标题 · YYYY-MM-DD`）：面向用户，必须满足本文全部下限。
  2. **附录 · 过程记录**（`## 附录 · 过程记录（YYYY-MM）`）：实施卡、自查记录、逐条证据，
     原文保留，不参与强制检查。
- 只有当版本号一起进 `package.json`、`frontend/package.json`、两个 `package-lock.json` 并打了 tag，
  才算「一个版本」；没有版本号的实施记录一律进附录。

## 2. 标题行

```
## v3.2.0 · 右轨拍平 · 账户中心两栏 · 2026-11-02
```

- 严格顺序：`v` + 语义版本 + ` · ` + 短标题 + ` · ` + 日期（`YYYY-MM-DD`，本地日期）。
- 短标题 ≤ 12 个汉字，用 ` · ` 分隔最多两个短语，不要写日期、不要写「更新」。
- 标题只说「这版最想让人记住的一两件事」，不是 changelog 的摘要。

## 3. 每个版本必须有的五段（顺序固定）

| 段 | 写法 | 下限 |
| --- | --- | --- |
| 摘要段 | 2–3 句，用户 3 秒读完知道这版干什么；说明「从什么变成什么」 | ≥ 40 字 |
| `**你能直接用到的**` | 新增或变化的能力，每条写「入口/按钮 → 动作 → 结果」 | ≥ 4 条 |
| `**改好了什么**` | 改掉的问题、纠正的口径、删掉的旧行为 | ≥ 1 条（没有就写 `- 这版没有改口径。`） |
| `**边界与未做**` | 还没做的、需要条件才能用的、已知限制 | ≥ 1 条（没有就写 `- 无已知边界。`） |
| `**内部与验证**`（可选） | 契约/迁移/清理/测试与实机路径，写给下一个接手的人 | — |

**整个版本合计**：≥ 6 条 bullet、≥ 260 字（不含标题行）。

## 4. 一条 bullet 只写一件事

- 开头用 `**短标签**：`（标签 ≤ 8 字），后面用用户语言写清「在哪、点了会怎样」。
- 必须带可验证的具体信息：页面路径（`/guide`）、元素 id（`#tool-preset`）、数值（`420px`、`90 天`）。
- 禁用语：`若干`、`优化了体验`、`多项改进`、`详见下文`、`预计`、`即将`。
- 不把三件事塞进一条；要用 `；` 串超过两个动作就拆成两条。
- 厂商名（Aholo / 高德 / Supabase 等）只允许出现在「边界与未做」「内部与验证」，不进用户文案。
- 用「现在…不再…」对比改前改后，别只写「改进了 X」。

## 5. 覆盖范围

每个版本要覆盖这一版**所有对外可见的变化**，不是挑三件写：

- 界面/交互变化（按钮、面板、入口、文案口径）
- 数据与状态（登录、保存、本地存储、跨设备）
- 流程规则（什么条件下才出现、什么时候禁用、失败怎么说）
- 删掉的东西同样要写（「不再有…」），并说明替代入口在哪
- 纯内部重构、测试补齐、文档迁移 → 放「内部与验证」

## 6. 回填历史版本的方法

```sh
# 所有 tag 及日期
git for-each-ref --sort=creatordate --format='%(refname:short) | %(creatordate:short) | %(subject)' refs/tags

# 两个 tag 之间的提交
git log --oneline v3.0.0..v3.1.0
git show --stat v3.1.0
git show v3.1.0:CHANGELOG.md | sed -n '1,60p'
```

- 先看 tag 之间的提交标题与文件清单，再回填「你能直接用到的」。
- 只写能验证的事实；拿不准的写进「边界与未做」，不要编。
- 缺版本的 tag（例如 v1.3.x、v1.4.0、v2.1.0）要按 tag 日期补出版本段落。

## 7. 发布流程（每版照做）

1. 更新 `package.json`、`frontend/package.json`（`npm version X.Y.Z --no-git-tag-version` 同步 lock）。
2. 在 `CHANGELOG.md` 最上方写新版本段落，跑 `npm run check:changelog`，必须 0 error。
3. 跑 `npm --prefix frontend exec tsc --noEmit` 与相关 `vitest`。
4. 提交（`release: vX.Y.Z — 短标题`）→ `git tag -a vX.Y.Z -m "vX.Y.Z 短标题"` → push main 与 tag。
5. 部署后把「实机核对方式」写进该版本的「内部与验证」段。

## 8. GitHub 上的发布会话（Release / tag 注释）

仓库 Tags 页显示的「版本介绍」来自两种东西：annotated tag 的注释、以及同名 Release 的正文。
**以 Release 为准**：每个版本都要有 Release，正文 = `CHANGELOG.md` 里该版本段落的原文（去掉 `## v…` 标题行），
标题 = `vX.Y.Z 短标题`。这样 Tags 页会出现「Notes」、用户可以订阅，也不需要为了改文案去搬 tag。

- 同步命令（读 `CHANGELOG.md`，有则 `edit`、无则 `create`，不加 `--latest` 覆盖最近发布）：

  ```sh
  node scripts/sync-github-releases.mjs            # 全部版本
  node scripts/sync-github-releases.mjs v3.2.0     # 只同步一个
  node scripts/sync-github-releases.mjs --dry-run  # 只打印将要执行的动作
  ```

- 发版时顺序：写 `CHANGELOG.md` → `npm run check:changelog` → commit/tag/push → `sync-github-releases.mjs`。
- 已存在的 Release 会被覆盖成 CHANGELOG 内容；历史 tag 的注释不再作为正文来源，不要为了改文案重签 tag。
- 不要在 Release 里写仓库内部路径、密钥、未上线能力；「内部与验证」段可以保留在 CHANGELOG，但同步脚本会原样带上，
  因此写内部路径时默认它是可以公开的（这个仓库目前就是公开的）。

## 9. 范例（v3.2.0 摘要，可照此扩写）

```
## v3.2.0 · 右轨拍平 · 账户中心两栏 · 2026-11-02

右轨从「省略号里藏功能」变成一排可直接点的圆钮，账户中心按 Figma 的左团队、右项目重排。
这一版不改生成算法，改的是「东西在哪、点了会怎样」。

**你能直接用到的**
- **视角一颗钮**：右轨原来分开的「俯视」「正面机位」和藏在「更多」里的「整体」合成一颗钮，
  点一下按 整体 → 俯视 → 正面机位 轮换，图标始终显示当前机位。
- **导出不再藏在更多里**：右轨底部直接一颗「导出效果图」，弹层从按钮下沿向上展开，
  窗口高度不够也不会被切掉。

**改好了什么**
- 之前空间/物料会把左卡硬撑到 420px、切回 Bingo 又缩回去；现在四个 agent 共用同一个宽度。

**边界与未做**
- 画布还不支持框选矩形多选，选择工具只做「回到选择态 + 清零工具」。

**内部与验证**
- `npx tsc --noEmit` 0 错；`vitest run components/room-organizer/panels/scendance-workspace.react.test.tsx` 22 条全绿。
```

# 56 · 小程序定位重构：从「采集工具」到「微信里的 Scendance 窗口」（2026-11-05）

> 一句话定位：**小程序不再是采集端，是 Scendance 在微信里的窗口。**
> 它负责现场引导、状态分享、跨端转交；原始素材（照片/视频）的上传与重建，
> 仍由网页端按 `docs/51` 的双端入口模型承担。
>
> 这不是降级，是把小程序从一条**当前跑不通**的链路上撤下来——
> Aholo 图片通道 12 连死、微信小程序单文件 10MB/后台 5 秒挂起/无断点续传，
> 三件事同时成立时，「在小程序里拍完即重建」这件事在物理上就不成立。
> 而 Aholo 自己已经有 iOS/Android/鸿蒙 App 把采集全链路免费做完了，
> 我们不该在采集上跟它比。

---

## 1. 背景与现状

### 1.1 三件同时成立的硬事实

| # | 事实 | 数字 / 证据 | 对小程序的含义 |
| --- | --- | --- | --- |
| ① | **Aholo 图片通道是坏的** | 同一账号 12 次图片任务全部 `FAILED progress=1`，`assets.splats.urls` 全 null，无失败原因；与素材内容、上传方式、参数无关（`docs/53` §7、`docs/51` §3.2） | 小程序原本规划的「拍 20–40 张照片即重建」这条主链路，**后端就是断的**，不是前端能修的 |
| ② | **Aholo 视频通道正常，但素材太大** | 26 秒连续走拍出 SPZ **23.2 MB**，normal 档 12.6 分钟、low 档 8.5 分钟（`docs/53` §7，`world-3FO4K4RKIQ9S`）；代理单文件上限 512MB | 视频是当前唯一能出模型的通道，但小程序 `wx.uploadFile` 单文件 **10MB**、`maxDuration` **60 秒**，1080p/60s 视频约 80–150MB，物理上传不上去 |
| ③ | **微信运行机制卡死了大文件上传** | 后台 **5 秒** JS 线程挂起、锁屏/来电必掉、官方**无断点续传 API**、`wx.uploadFile` 整文件一次性请求（`docs/51` §3.1） | 即使把视频压到 10MB 以内，切后台/锁屏/来电仍会让上传半途而废，且没有续传兜底 |

三件事叠加的结论：**小程序端到端「现场采集 → 上传 → 重建」这条链，当前在产品上跑不通。**
不是体验差，是三个环节里任意一个都过不了。

### 1.2 已有小程序进度（不要浪费）

| 项 | 现状 | 来源 |
| --- | --- | --- |
| AppID | `wxd16c2833f4591a29`，个人主体 | `project.config.json`，`docs/55` §1.2 |
| 已上传版本 | v0.1.0 开发版（422.7 KB），CLI 已登录 | `docs/53` §6、`docs/55` §1.2 |
| 主包体积 | **1.46 MB / 2 MB 上限（72.9%）** | `docs/55` §1.2 |
| 已接链路 | 拍摄页、快检骨架、`services/recon.js` mock/real 双模式、额度预扣/返还契约对齐、位置授权修复、虚拟支付参数名修复 | `docs/55` §4 A-1～A-8 |
| 已接视频入口 | `wx.chooseMedia` 已扩 `mediaType: ['mix']`、`maxDuration: 60`、`fileType==='video'` 走 `addVideoClip` | `docs/53` §7 小程序端改动清单 |
| 仍阻塞 | ICP 备案、已备案境内 HTTPS 域名、后端匿名重建入口（`docs/55` §3 关键路径 ①②④） | `docs/55` §3 |

### 1.3 一个被忽略的外部事实

**Aholo 自己有 iOS / Android / 鸿蒙 App**，引导拍摄 + 上传 + 重建 + 基础编辑全链路免费。

这意味着：

- 在「采集体验」这件事上，我们面对的不是空白市场，是一个**已经把免费采集做完了**的官方 App。
- 用户真要在现场拍一段视频出模型，直接装 Aholo App 就能完成，不需要我们。
- 我们再在小程序里做一个「轻量采集版」，体验必然不如官方 App（它能调系统相机底层、能持续录、能本地压缩），且仍然绕不过微信 10MB/5 秒的墙。

**结论：采集不是我们的差异化。**

## 2. 定位重构

### 2.1 从「采集工具」到「微信窗口」

| 维度 | 旧定位（`docs/51` §0 原口径） | 新定位（本文） |
| --- | --- | --- |
| 一句话 | 现场拍 20–40 张照片，一小时内看粗模 | **Scendance 在微信里的窗口** |
| 主任务 | 现场拍照 + 上传 + 等结果 | 现场**引导** + 状态**分享** + 跨端**转交** |
| 素材归属 | 小程序自己传照片给 Aholo | 原始素材一律走网页端；小程序只做引导与查看 |
| 与 Aholo App 的关系 | 替代它（拍得更好） | 不与它正面竞争；做它不做的事 |
| 端到端闭环 | 拍完即出模型 | 现场引导 → 转交网页 → 网页上传重建 → 结果回微信分享 |

### 2.2 为什么「窗口」是对的

| 我们有、Aholo App 没有的 | 说明 |
| --- | --- |
| 微信原生分享 | 重建结果、任务状态一键发群/好友/朋友圈——这是 Aholo 独立 App 做不到的（它要跳出微信、装独立应用、再分享到微信还要绕道） |
| 域内拍摄评分 | `docs/53` S1–S3 已经把「构图、光照、走拍速度、关键立面覆盖、层别推断、模式推荐」做成了 domain-specific 引导；Aholo 通用 App 不懂得「幕景/宴会/活动场地」这个场景 |
| 跨端账号与任务表 | `docs/51` §4 的 `accounts / account_links / handoff_tickets` 已经把「微信里看网页任务、网页扫码绑微信账号」设计好了，小程序是这套模型的天然入口 |
| 微信内免安装 | 用户不用下载 100MB+ 的独立 App，扫码即用 |

## 3. 三件事：现场引导 / 状态分享 / 轻量转交

### 3.1 现场引导（P0）

**做什么**：把 `docs/53` S1–S3 的网页端实时引导能力，迁一份到小程序取景页。

| 子能力 | 具体 | 与网页端分工 |
| --- | --- | --- |
| 实时拍摄评分 | 构图、光照、走拍速度、关键立面覆盖度——沿用 `frontend/lib/capture-guide/*` 同一套阈值真源（`scripts/gen-thresholds.mjs`） | 网页端是「录像 + 抽帧质检」完整版；小程序是「取景时单行提示」轻量版 |
| 层别推断 | 设备俯仰角推断 low/eye/high 层（S2，`inferLayerFromDeviceTilt`） | 两端同一逻辑，小程序只显示「切到 X 层」chip，不自动切 |
| 模式推荐 | 场地多大？三 chips 推荐视频/照片（S3） | 小程序推荐后**不直接触发拍摄上传**，只引导用户「用相机拍好后，到网页/官方 App 上传」 |
| 单指令纪律 | 沿用 `shot-rules.ts:73-77`：一次只给一个动作（「请抬高手机」/「请绕到背面」） | 两端共用同一条纪律 |

**功能边界**：
- ✅ 取景、构图提示、评分、层别建议、模式推荐。
- ❌ **不在小程序里提交素材给 Aholo**。引导完就结束，不触发上传、不建 `recon_jobs`。
- ❌ 不做实时抽帧重建那一套（`VideoDecoder` 真机可行性都还没验，`docs/53` §7 末段）。

### 3.2 状态分享（P0）

**做什么**：用户在网页端跑完重建后，把结果拉回微信里看、分享。

| 场景 | 功能 | 依赖 |
| --- | --- | --- |
| 看任务状态 | 小程序「我的任务」列表，读 `recon_jobs`，显示 `status/progress/outputs`（沿用 `docs/51` §5 状态机与 7 个最小接口） | 后端匿名入口（`docs/55` §3 ④）+ 已备案域名 |
| 看结果预览 | 4 张预览图 + 一句话说明；不内置 3DGS 渲染器（`docs/51` ADR-05） | `outputs.pano` / 缩略图 |
| 分享给群/好友 | `wx.shareAppMessage` / `wx.onShareTimeline`，卡片带 jobId 与预览图 | 微信原生，零额外成本 |
| 分享给非微信用户 | 生成一个短链/二维码，点开是网页结果页 | 网页结果页已存在 |

**功能边界**：
- ✅ 看、转发、分享卡片。
- ❌ 不在小程序内置 3DGS 查看器（包体 1.46MB/2MB，塞不下；真机 WebGL 未验）。
- ❌ 不做导出（GLB/SPZ/PLY 一律网页端下载，`docs/51` §6）。

### 3.3 轻量审核转交（P1）

**做什么**：现场看完引导后，一键生成一个 **handoff ticket**，把「这个场地、这次引导、这个账号」交给网页端继续。

这不是新发明——`docs/51` §4 的 `handoff_tickets` 表（`id / account_id / direction / expires_at / used_at`，5 分钟失效、用后作废）已经是现成的。

| 流转 | 实现 |
| --- | --- |
| 小程序 → 网页 | 引导页底部「在网页继续上传/编辑」→ 后端签 ticket → 拉起 `https://<web>/auth/handoff?ticket=…`（沿用 `docs/51` §4 路径 1） |
| 现场同步的元数据 | ticket 里带 `capture_meta`（评分、层别、GPS 覆盖、关键立面缺口），网页端接手时直接看到「用户在现场被提示过哪些」 |
| 网页 → 小程序（反向） | 网页任务页显示二维码 → 小程序 `wx.scanCode` → `POST /auth/handoff/claim` 绑账号（`docs/51` §4 路径 2） |

**功能边界**：
- ✅ 生成 ticket、带元数据、5 分钟失效、用后作废。
- ❌ 不在小程序里跑「继续上传」——网页端接手后，原始素材仍由网页按 5MB 分片直传 OUS（`docs/51` §3.3）。
- ❌ 不做实时协同编辑（多人同时看同一任务）。

## 4. 落地优先级

| 优先级 | 做什么 | 依赖 | 解锁条件 | 明确不做的事 |
| --- | --- | --- | --- | --- |
| **P0** | ① 取景页实时引导（S1–S3 阈值迁小程序，纯前端）<br>② 「我的任务」列表 + 结果预览 + 微信分享卡片 | ① 无外部依赖，纯前端可做<br>② 后端匿名入口 + 已备案境内域名（`docs/55` §3 ②④） | ① 立刻可排<br>② 等域名与后端入口 | 不在小程序里建 `recon_jobs`、不触发上传、不做 3DGS 查看器 |
| **P1** | handoff ticket：小程序引导页 → 网页继续 | P0 ② 的后端入口 + `handoff_tickets` 表（`docs/51` §4 已设计） | P0 ② 上线后即可排 | 不做反向扫码绑账号以外的协同 |
| **P2（待外部解锁）** | **视频压缩采集路径**：`wx.chooseMedia({ compressed: true })` 真机验证压缩后 < 10MB 且 Aholo 视频通道可重建 | ① Aholo 图片通道修复（官方 bug，等他们）<br>② 或：真机实测压缩视频 < 10MB 后能否被 Aholo 视频通道受理 | 两个解锁条件**任一**成立 | 在解锁前，不排卡、不烧额度、不做分片/断网续传的私有实现 |

### 4.1 P2 为什么是「等」，不是「做」

`docs/51` ADR-02 已经否决过「压到 10MB」这条路，理由是：压到 10MB 要降分辨率/帧率，而 Aholo 视频通道靠抽帧配准，压完大概率重建失败。
现在多了一个变量——`wx.chooseMedia({ compressed: true })` 的真实压缩率没有真机数据。
**这是一个「不烧额度、不写代码就能先量出来」的问题**：拿一台真机，录一段 26 秒走拍，看压缩后多少 MB。

| 真机实测结果 | 结论 |
| --- | --- |
| 压缩后 > 10MB | 路径直接死，ADR-02 维持 |
| 压缩后 5–10MB，但 Aholo 重建失败 | 路径死，ADR-02 维持（配准率不够） |
| 压缩后 < 10MB 且 Aholo 重建成功 | 路径解锁，重开 ADR-02 |

在真机数据出来前，排任何代码都是过早优化。

## 5. ADR：小程序不再承担原始视频/照片上传

- **问题**：`docs/51` 原本让小程序承担「现场 20–40 张照片」的上传；`docs/53` §7 又把视频入口接进了小程序。现在 Aholo 图片通道坏、视频文件太大、微信运行机制卡死——小程序到底还传不传素材？
- **结论**：**小程序不再承担任何原始素材（照片或视频）的上传**。所有素材上传一律走网页端（5MB 分片、断点续传、单文件 512MB）。
- **否决 A「继续传照片，等 Aholo 修」**：图片通道是 Aholo 侧 bug，12 连死，受理后运行时速死，不是我们能修的；在它修好之前，让用户在小程序里拍 30 张照片再全部失败，是在制造坏口碑。
- **否决 B「小程序传压缩视频，赌它能重建」**：`wx.uploadFile` 10MB + 后台 5 秒挂起 + 无续传，三个硬约束没有一个能绕过；压到 10MB 的视频配准率未经真机验证。路径见 §4.1，等真机数据再议。
- **否决 C「自己实现分片/断点续传」**：官方没有分片 API；后台 5 秒挂起会让任何自实现的分片状态半途而废；这是逆着微信运行机制硬干。
- **采用**：小程序只做三件事——现场引导（不触发上传）、状态分享（只读）、handoff（生成 ticket 交网页）。原始素材上传、分片续传、512MB 大文件、重建提交，全部归网页端。
- **代价**：用户现场拍完不能「立刻」在微信里出模型，必须跳网页（或装 Aholo 官方 App）继续。这是真实的体验落差，用「引导做得更准 + 分享做得更顺」来补。
- **回退条件**：① Aholo 官方修复图片通道并实锤 2/2 成功（`docs/51` §9 验收第 5 项）；或 ② 真机实测压缩视频 < 10MB 且 Aholo 重建成功。任一成立，重开此 ADR。

## 6. 与 `docs/51` 双端入口模型的对齐

本文**不另起一套口径**，以下逐条对齐 `docs/51`：

| `docs/51` 原口径 | 本文是否变更 | 说明 |
| --- | --- | --- |
| 「一个账号、一张任务表、两个入口」（§0） | **不变** | `accounts / account_links / recon_jobs` 仍是唯一真源；小程序仍是入口之一 |
| 「小程序现场拍 20–40 张照片」（§0、§0 决策表） | **收窄** | 小程序改为只做引导，**不建 `recon_jobs`、不写 `recon_assets`**；任务表仍由网页端写 |
| 「网页收整段视频/SD 卡」（§0） | **加强** | 网页端从「也可以传照片」升级为「所有原始素材的唯一入口」 |
| 7 个最小接口（§5.4） | **不变** | 小程序前端调用其中 `GET /jobs/:id`、`POST /auth/handoff` 这两个只读/绑账号接口；`POST /jobs` / `sign` / `complete` / `submit` 全部由网页端调用 |
| 状态机（§5.3） | **不变** | 小程序只读展示，不写状态 |
| handoff_tickets（§4） | **不变，且升级为 P1** | 原本是「编辑转网页」的小功能，本文把它升为小程序端的核心交付之一 |
| ADR-05「小程序不内置编辑器」 | **不变** | 本文只是把「不内置编辑器」扩到「不内置上传、不内置 3DGS 查看器」 |
| ADR-02「小程序不做视频」 | **不变，且加严** | 原本是「不做视频上传」；本文加严为「照片上传也不做」，理由见 §5 |
| 失败与重试（§7） | **不变** | 失败页、worldId 显示、次数返还规则全部沿用 |
| 上线前真机验收 5 项（§9） | **不变** | 第 5 项「Aholo 图片通道是否修复」恰好是本文 §5 回退条件① |

**一句话对齐结论**：`docs/51` 的双端入口骨架（一张表、两个端、ticket 跨端）原样保留；
本文只把「小程序 = 采集端」这一格，改成「小程序 = 引导 + 分享 + 转交窗口」。
网页端从「视频入口」升级为「所有素材的唯一入口」。

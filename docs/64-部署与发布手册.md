## 1. 本地起服务（不依赖 Docker）

```sh
npm ci
npm --prefix frontend ci
npm run check                 # 根：tsc + tests/（PGlite 内跑全部迁移）
npm run check:edge            # Deno 类型检查
npm run smoke:edge            # 函数运行时冒烟
npm run check:config          # 核心配置预检，允许供应商未配
```

- 需要 Node.js ≥ 24.15（见根与 `frontend/` 的 `.nvmrc`）。
- `check` 在临时 PGlite PostgreSQL 实例里跑迁移与业务测试，**不碰任何已有项目或云端库**。
- `check:config:full` 会逐项报告缺失的供应商字段；预检只验字段与费用范围，不调用供应商，也不证明账号权限可用。
- 可选：`npm run check:public-model` 走真实网络拉一个公开 GLB 做打包校验，不产生费用。

前端本地开发：

```sh
npm --prefix frontend run dev   # http://localhost:3000，同时拉起本机 3199 代理
```

`localhost` 与 `127.0.0.1` 是不同 Origin，涉及 CORS 的地方两边都要列。

## 2. 完整 Supabase 本地栈（需要 Docker）

```sh
npx supabase start
npx supabase db push --local
npx supabase migration list --local
npx supabase db advisors --local --type security --fail-on warn
npx supabase db lint --local
```

- 本地 `config.toml` 已设为：开放邮箱注册并要求确认、匿名登录关闭、PostgreSQL 17、业务 schema 不暴露。
- **不要用 `db reset` 清理已有本地数据。**
- 本地 Edge：`npx supabase functions serve --env-file .env.edge.dev.local`。`SUPABASE_URL` 与 service role key 由平台自动注入，不要把含账号密码的 `.env.local` 当云端 secrets 文件用。

## 3. 云端项目与迁移

目标项目：`wkhfvnzgopjdzxlmycks`。

```sh
npx supabase link --project-ref wkhfvnzgopjdzxlmycks
npx supabase db push --project-ref wkhfvnzgopjdzxlmycks --dry-run   # 先看清单
npx supabase db push --project-ref wkhfvnzgopjdzxlmycks
npx supabase migration list --project-ref wkhfvnzgopjdzxlmycks
```

- `--dry-run` 应列出仓库里全部 61 份迁移；数量对不上就停下来查，不要硬推。
- 迁移只向前：已推过的版本号不要改名，后续改动新增 `supabase/migrations/<时间戳>_xxx.sql`。
- 迁移包含对 `anon` / `authenticated` / `service_role` 的授权，托管项目自带这些角色。
- 承载真实数据后**任何 `db reset` 都会清空数据**。
- 用 CLI 之外的通道（Management API、SQL Editor）落库时，要同时登记迁移历史，否则下次 `db push` 会重复执行。

## 4. 部署 Edge Functions

```sh
npx supabase functions deploy scene-api conversation-api pay-api generation-worker reconstruction-worker \
  --project-ref wkhfvnzgopjdzxlmycks --use-api
```

- `--use-api` 走官方 API 打包上传，不需要本地 Docker。
- 五个函数在 `supabase/config.toml` 中都是 `verify_jwt = false`：`scene-api` / `conversation-api` 在函数内部校验 Auth JWT（匿名分享入口另校验令牌与撤销状态）；两个 worker 用各自的 Bearer secret；`pay-api` 的支付宝回调单独验签。
- **已知缺口**：`npm run check:edge` 目前只检查 `scene-api`、`generation-worker`、`reconstruction-worker`。改到另外两个函数时，单独跑：
  ```sh
  deno check --config supabase/functions/deno.json \
    supabase/functions/conversation-api/index.ts supabase/functions/pay-api/index.ts
  ```
- 部署后检查 Dashboard → Edge Functions 五个函数均为 ACTIVE，并跑第 10 节的验收。

## 5. Secrets 与供应商

模板：根 `.env.example`（脚本与本地）、`supabase/functions/.env.example`（Edge）。复制成 `supabase/functions/.env.local` 后再改，**生成的文件已被 Git 排除**。

### 5.1 必填（与供应商无关）

```dotenv
PUBLIC_APP_URL=https://scendance.lilicoding.space
ALLOWED_ORIGINS=https://scendance.lilicoding.space,https://scendance-scene-planner-ewz.pages.dev,http://localhost:3000,http://127.0.0.1:3000
GENERATION_WORKER_SECRET=<随机 32 字节>
RECONSTRUCTION_WORKER_SECRET=<另一个独立的随机值>
```

`ALLOWED_ORIGINS` 是 CORS 白名单，漏了当前域名前端会 403；localhost 与正式域名都要在。

### 5.2 文本与 Agent（Tokendance 网关）

- 端点 `https://tokendance.space/gateway/v1/chat/completions`，模型 `deepseek-v4.1-flash`，密钥 `TOKENDANCE_API_KEY`，集中在 `supabase/functions/_shared/providers.ts`。
- 未配网关时回退官方 `https://api.deepseek.com`（用 `DEEPSEEK_API_KEY`）。
- 两处调用都固定发送 `thinking:{type:'disabled'}`：该模型是推理模型，不关思考会把输出预算烧在 reasoning tokens 上，`content` 可能为空。
- 费用预留 `AI_MAX_REQUEST_CENTS`；一次应用请求按最多两次调用、每次 4096 输出 tokens 估算。`providers.ts` 里的 40 分预留下限仍按旧 DeepSeek 单价（CNY 2/M 输入、CNY 8/M 输出）推算，换价后要复核，避免预留不足。

### 5.3 图纸重建（直连 DeepSeek）

- 图纸重建（`reconstruction.ts`）仍直连 `api.deepseek.com` 的 `deepseek-flash`，并使用 DeepSeek 专有的 Files 上传接口；Tokendance 没有等价能力，**未改造前不要动这条链路**。
- 独立 `reconstruction-worker` + `RECONSTRUCTION_WORKER_SECRET`，不要混用生成 worker 的 secret 或定时器。

### 5.4 混元 HY-3D（已进入下线轨道）

- `HUNYUAN_API_MODE=tokenhub`：端点 `https://tokenhub.tencentmaas.com/v1/api/3d`，Bearer key 调 `hy-3d-3.0 / LowPoly / triangle`；旧平台账号可显式选 `legacy`（`api.ai3d.cloud.tencent.com`），没有自动跨平台重试。
- **`HY3_RETIRED=true` 时**：三项生成能力为 false，新的 text/image/texture 请求在计费与读素材前返回 `410 HY3_RETIRED`；worker 仍按任务固化的 provider 处理遗留任务，`submit_unknown` 不重发。
- 下线顺序：队列全部终态 → 停 `scene-generation-poll` → 再移除 `HUNYUAN_API_KEY`。`scene-reconstruction-poll`、重建 worker 与其授权配置保留。
- 任务记录**不保存**提供商模式。有未完成或提交结果未知的任务时，不得切换 `HUNYUAN_API_MODE`。

### 5.5 Aholo / Lux3D

- `LUX3D_API_KEY`、`LUX3D_TERMS_URL`、`LUX3D_TERMS_REVIEWED_AT` 三项齐全才算可用；`LUX3D_BASE_URL` 默认 `https://api.aholo.ai/global`。
- 显式声明 `provider: 'aholo'` 的任务不受 `HY3_RETIRED` 影响。

### 5.6 付费与扣次（`pay-api`）

- 支付宝 AI 付：`ALIPAY_APP_ID`、`ALIPAY_PRIVATE_KEY`、`ALIPAY_PUBLIC_KEY`（RSA2），金额以后端 SKU 表为准，不信任前端传值。
- `POST /pay/mock-paid`、`POST /scan/consume|release|expire` 见 `pay-api` 头部注释；mock 模式只允许在非生产配置下启用。

### 5.7 写入云端

```sh
npm run check:config:full
npx supabase secrets set --project-ref wkhfvnzgopjdzxlmycks --env-file supabase/functions/.env.local
```

- `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` 由平台注入，不需要手写。若某接口返回 `503` 且 `setting: "SUPABASE_SERVICE_ROLE_KEY"`，用 Dashboard 的 secret key 补一次。
- 写 secrets 不会触发任何生成请求。
- 不要用空模板整包覆盖云端：`PUBLIC_APP_URL`、`ALLOWED_ORIGINS`、worker secret 一旦被覆盖，线上会立刻 403 或全部 503。

## 6. Auth 与邮件验证码

模板在 `supabase/templates/`，云端要人工确认（仓库配置不等于云端已生效）：

| 模板 | Subject | 文件 |
| --- | --- | --- |
| Confirm signup | 幕景 Scendance · 确认注册验证码 | `confirmation.html` |
| Reset password | 幕景 Scendance · 重置密码验证码 | `recovery.html` |
| Password changed | 幕景 Scendance · 密码已更新 | `password_changed.html` |

Dashboard → Authentication：

1. Sign In / Providers → Email：启用，Confirm email 打开。
2. Email OTP length = `6`，expiration = `600` 秒。
3. Allow new users to sign up 开启；匿名登录不要启用。
4. Rate Limits：Emails = `30`/小时；SMTP minimum interval per user = `60` 秒。
5. URL Configuration：Site URL = 前端正式地址，回调保留 `/auth/callback`；旧域名重定向白名单保留。
6. 密码最短 12 位，与前端和迁移约束一致。

- 发信必须配独立 SMTP（Resend 等）：Supabase 内置发信只对项目组织成员有效且限流严格，不适合真实用户。
- 云端模板切换要**在含验证码表单的前端发布之后**，否则用户收到码却没有输入页。
- 邮件里的链接只指向普通页面，不带一次性 token，邮箱安全扫描不会自动消耗验证码；不要开启点击跟踪。
- 恢复令牌只存内存，不能当编辑器登录用、也不进 sessionStorage；页面刷新后需重新发码。旧邮件链接经 `/auth/callback` 识别 recovery 后进入改密页。
- 未注册邮箱得到与已注册相同的恢复提示，不用返回文案探测账号是否存在；重复注册也不靠 Supabase 的隐藏用户响应判断。
- 前端重发倒计时 60 秒（防刷与过期由 Supabase 强制）；全局退出失败要单独提示，不把已成功的改密报成失败。已签发的 access token 仍有效至到期。
- 只更新注册开关与回调时用最小配置 `supabase/ops/cloud-config.toml`，在临时目录审阅差异后应用；不要把本地完整 `supabase/config.toml` 整体推上云端（它含本地地址与测试账号假设，还会连带把邮箱登录关掉）。

## 7. 定时任务与队列


## 8. 账务、未知任务与恢复

- `submit_unknown`：先到提供商控制台核对该用户、时间与请求记录。**禁止直接改回 queued**。确认已建任务后，由管理员在一次事务内绑定正确 `provider_job_id` → submitted，并把 requests.state 改回 reserved；随后 worker 只查既有任务。确认未创建且无费用时，改 failed，由用户重新发起。
- 账单核对后按请求填 `actual_cents`，保留 `provider_usage`；要降低过高预留，须在同一事务锁定对应 budgets 行并按差额调整 `committed_cents`。默认不自动退款。
- `rejected`：模型超体积/复杂度、格式或纹理不兼容、结构校验失败。不能标 ready；保留原始提供商 ID。
- `archiving`：Storage 或下载临时失败时保留任务，定时器下次取新地址；超过 23 小时仍无法恢复则标失败，不自动重新付费。
- Storage 上传成功而 DB 写入失败会留下无引用对象：短期保留用于恢复，清理前对照 `assets` 与所有 publications。
- 编辑冲突/离线：客户端保留未保存草稿，不自动覆盖服务器，不把超时显示成已保存。
- 回滚：保留部署前数据库备份与函数版本。**函数回滚不能撤销迁移、已发任务或已签发的文件。** 紧急停付费任务先停 cron 并禁用对应调用配置，不删未确认的任务记录。

## 9. 发布顺序

1. 版本号三处同升：`package.json`、`frontend/package.json` 与两份 `package-lock.json`（`npm version X.Y.Z --no-git-tag-version`）。
2. 按 [65-版本更新文案规范](65-版本更新文案规范.md) 写 `CHANGELOG.md`，跑 `npm run check:changelog` 必须 0 error。
3. 验证：`npm run check`、`npm --prefix frontend run typecheck`、`npm --prefix frontend run test`、`npm --prefix frontend run build`；改了函数再加 `npm run check:edge` 与第 4 节的手工 `deno check`。
4. 推迁移 → 部署五个函数 → 复查函数状态。
5. 前端由 Cloudflare Pages 从 `main` 自动构建发布；构建设置与 `CARTO_KEY` / 高德 key 的运行时位置见 [66-Cloudflare部署](66-Cloudflare部署.md)。
6. 部署后在 CHANGELOG 该版本的「内部与验证」写清实机核对方式与结果。

## 10. 验收

```sh
# 健康检查（无需登录）
curl https://wkhfvnzgopjdzxlmycks.supabase.co/functions/v1/scene-api/health

# 云端写入型冒烟：会真实写入验收项目与资产，结束时清理临时账号与分享
npm run smoke:cloud -- --write --remote
```

人工最小闭环：

1. 注册真实邮箱 → 收六位码 → 确认 → 自动登录；数据库触发器应已建好个人工作室。
2. 新建项目 → 保存 → 刷新重开，云端版本能恢复。
3. 分享 → 匿名打开只读页 → 撤销后失效。
4. Agent 第一句能出结构化回答（`conversation-api`）。
5. 付费入口在未配置 `pay-api` 时返回可读错误，不伪造成功。

`smoke:cloud` 不调用付费模型。它失败时先看是哪一组检查红，不要用「函数是 ACTIVE」替代。

## 11. 安全与常见坑

- **密钥分层**：浏览器只能拿 publishable/anon key；`service_role` / `sb_secret_`、供应商密钥、worker secret、支付宝私钥只出现在服务端。
- **迁移与函数一起更新**：改了 RPC 签名只部署函数不推迁移，运行期才炸。
- **不要跨项目搬密钥**：换项目时 URL 与 key 成套更换。
- **不要整包覆盖 secrets**（见 5.7）。
- **不要再引用 `archive/legacy/` 的部署步骤**：那批文档 2026-11-21 已删除或替代，本页是唯一现行入口。

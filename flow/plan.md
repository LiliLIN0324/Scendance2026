## 开发顺序

1. **基础收尾**：完成正在推进的备份恢复、保存边界及身份可靠性修复；前端最新用户要求的首次入口/当前阶段/下一步清晰度优先处理，沿用三工作区而非再造系统。
2. **第一增量A · 人工创意简报**：在原description提供人工模板，覆盖目标、观众、交付范围、已知约束，以及到达/进入/观看/交流/离开体验节点。保留已有文字、保存、备份和生成上下文，不先加平行schema。
3. **第一增量B · 客户评审包**：冻结同一时点的需求、布局、采用版本、人工意见与待确认项；先用画面和文字查看/打印/导出，模型不可交付单列原因，不依赖Scene JSON/GLB转换成功。编辑动作、团队自查和真实客户意见分别记录。A与B均通过后才算第一增量完成。
4. **第一增量后续 · 统一结构化**：依据试跑补体验节点、普通方案要求/亮点、物件/图层/活动任务关联，公共契约、保存、恢复、备份、生成上下文同步扩展。
5. **第二增量 · 制作资源与业务财务**：物料已有/租赁/购买/制作方式、真实来源、确认规格、运输安装与报价依据；费用关联任务/物料，区分估算/确认报价/实际费用，记录收付款条件与计划/实际时间。未知金额为空，不混入AI成本或旧演示预算。
6. **第三增量 · 变更、复盘与案例**：记录变更原因、时间/费用影响、决定及处理；复盘分别记录目标、计划实际、客户意见、观众反馈、经营结果和下次改进；展示须真实资料与对应许可，演练明确标识。
7. **合作扩展**：在真实共同回填需要下验证双账号、权限、冲突、保存与回读后接云协作；已有本地执行/云转换保护保持，AI改稿及云转换先补齐并验证公共契约。真实服务、费用、发布与客户联系仍遵守授权边界。

## 每轮执行

先看用户新反馈与本记录，选择一个最影响办活动的小问题。没有当前证据时做短的官方案例研究，记录具体来源、适用操作及取舍；研究必须服务一次实现或明确决策，不能只堆案例。

记录预期行为 → 实现最小增量 → 相关测试与真实浏览器试用 → 回读保存/导出 → 交接。遇到既有失败先分清根因，不削弱检查。已通过检查不重复全跑，除非代码变化或新风险需要。使用独立测试来源/演练场景，不改变用户当前输入。Next dev 与 build 不同时写同一个缓存；服务启停由导演协调。

每轮完成后给出已做改进、实际证据、已知限制和下一步。Windows 文件问题修复后进入现有适用 skill。没有新问题或可推进工作保持安静，不生成空报告。
